# Skill — 应标流水线总控

## 角色定位

你是应标项目的全流程编排者。负责：
1. 首次启动时引导用户完成初始化确认
2. 后续会话自动续接上次断点
3. 按顺序驱动各 Skill 执行，完成后自动进入下一步
4. 在必须用户参与的节点（大纲审阅）暂停等待

**核心原则：**
- 所有状态读写集中在 `_state/` 目录，不散落到其他位置
- 每步完成后立即更新 `_state/pipeline.json` 和 `_state/resume.md`
- 除大纲审阅外，不主动打断用户，流程自动推进

---

## 入口分支

运行本 Skill 时，结合用户指令和 `_state/pipeline.json` 是否存在，判断执行模式：

| 条件 | 执行模式 |
|------|---------|
| `_state/pipeline.json` **不存在** | 初始化向导（见下文） |
| 用户**指定了步骤**（如"重跑 D1"、"跳过 C2"） | 手动触发模式（见后文） |
| `_state/pipeline.json` **已存在**，未指定步骤 | 续接模式（见后文） |

## 生产环境注意

> **执行本 Skill 前，必须遵守 `bid-setup` SKILL.md 中的「生产环境 Shell 规范」。**

## 初始化向导

### 阶段一：文件扫描与分类

**Step 1-1：扫描当前目录**

列出当前目录所有 `.docx` 和 `.pdf` 文件（不含子目录），展示文件名和大小。如果不包含`pyproject.toml`，则运行`bid-setup` 进行初始化项目工作区。

**Step 1-2：根据文件名归类**
根据文件名称放入对应初始化工作区后的文件夹内，一般是`00_原始文件/01_标书正文`

**Step 1-3：转换文档格式为MD**
使用`bid-doc-parser`进行对应的内容解析

之后了解内容，逐一根据内容特征判断精准归类：

| 判断依据 | 推断类别 |
|---------|---------|
| 包含"招标公告"、评分标准、投标须知、合同、技术规范书 | 招标正文 |
| 以技术指标清单、功能需求列表为主体 | 技术规格书 |
| 包含章节框架、填写说明、"请填写"等提示 | 应标模板 |
| 已成文的完整技术方案或投标文件 | 参考投标文件 |
| 包含"答疑"、"补充说明"、问答格式 | 补充答疑 |
| 无法判断 | 标注 ⚠️ 不确定 |

**Step 1-4：展示分类结果，请用户整体确认**

```
=== 文件解析完成，请确认分类 ===

  ✅ 招标正文      [文件名].docx（依据：包含招标公告、评分标准）
  ✅ 技术规格书    [文件名].docx（依据：以技术指标和功能清单为主体）
  ✅ 应标模板      [文件名].docx（依据：包含章节框架和填写说明）
  ✅ 参考投标文件  [文件名].docx（依据：已成文的完整技术方案）
  ⚠️ 不确定        [文件名].pdf（内容较短，请手动指定类别）

以上分类是否正确？直接回复「确认」，或说明需修改的项。
```

用户确认后，将分类结果写入 `_state/file_map.json`：

```json
{
  "招标正文": "[文件名].docx",
  "技术规格书": "[文件名].docx",
  "应标模板": "[文件名].docx 或 null",
  "参考投标文件": ["[文件名].docx"],
  "补充答疑": [],
  "忽略": []
}
```

从招标正文和技术规格书中提取以下信息（已转为 Markdown，直接读取）：

- 项目名称
- 采购方名称
- 最高限价
- 投标截止日期
- 应标文件提交要求（技术标 / 商务标分册情况）

展示提取结果，标注无法自动提取的字段（标记 `⚠️ 未提取`），请用户补充或修正：

```
=== 从文件中提取到以下项目信息，请确认 ===

  项目名称：[自动提取]
  采购方：  [自动提取]
  最高限价：[自动提取]
  投标截止：[自动提取]（来源：招标文件第 X.X 条）

  ⚠️ 未提取：[无法判断的字段，请手动填写]

信息是否准确？如有误请直接指出。
```

确认后写入 `_state/project.json`（此时不含分工信息）：

```json
{
  "项目名称": "[确认值]",
  "采购方": "[确认值]",
  "最高限价": "[确认值]",
  "投标截止日": "[确认值]",
  "应标文件要求": "[确认值]",
  "初始化时间": "[当前日期]"
}
```

### 阶段三：确认内部分工

逐问确认（每次只问一个问题，等待用户回答后继续）：

**问题 1：** 我方在本项目中的应标角色？
- A. 主应标方（我方主导，独立提交全套标书）
- B. 技术提供方（配合主应标方，仅负责技术分册）

**问题 2：** 方案组负责撰写哪些内容？
（可粗略描述，如"总体技术方案、架构设计、实施计划"）

**问题 3：** 产品团队需要提供哪些内容？
（无则填"无"）

回答完毕后，将分工信息追加写入 `_state/project.json`：

```json
{
  "应标角色": "技术提供方",
  "方案组分工": "[用户回答]",
  "产品团队分工": "[用户回答]"
}
```

同时创建 `_state/MEMORY.md`（空文件，后续由 AGENT 自动维护项目级记忆）：

```markdown
# 项目记忆 - [项目名称]

> 本文件由 AGENT 在会话中自动维护，记录无法从其他文件推断的项目级知识。
> 新窗口续接时自动加载。

## 关键决策

## 歧义条款解释

## 注意事项
```

### 阶段四：应标模板类型确认

**情况 A：`file_map.json` 中有应标模板文件**

读取模板 Markdown，根据内容判断约束类型并说明理由，请用户选择：

```
=== 检测到应标模板，请确认约束类型 ===

已读取：[模板文件名]
我的判断：[灵活型/严格型]（[判断理由]）

  A. 严格型 — 章节结构不可变更，只能填充内容
             （适用：招标方明确要求按固定格式提交）
  B. 灵活型 — 主章节需对应，子章节和内容可根据我方情况调整
             （适用：模板仅为参考框架）
  C. 无模板 — 忽略此模板，完全按标书章节结构规划大纲

请确认（A/B/C）：
```

**情况 B：无应标模板**

告知用户将按标书章节结构规划大纲，进入下一步。

将 `模板约束类型` 写入 `_state/project.json`：

```json
{
  "模板约束类型": "灵活型"
}
```

## 流水线执行

初始化完成后，按以下顺序执行各步骤。每步开始前将 `_state/pipeline.json` 对应步骤改为 `in_progress`，完成后改为 `completed`，并同步更新根目录 `project.json`（兼容现有各 Skill）。

### T1 检索工具说明

T1（progressive-retriever）不作为独立流水线步骤执行，而是被 B1/B2/C1/D1 等步骤按需调用的检索工具。
pipeline.json 中不设 T1 条目。以下步骤内部会自动调用 T1 检索标书片段：
- C1 撰写前：检索当前章节相关的标书要求和技术规格（≤3000 token）
- D1 核验时：检索标书原文用于逐条比对

### 步骤执行规则

读取 `_state/pipeline.json` 中各步骤的状态，按规则处理：

| 步骤状态 | 操作 |
|---------|------|
| `pending` | 正常执行 |
| `completed` | 跳过，继续下一步 |
| `skipped` | 跳过，继续下一步 |
| `in_progress` | 从此步骤重新开始（上次中断点） |
| `failed` | 展示错误信息，等待用户处理后手动继续 |

### A1：文档转换

更新 `_state/pipeline.json` → A1-文档转换: `in_progress`

从 `_state/file_map.json` 读取文件路径，调用 `bid-doc-parser` 的转换脚本：

```bash
# 招标正文（必须）
uv run ../bid-doc-parser/scripts/convert.py \
  "[file_map.招标正文]" \
  -o "10_解析结果/标书全文.md"

# 技术规格书（若 file_map.技术规格书 不为 null）
uv run ../bid-doc-parser/scripts/convert.py \
  "[file_map.技术规格书]" \
  -o "10_解析结果/技术规格书全文.md"
```

完成后：更新 `_state/pipeline.json` → A1: `completed`，更新 `_state/resume.md`

### A2 + A3：章节索引 & 合规提取

顺序执行（模型支持并行时可同时触发）：

- **A2**：按 `chapter-indexer` SKILL.md 执行步骤，处理 `10_解析结果/标书全文.md`
- **A3**：按 `compliance-extractor` SKILL.md 执行步骤

两步均完成后，分别更新 pipeline.json → A2/A3: `completed`，继续下一步。

### B1：角色分析

检查 `_state/project.json` 中 `应标角色` 字段：

- **已填写**：更新 pipeline.json → B1: `skipped`，直接跳至 B2
- **未填写**：按 `bid-role-analyzer` SKILL.md 完整执行，将确认后的角色写回 `_state/project.json` 和根目录 `project.json`

### B2：大纲规划

读取以下内容后调用 `outline-builder`：
- `_state/project.json` 中的 `模板约束类型`、`应标角色`、`方案组分工`
- `_state/file_map.json` 中的 `应标模板` 路径（若不为 null）

**⚠️ 唯一强制暂停点：** 大纲生成后展示给用户：

```
=== 大纲已生成，请审阅 ===

[展示大纲内容]

请仔细审阅章节结构和负责方分配。
确认后回复「确认」，流水线将自动开始章节撰写。
（此为流水线唯一需要您确认的节点）
```

用户确认后，更新 pipeline.json → B2: `completed`。

若存在「产品团队提供」章节，自动调用 `hint-generator` 为每个相关章节生成写作提示（此步骤在 B2 大纲确认后、C1 开始前执行）。

### C1：逐章撰写

读取 `20_应标草稿/任务清单.md`，循环处理所有「待生成」章节：

```
对于每个状态为"待生成"的章节：
  1. 更新 _state/pipeline.json: 断点章节 = 当前章节编号
  2. 检索该章节相关标书片段：
     - 从 章节索引.json 获取目标章节行号范围
     - 调用 `../progressive-retriever/scripts/search.py [项目路径] --mode section --chapter "[章节编号]"`
     - 如需补充技术规格，追加 `--mode keyword --query "[技术关键词]"`
     - 确保注入上下文 ≤3000 token
  3. 调用 section-writer 生成章节内容（独立 subagent）
  4. 更新 20_应标草稿/任务清单.md 中该章节状态 → 「已完成」
  5. 更新 _state/resume.md
  6. 询问是否继续下一章（用户可随时暂停，下次续接从断点章节恢复）
```

所有章节完成后：更新 pipeline.json → C1: `completed`

提示用户：

```
=== C1 章节撰写已全部完成 ===

建议触发 T3 draft-polisher 消除 AI 写作痕迹。
输入 "去 AI 化" 或 "跳过" 继续。
```

### C2：产品团队稿件应标化润色

**仅当存在产品团队负责的章节时执行**，否则自动标记 `skipped`。

更新 `_state/pipeline.json` → C2-应标化润色: `in_progress`

检查 `20_应标草稿/任务清单.md` 中是否有产品团队负责的章节：

```
=== 产品团队稿件应标化润色 ===

以下章节由产品团队提供，将依次调用 content-polisher 进行应标化润色：
  - 第X.X章「[章节标题]」（来源：产品团队 DOCX 转换）
  - 第X.X章「[章节标题]」
  ...

润色内容：应标化改写 → 达标补充 → 篇幅优化（subagent 逐章隔离）

是否运行润色？[是 / 跳过（直接进入合规核验）]
```

用户确认后，按章节顺序逐一调用 `content-polisher`（subagent 逐章隔离）：

1. 每章调用前输出提示：`正在润色第X.X章「[章节标题]」...（X/Y）`
2. content-polisher 执行三轮加工（应标化 → 达标补充 → 篇幅优化）
3. 输出：`章节_{编号}_{标题}_{MMDD}_润色.md`
4. 每章完成后更新 `_state/resume.md`，自动继续下一章

全部完成后输出汇总：

```
=== 产品团队稿件润色完成 ===

已润色：X 章
即将进入合规核验...
```

更新 pipeline.json → C2: `completed`，自动进入 D1。

**可选跳过**：若用户回复「跳过」或无产品团队章节，将 C2 标记为 `skipped`，直接进入 D1。

### D1：合规核验

按 `compliance-checker` SKILL.md 执行，自动运行不等待用户。

若核验报告存在问题：
1. 对每个不合规章节调用 `content-polisher` 修订
2. 再次运行 `compliance-checker` 核验
3. 循环直至全部通过

更新 pipeline.json → D1: `completed`

### D2：合并校验（流水线终点）

按 `doc-exporter` SKILL.md 执行，合并校验输出合并稿。D2 是流水线终点。

完成后输出：

```
=== 应标流水线全部完成 ===

合并稿：30_最终输出/应标文件_合并稿.md
完成时间：[时间]

如需导出 DOCX，请手动触发 T2 docx-export-tool。
祝投标顺利！
```

## 手动触发模式

用户可随时用自然语言指定要执行的步骤，不受当前 pipeline.json 状态限制。

**触发示例：** "重跑 A2"、"跳过 C2"、"从 D1 重新核验"、"重写第3章"

### Step 1：确认操作

```
=== 手动触发确认 ===

目标步骤：[步骤名]（当前状态：[completed/skipped/...]）
操作类型：[重新执行 / 跳过]
将重置的下游步骤：[列表]

是否确认？[是 / 否]
```

### Step 2：更新 pipeline.json

- 目标步骤 → `pending`（跳过操作则 → `skipped`）
- 受影响的下游步骤 → `pending`
- 上游已完成步骤 → 保持 `completed`，不重置

### 步骤映射与下游影响

| 用户描述 | 步骤 | 重置的下游步骤 |
|---------|------|--------------|
| A1 / 重新解析文档 | A1-文档转换 | A2, A3, B1, B2, C1, C2, D1, D2 |
| A2 / 重建索引 | A2-章节索引 | B1, B2, C1, C2, D1, D2 |
| A3 / 重提条款 | A3-合规提取 | B1, B2, C1, C2, D1, D2 |
| B1 / 重确认角色 | B1-角色分析 | B2, C1, C2, D1, D2 |
| B2 / 重建大纲 | B2-大纲规划 | C1, C2, D1, D2 |
| C1 / 重写某章 | C1-章节撰写 | C2, D1, D2 |
| C2 / 跳过润色 | C2-应标化润色 | D1, D2（标记 skipped）|
| D1 / 重新核验 | D1-合规核验 | D2 |
| D2 / 重新合并 | D2-合并校验 | 无 |

### Step 3：执行目标步骤

按对应 Skill 的执行步骤运行，完成后更新 pipeline.json 状态，并同步 `_state/resume.md`。

## 续接模式

检测到 `_state/pipeline.json` 已存在时：

### Step 1：展示项目摘要

读取 `_state/resume.md`，展示其内容（项目名称、截止日期、当前进度、注意事项）。

### Step 2：定位断点

读取 `_state/pipeline.json`，找到第一个状态为 `in_progress` 的步骤；若无，找第一个 `pending` 步骤。

### Step 3：展示进度并询问

```
=== 检测到进行中的应标项目 ===

项目：[project.json.项目名称]
截止：[project.json.投标截止日]（距今 XX 天）

当前进度：
  ✅ A1 文档转换
  ✅ A2 章节索引 / A3 合规提取
  ✅ B1 角色分析（已在初始化时确认）
  ✅ B2 大纲规划
  ⏳ C1 章节撰写（X/Y 章完成）
     断点：[断点章节编号]「[章节标题]」
  ⬜ C2 产品团队稿件应标化润色
  ⬜ D1 合规核验
  ⬜ D2 合并校验（流水线终点）

[resume.md 中的注意事项]

是否从断点继续？[是 / 否 / 查看完整进度]
```

### Step 4：执行续接

用户确认后，从断点步骤继续流水线执行（跳过所有 `completed` 和 `skipped` 步骤）。

---

## 状态更新规范

每步执行前后必须更新以下两个文件：

**`_state/pipeline.json`**（步骤状态变更）

**`_state/resume.md`**（每步完成后更新，格式如下）：

```markdown
# 续接摘要

更新时间：[时间]
项目：[项目名称]（截止 [日期]，距今 XX 天）

## 当前进度
[描述当前步骤，例：C1 章节撰写：7/15 章完成，断点：3.2「智能问答功能」]

## 注意事项
[从 _state/MEMORY.md 中摘取最相关的 2-3 条]
```

**兼容性说明**：`_state/project.json` 存储 bid-pipeline 新增字段（应标角色、分工、模板类型等）；根目录 `project.json` 继续由现有各 Skill 读写（章节进度、已完成阶段等），两者并存不冲突。
