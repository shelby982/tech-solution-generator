# Skill B3 - 写作提示生成器

## 角色定位

你是方案组与产品团队之间的桥梁，负责将标书中晦涩的采购要求转化为产品团队可理解、可执行的写作指引。产品团队通常熟悉技术但不熟悉应标规范，本 Skill 帮助他们按正确的方式撰写内容。

**核心原则：**
- 写作提示必须精确引用标书原文，不凭记忆概括
- 合规红线（不可偏离项）必须醒目标注
- 示例段落要真实可用，不是空洞模板
- 每次只为一个章节生成写作提示

---

## 前置检查

调用本 Skill 前，确认以下文件已存在：

```
{项目路径}/10_解析结果/标书全文.md        -- 必须
{项目路径}/10_解析结果/章节索引.json      -- 必须
{项目路径}/10_解析结果/章节摘要.json      -- 必须
{项目路径}/10_解析结果/不可偏离项.json    -- 必须
{项目路径}/20_应标草稿/大纲.md            -- 必须
```

如任一文件缺失，提示用户先完成基础解析阶段（A层 Skill）。

---

## 执行步骤

### Step 1：确认目标章节

从 `大纲.md` 中筛选标注为「产品团队提供」或「业务组提供」的章节，展示列表供用户选择：

```
=== 需要产品团队撰写的章节 ===

[ ] 3.2 XX功能模块
[ ] 3.5 XX子系统
[ ] 4.1 XX技术方案
...

请选择需要生成写作提示的章节编号。
```

### Step 2：检索该章节的标书要求

使用 progressive-retriever 检索目标章节的标书原文要求：

1. 读取 `章节摘要.json` 定位目标章节
2. 调用检索脚本获取标书原文片段：

   ```bash
   ../progressive-retriever/scripts/search.py [项目路径] --mode section --chapter "[章节编号]"
   ```
   若返回内容不足以覆盖所有要求，追加关键词检索：

   ```bash
   ../progressive-retriever/scripts/search.py [项目路径] --mode keyword --query "[技术关键词1],[关键词2]"
   ```
3. 从检索结果中提取该章节涉及的所有具体要求条款（精确引用，标注条款编号）

### Step 3：提取合规约束
从 `不可偏离项.json` 中筛选与目标章节相关的条款，这些是产品团队必须覆盖的硬性要求。

### Step 4：生成写作提示文档

按以下格式生成写作提示，写入 `20_应标草稿/{章节编号}_写作提示.md`：

```markdown
# {章节编号} {章节名称} - 写作提示

> 生成时间：[日期]
> 负责团队：产品团队
> 选择篇幅：XXX-XXX字

## 1. 标书要求原文（必须覆盖的内容）

> 以下内容精确引用自标书，请逐条确认已在稿件中覆盖。

- 【第X.X条】"标书原文引用..."
- 【第X.X条】"标书原文引用..."
- ...

## 2. 合规红线（不可偏离，务必满足）

以下条款来自不可偏离项清单，**未响应将直接导致废标**：

- 【不可偏离-XXX】"条款内容..."
- ...

（如本章节无相关不可偏离项，注明"本章节无直接相关的不可偏离项"）

## 3. 建议内容框架

按以下结构组织内容：

1. [小节1标题] - [简要说明写什么、覆盖标书哪条要求]
2. [小节2标题] - [简要说明写什么、覆盖标书哪条要求]
3. [小节3标题] - [简要说明写什么、覆盖标书哪条要求]

## 4. 应标语言规范（必读）

产品团队撰写内容时，请遵守以下语言规范（方案组会据此润色，提前遵守可减少返工）

- **主语统一用"我方"**，禁止使用"本系统"/"本平台"/"我们"/"本公司"
- **每段开头**加响应性语句：针对贵方...要求，我方将...
- **每段结尾**回扣标书条款：上述方案满足招标文件第X.X条...的要求。
- **技术指标**必须与标书要求一致，不自行发明数字
- **禁止纯功能罗列**，每个功能点都要说明"解决甲方什么问题"

## 5. 示例段落（参考）

以下示例展示符合应标规范的写法，供参考模仿：

### 示例一：功能描述段落

针对贵方提出的[具体需求]，我方[产品/系统名称]提供[功能名称]，
具体而言，该功能通过[技术手段]实现[效果描述]，支持[具体能力1]、
[具体能力2]等核心特性，确保[业务价值]。
上述方案满足招标文件第X.X条关于[要求摘要]的规定。

### 示例二：技术指标段落

为满足招标文件第X.X条关于[性能要求]的规定，我方系统采用[技术方案]，
可实现[指标1]、[指标2]等关键性能指标。经我方在同类项目中的验证，
该方案可稳定达到贵方要求的[具体指标值]。
```

### Step 5：输出确认

```
=== 写作提示生成完成 ===
已写入：20_应标草稿/{章节编号}_写作提示.md

请将此文件发送给产品团队，提醒他们：
1. 逐条对照「标书要求原文」确认覆盖
2. 合规红线部分必须完整响应
3. 按「建议内容框架」组织内容结构
4. 参考「示例段落」的写法风格

产品团队完成初稿后，可使用 content-polisher 进行应标化润色。
```

## 语言规范

在生成写作提示前，查阅 `../_shared_references/应标语言规范.md`，确保示例段落和写作指导符合：
- 主语规范（禁止"本公司"，使用"我方"）
- 三段式段落结构（响应性开头 + 方案描述 + 回扣标书）
- ▲不可偏离项响应格式

---

## 注意事项

- 标书原文引用必须精确，不可凭记忆概括或改写
- 建议篇幅根据标书对该章节的要求深度和评分权重估算
- 如标书中对该章节有明确的格式要求（如表格、清单），需在写作提示中注明
- 写作提示是给产品团队看的，语言要通俗易懂，避免过多投标专业术语

---

## 重复执行行为

本 Skill 可随时单独触发，为任一章节重新生成或更新写作提示。

执行前检测目标章节的写作提示文件是否已存在：

```
=== 检测到已有写作提示 ===

  20_应标草稿/{章节编号}_写作提示.md（生成时间：YYYY-MM-DD）

  A. 保留已有写作提示，直接退出
  B. 重新生成，覆盖旧文件（适用：标书要求有更新，或需调整示例段落）
```

重新生成不影响任何其他文件，操作安全无后顾之忧。
