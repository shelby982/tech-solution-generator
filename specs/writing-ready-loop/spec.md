# SPEC：写作三件事：就绪度可见、要求按节映射、写后证据结果卡

- slug：writing-ready-loop
- 日期：2026-11-05
- 状态：待评审（人审后改为「已批准」）

## 1. 背景与问题

近期已经补了素材证据供应链与写作 readiness，但用户实际仍要“点了才知道”：

1. 就绪度只在点击写作时查询，章头/大纲/节列表看不到；
2. `requirement_ids` 字段虽支持过滤，但生成大纲时没有真正产出映射，导致按节过滤是空的；
3. 写作完成后的 `used_evidence / coverage` 只出现在 toast，刷新即消失，无法核对。

本 spec 只做三件事，不扩展素材类型、检索源或全屏工作台。

## 2. 目标（可验证）

### G1：就绪度可见

- 章头可见本章就绪摘要：已就绪节数 / 未就绪节数 / 缺证据节数；
- 大纲/节列表每节可见状态：`可写 / 部分证据 / 缺证据 / 无大纲`；
- 无需先点击写作即可看到状态；
- 点击未就绪状态能定位到对应节/证据缺口；
- 状态数据来自统一 readiness API，不在前端各算一套。

### G2：要求按节映射真正生成

- 生成大纲时，把本章 requirements / spec clauses 的 ID 和摘要提供给模型；
- 大纲每节必须产出 `requirement_ids`（可为空数组，但不能缺字段）；
- 系统校验：
  - 每个 requirement 至少映射到一节，或明确标记“未分配/章节级”；
  - 不存在的 ID 被丢弃并记录；
  - 旧大纲无映射时回退章节级，并显式标记；
- `section_context` / `section_evidence_needs` 按映射过滤；
- 计划面板能看到“哪条要求分到哪节”。

### G3：写后证据结果卡

- 每次节级写作生成一条持久结果，包含：
  - `context_evidence`：进入写作上下文的证据；
  - `cited_evidence`：正文实际引用/来源（能解析多少算多少）；
  - `coverage_before` / `coverage_after`；
  - `generic` 标记；
  - 时间/模型。
- 结果必须可查询、刷新后仍存在，不依赖 toast；
- 正文/侧栏固定展示：
  - 使用证据 N 条 · 覆盖 X/Y；
  - 证据来源 chips；
  - 缺证据项；
  - “补证据 / 重写本节”动作。
- 无证据写作显示“未使用证据（概括写法）”，不能伪装成有依据。

## 3. 非目标

1. 不做上传→解析→候选闭环（后续）；
2. 不做推荐证据 need 匹配优化（后续）；
3. 不做完整素材抽屉/全屏工作台；
4. 不改生成模型；
5. 不做全量旧章节自动重写；
6. 不改评审/评分链路。

## 4. 约束与依赖

- FastAPI + aiosqlite + 原生 JS；
- 复用 `writing_readiness`、`section_context`、`section stream`；
- 新增持久化表必须 additive，旧数据可读；
- 大纲生成仍可失败回退到 fallback，但 fallback 也要带 requirement_ids 字段（可为空）；
- 旧计划无映射时不能假装节级。

## 6. 风险与待决问题

| 风险 | 影响 | 缓解 |
|---|---|---|
| 大纲模型不按要求输出 IDs | 映射为空 | 校验 + fallback 按关键词映射，最后标章节级 |
| 章节头 readiness 查询增加加载 | 页面变慢 | 与 studio 数据并行请求；缓存到一次刷新 |
| 结果卡数据量 | 表膨胀 | 只保留每节最近一次；旧记录可清理 |
| context/cited 口径混淆 | 用户误解 | 文案明确“进入上下文 / 正文引用” |
| 旧计划无映射 | 看起来没生效 | 显示“章节级要求”，给重新生成入口 |
