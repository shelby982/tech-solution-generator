# SPEC：编写就绪度：从素材缺口到可写/写后可核对的工作流

- slug：writing-readiness
- 日期：2026-11-05
- 状态：已批准（2026-11-05，人审通过）

## 1. 背景与问题

素材侧已经有了“需求动作 + 证据卡 + 覆盖”，但编写侧仍是另一条流程：

- 素材页显示 3 条证据需求、0% 覆盖；
- 点击「编写整章」直接报“还没有章节大纲”；
- 没有写前检查：0 证据也能点写作；
- 没有节级写作，只有整章批处理；
- 写作完成后只报覆盖，不告诉用户“这段用了哪几条证据”；
- 大纲/计划没有把 requirement 映射到节，所有节拿到同一批章级要求；
- 从需求“上传”后，用户还要自己去素材库找片段、勾选、绑定，pending need 容易丢。

核心判断：

> **素材模块已经能回答“缺什么”，但编写模块还没有回答“现在能不能写、写的时候用了什么、写完还缺什么”。**

本期只做“编写就绪度 + 节级写作 + 写后证据反馈”，不重写生成模型。

## 2. 目标（可验证）

### G1：写作前有就绪度，不再直接报错

- 新增写作就绪度查询：给定章节/节，返回：
  - 是否有大纲；
  - 本节证据需求数、已覆盖数、缺口数；
  - 状态：`no_outline` / `no_evidence` / `partial` / `ready`；
  - 阻塞原因与下一步动作。
- 章节没有大纲时，写作入口不直接报错，显示“先生成本章大纲”的 CTA。
- 界面按钮必须反映状态：
  - `no_outline`：先生成大纲；
  - `no_evidence`：补证据 / 按概括写法；
  - `partial`：用现有证据写 / 先补缺；
  - `ready`：写本节。
- 0 证据不允许静默写作；用户必须显式选择“按概括写法”。

### G2：支持节级写作

- 每一节有独立的“写本节”入口；
- 节级写作只生成该节，不覆盖其他节；
- 章级“编写整章”保留，但必须显示就绪度摘要（例如“3 节未就绪”）；
- 节级写作完成后，只更新该节并返回该节的证据使用/覆盖结果。

### G3：证据需求按节映射

- 计划大纲的 section 支持 `requirement_ids` / `evidence_need_ids`；
- 有映射时，本节只显示/使用自己的要求，不再把整章要求复制到每节；
- 没有映射时，回退到章节级，并明确标记“章节级要求”，不伪造节级映射；
- 写作 Prompt 只注入本节相关要求，避免重复与跑题。

### G4：写作结果可核对“用了哪些证据”

- 节级/章级写作完成后，返回：
  - `used_evidence`: 实际进入上下文的证据卡（来源/页码/要求 ID）；
  - `coverage_before` / `coverage_after`；
  - `missing`: 仍未覆盖的要求；
- 前端在生成结果下显示：
  - “本节使用证据 N 条 · 覆盖 X/Y”；
  - 证据来源 chips；
  - “补缺证据 / 重写本节”动作；
- 没有使用任何证据时，必须显示“本节未使用证据（概括写法）”，不能伪装成有依据。

### G5：从需求上传/选库后闭环

- 从某条需求点「上传」时，保留该 need 的 section/need_id；
- 上传后进入解析状态，解析完成时给出该 need 的最多 3 条候选片段；
- 用户确认后绑定到该 need（section + requirement_id），需求变为已覆盖；
- 从某条需求点「选库」时，素材库只展示/优先展示与该 need 相关的条目，应用时带 section + requirement_id；
- 不允许上传/选库完成后丢失 need 上下文，退回“绑到整章”。

### G6：空推荐状态可解释

- 没有候选时区分：
  - 没有上传/素材库为空；
  - 未配置联网检索；
  - 有素材但无匹配；
  - 已全部忽略；
- 每种状态给对应 CTA，不能只显示“还没有绑定证据”。

## 3. 非目标（明确不做）

1. 不重写正文生成模型或评审模型；
2. 不做素材 OCR、表格识别新能力；
3. 不做素材权限、有效期、审批流；
4. 不做跨项目复用；
5. 不做自动批量重写全部旧章节；
6. 不把右栏整体改造成全屏应用；先做节级工作流与抽屉；
7. 不新增外部检索 API。

## 4. 约束与依赖

- 技术：FastAPI + aiosqlite + 原生 JS；复用 `chapter_sse` / `chapter_studio` / 素材 API；
- 兼容：没有 `requirement_ids` 的旧计划继续可用，回退章节级；
- 既有：节级写作流 `GET /blocks/{id}/studio/section/stream` 已存在，复用；
- 数据：`chapter_material_chunks.requirement_id`、`evidence_need_actions` 已有；
- 写作仍允许“无证据概括写法”，但必须显式；
- 不破坏现有整章写作、保存、导出、引用链路。

## 6. 风险与待决问题

| 风险 | 影响 | 缓解 |
|---|---|---|
| readiness 阻塞正常写作 | 用户烦躁 | 默认允许“按概括写法”，但显式确认 |
| 节级写作与整章作业并发 | 正文冲突 | 节级写按节替换；整章运行中禁用节级写 |
| 旧大纲无 requirement_ids | 仍复制章级要求 | 标记“章节级”，引导重新生成大纲 |
| 上传后解析耗时 | 闭环断裂 | 解析状态可见；完成后再给候选，不假装即时 |
| 证据使用统计依赖 Prompt 注入 | 统计不准 | 从实际注入的 evidence cards 计数，不从正文猜测 |
| 节级写会绕过整章检查 | 质量不一致 | 节级写后仍跑覆盖/引用检查 |

### 待决问题

1. “按概括写法”是否需要记录到章节状态，便于评审识别？倾向记录 `evidence_mode=generic`。
2. 节级写作是否允许没有大纲时按标题临时写？首期不允许，必须先确认大纲。
3. 上传后的候选片段是自动绑定还是用户确认？首期必须用户确认。
