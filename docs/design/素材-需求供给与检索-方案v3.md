# 素材：从「缺口清单」到「证据供应链」（方案 v3）

> 用户反馈：
> 1）「素材」模块把两类东西混在一起——**编写后才需要补的素材**，和**前期外部素材/用户上传**。
> 2）真实关系是**嵌套**的：编写中要补的素材，要么来自公开市场挖掘，要么来自用户上传；不是并列关系。
> 3）「编写中需要补的内容」在「待办」里已经处理，再放「素材」下面很奇怪。
> 4）用户上传的素材要做**解析**；公开挖掘要建**检索机制**，按章节所需内容给出关键词/关键句；
>    检索结果不能直接放正文，要作为提示词/依据，再交给正文 Agent 整合；图片交给图片 Agent，表格交给表格 Agent。
>
> 本文给出素材模块的产品重构方案：**需求（待办）与供给（素材）分离；素材只做"库 + 解析 + 检索 + 证据 + 绑定"**。
>
> **已确认（2026-10-21）**：① 采用 **AI 检索**；② 本期**不扩展** Excel/PPT/独立图片上传格式；③ 官方来源按建议（自动进候选、片段勾选）；④ 公开图片/表格按建议（仅官方/可授权 + 用户确认 + 标来源）。

## 一、结论先行（6 条）

1. **拆成三层**：`需求 Need`（这一节要什么证据）→ `供给 Evidence`（上传/检索得到的可引用片段）→ `使用 Usage`（绑定到要求，进入编写）。
   **需求归待办，供给与使用归素材**，不再两边各挂一份缺口。
2. **素材模块只展示三类东西**：本章可用证据、项目素材库（上传解析）、公开来源（检索/采纳）。
   「素材缺口」不再作为素材页签里的并列清单，只保留一行**覆盖摘要**，点击跳待办。
3. **用户上传 = 解析流水线**：入库 → 识别/OCR/结构化 → 切片（段落/表格/图片，带页码）→ 质量检查 → 用户核对 → 自动建议绑定 → 可用。
   状态、进度、失败原因、重试、预览必须可见；一次上传，全项目复用。
4. **公开挖掘 = 需求驱动的检索流水线**：需求 → 检索计划（3–5 个关键词/关键句 + 来源范围）→ 检索/抓取/抽取/重排 → 证据卡 → 用户采纳 → 绑定需求。
   不再用"章节标题 + 一个词"盲搜。
5. **检索结果不是正文**：只作为**证据卡/提示词**交给正文 Agent，要求改写并标注来源；图片/表格分别交给图片/表格 Agent。
   检索原文整段照搬、图片直接外链、表格直接粘贴，都不允许。
6. **检索模型做成可插拔**：你说的「AAI」请确认是"某家检索 API"还是"BAAI 的检索模型"；
   推荐组合是 `LLM 检索计划 + 外部搜索 API + 内部素材库 hybrid 检索 + reranker`，不把检索模型和写作模型混为一谈。

## 二、现状：素材模块到底在做什么

### 2.1 页面结构（实测）

当前「素材」页签由两块拼成：

```
素材
├─ 素材缺口（来自计划 material_gaps）
│   ├ 公开资料可补 → [去检索]
│   └ 必须你上传   → [上传]
└─ 已关联素材与外部依据（折叠）
    ├ 外部依据（citations，已采纳/未采纳、片段、打开原文）
    └ 本章素材（上传文件、parse_status、标记核对、移除关联）
```

项目 29 实测：
- 4 份材料，`parse_status=done`；
- 2 条已采纳引用（项目级/章级），各选了 2 个片段；
- 本章 `material_gaps` 只有 1 条：`我方材料（数据/案例/业绩）`，`availability=upload`；
- 同一缺口在「待办」里也有一条「补 1 份我方材料」——**同一个需求出现两次**；
- 后端 `SERPER_API_KEY` 未配置，`search_configured()` 为 false，当前"去检索"只能扫官方入口，**不能真正全网检索**；
- `parse_status` 原样显示英文 `done`，没有解析进度、质量、失败原因、重试入口。

### 2.2 问题清单

| # | 问题 | 后果 |
|---|---|---|
| 1 | **需求与供给混排** | 「素材缺口」是需求，「已关联素材」是供给；用户以为缺口就是素材，关系理不清 |
| 2 | **与待办重复** | 同一缺口在待办、素材各有一套动作和状态，操作后不知道以哪边为准 |
| 3 | **"公开可补/必须上传"是需求的渠道分类，不是素材属性** | 它被画成素材分类，导致素材模块看起来像"缺口清单" |
| 4 | **缺口是硬编码的，不是从真实要求派生的** | `_materials_plan` 固定生成"政策原文 2 条、招标条款 N 条、我方材料 1 条"，和本章实际要求经常对不上 |
| 5 | **所有 requirement 都被算成素材需求** | 文本/表格/图示要求也带着 `material=待补`，完成检查报"5 条要求素材未满足"，噪声大 |
| 6 | **上传解析是黑盒** | 只有 `pending/parsing/done/failed` 原始状态；无进度、无质量、无预览、无失败原因、无重试 |
| 7 | **素材库不可见，按章上传重复** | 看不到项目里已有哪些材料、解析到哪、被哪些章用；同一份材料可能在多章重复上传 |
| 8 | **检索不可用/不可解释** | 无搜索 key 时仍显示"去检索"；查询词只有一个；没有关键句、来源范围、重排、命中需求 |
| 9 | **检索结果落不了地** | 接受的是"一条来源"，不是"满足某条需求的片段"；没有绑定、覆盖、使用位置 |
| 10 | **图片/表格没有链路** | 检索片段里的表和图没有抽取/入库/交给对应 Agent 的路径 |
| 11 | **没有证据级溯源** | 页码、机构、日期、trust、原文快照、引用位置，用户看不到完整链条 |
| 12 | **内部素材按需检索能力闲置** | `material-search` 接口已有（关键词检索 chunks），前端没用上 |

一句话：**素材模块现在是"缺口清单 + 素材附件"的混合体；它应该变成"证据供应链"。**

## 三、目标概念模型

```
编写要求 Requirement（计划里，逐条）
   └─ 证据需求 Need（这条要求需要什么证据；没有证据需求的要求不生成 Need）
        ├─ 供给通道 A：公开检索（系统）──┐
        └─ 供给通道 B：用户上传（用户）──┤
                                          ↓
                                   Evidence 证据（最小可引用单元）
                                   · 段落：quote + 页码/URL + 标题 + 机构 + 日期
                                   · 表格：结构化行列 + 表名 + 来源
                                   · 图片：图片文件 + OCR 文本 + 图注 + 来源
                                          ↓
                                   绑定 Need（覆盖/未覆盖）
                                          ↓
                              正文/图片/表格 Agent 使用（带引用，不照搬）
```

**三条边界：**

- **Need 只在待办出现**：待办回答"还缺什么、谁去补、怎么补"。
- **素材只出现 Evidence 和素材库**：回答"已经有什么、从哪来、能不能用、用在哪"。
- **Usage 连接两边**：绑定关系让"待办补完"和"素材可用"是同一件事，不重复维护。

把用户原来看到的两类东西放回各自层：

| 用户看到的两类 | 实际属于 | 应该在哪 |
|---|---|---|
| 前期外部素材、用户上传 | **Supply / 库存**（项目素材库 + 公开来源） | 素材 → 素材库 / 公开来源 |
| 编写中需要补的素材 | **Need / 需求单**（由本章要求派生） | 待办 → 补素材动作 |

它们不是"两类素材"，而是**库存**与**需求单**：需求单指向库存；库存补充后回填需求单的状态。

## 四、素材模块的新信息架构

### 4.1 页签结构

```
素材
├─ 本章证据（默认）
│   ├ 覆盖摘要：3 条证据需求已覆盖 2 条 · 还缺 1 条 → 去待办
│   ├ 上传素材证据（文件 · 页码 · 已核对 · 被哪节引用）
│   └ 公开来源证据（机构 · 日期 · 官方/待确认 · 被哪节引用）
├─ 素材库（项目级）
│   ├ 全部上传（解析状态/质量/页数/切片/使用章节）
│   ├ 待核对 / 解析失败
│   └ [上传素材] [从素材库绑定本章]
└─ 公开来源
    ├ 已采纳来源（片段、trust、引用位置）
    ├ 检索历史
    └ [按本章需求检索]
```

- **不再出现「素材缺口」动作列表**；只保留覆盖摘要 + "去待办"链接。
- 「上传素材」「按需求检索」保留，但它们是**供给动作**，不是"补缺口"的替代品。
- 待办里点「上传/检索」→ 打开**补素材抽屉**，上下文就是那条 Need；完成后回到待办复检。

### 4.2 补素材抽屉（从待办进入）

```
┌ 补素材：我方材料（数据/案例/业绩） ──────────────── × ┐
│ 用于：项目背景现状目标 › 现状分析（第 2 段、第 4 段）    │
│ 要求：提供现状业务量/佐证；公开渠道没有这类材料          │
│                                                        │
│ [上传文件]  [从素材库选]  [试试公开检索]                 │
│                                                        │
│ 支持：PDF / Word / Excel / 图片（扫描件走 OCR）          │
│ 上传后自动解析；解析完成需你核对一遍                     │
└────────────────────────────────────────────────────────┘
```

- 同一份材料跨多章：上传一次，抽屉里列出"将同时覆盖 96 章同类需求"，可取消勾选。
- 关闭抽屉时如果没完成，回到待办仍显示"待补"，不假消失。

### 4.3 素材库（项目级）

```
素材库
[全部 12] [待核对 2] [解析失败 1] [未使用 4]
┌──────────────────────────────────────────────────────┐
│ 业绩证明_2024.docx                                   │
│ 已解析 · 12 页 · 8 段 · 2 表 · 质量：良 · 已核对       │
│ 用于 3 章 · 2 处未引用        [预览] [绑定章节] [重解析] │
├──────────────────────────────────────────────────────┤
│ 资质证书扫描件.pdf                                    │
│ 待核对 · 3 页 · OCR 置信度中 · 2 张图片               │
│ [预览识别结果] [重新识别] [标记可用]                   │
└──────────────────────────────────────────────────────┘
```

- 状态中文化：`已上传 / 解析中 40% / 待核对 / 可用 / 解析失败`。
- 质量：页数、切片数、表格数、图片数、OCR 是否使用、空页/乱码提示。
- 操作：预览、绑定/解绑章节、重新解析、替换版本、删除。
- 上传即入项目库；章节只是"绑定"，不复制文件。

### 4.4 公开来源

```
公开来源
[按本章需求检索]
已采纳 2：
  [官方] 中共中央 国务院关于发展新质生产力的意见 · gov.cn · 2025-xx
  片段 2（已选 2）· 用于 项目背景现状目标 · [查看] [移除]
检索历史：...
```

- 每条来源显示 trust、机构、日期、命中需求、选中片段、使用章节。
- 未采纳候选不长期堆在页签里，进检索抽屉处理。

### 4.5 与其他模块的分工

| 模块 | 负责 | 不负责 |
|---|---|---|
| 待办 | 需求缺口、谁去补、动作与复检 | 素材内容管理、解析 |
| 素材 | 素材库、解析、检索、证据、绑定、覆盖 | 决定"这一章还缺什么"（那是待办） |
| 进度 | 编写进度/篇幅 | 素材 |
| 评审 | 质量意见 | 素材补充 |

## 五、用户上传：解析流水线

### 5.1 状态机

```
上传 → 识别（类型/角色）→ 解析中（页/进度）→ 待核对 → 可用 → 已绑定 → 已使用
                          └→ 解析失败（原因 + 重试）
```

- 解析自动开始，用户不需要点"解析"；只做"核对/重试/替换"。
- 解析不阻塞上传：上传后立刻出现在素材库，状态"解析中"。
- 解析完成不等于可用：必须核对（干净文本 PDF 可自动核对，扫描件/OCR 需人工确认）。

### 5.2 解析要产出什么（不只是纯文本）

| 产物 | 用途 |
|---|---|
| 结构化段落/章节 + 页码 | 正文引用时可定位"第 12 页第 2 段" |
| 表格（行列 + 表名 + 页码） | 表格 Agent 直接使用；不重新编数字 |
| 图片（原图 + OCR 文本 + 图注） | 图片 Agent 作为素材图插入；不生成假图 |
| 文档元信息（标题/机构/日期/文号） | 引用来源、判断时效 |
| 质量信息（空页/OCR 置信度/乱码） | 提示"这份扫描件识别质量差，建议重传" |
| 角色/类型（业绩/资质/合同/数据/截图） | 自动建议绑定到哪类需求 |

### 5.3 解析能力与格式

- **本期范围（已确认）**：保持现有 `PDF / DOC / DOCX`，扫描件/文档内图片走 OCR；**不扩展** Excel / PPT / 独立图片上传。
- 表格仍可从已有 docx/pdf 中按需抽取（现有能力），不作为独立上传格式。
- 对扫描件：OCR + 原图入证据；证书/截图类可只作为图片证据，不强行转文字。
- 对表格：解析成结构化行列，保留表头/合并单元格；表格 Agent 用结构化数据，不用 OCR 文本。
- 对加密/超大/空文件：明确失败原因，给"换文件/解锁后重传"；后续再评估格式扩展。

### 5.4 核对与绑定

- 解析完成展示：前 3 段/前 2 页预览 + 抽取的表格/图片缩略图 + 质量提示。
- 用户点"确认可用"后，才进入编写可用的证据池。
- 系统按需求关键词/向量给出"可能用于：需求 1、需求 2"，用户确认绑定；不自动绑死。
- 一份材料可绑多章；一个需求可绑多份证据；绑定关系决定覆盖状态。

### 5.5 去重与版本

- 文件 hash 去重：重复上传提示"项目里已有，是否直接绑定本章"。
- 同名替换：保留旧版本，新版本解析完成后切换；旧绑定标记"待复核"。
- 同一材料的多章绑定共享同一份解析结果，不重复解析。
- 删除材料前提示影响章节；软删除保留引用记录。

### 5.6 UI 文案（替代原始状态）

| 现在 | 改为 |
|---|---|
| `pending` | 等待解析 |
| `parsing` | 解析中 · 第 3/12 页 |
| `done` | 待核对 / 可用（看是否核对） |
| `failed` | 解析失败：扫描件模糊 / 加密 / 格式不支持 [重试] |

## 六、公开挖掘：检索流水线

### 6.1 第一步：需求 → 检索计划

不要用一个章节标题拼一个词去搜。每条 Need 生成一个**检索计划**：

```jsonc
{
  "need": "缺少 2027 年前央企系统安可替代要求原文",
  "intent": "policy_clause",
  "queries": [
    {"q": "2027年 央企 信息系统 安可替代 要求 文件", "source": "official", "why": "找政策原文"},
    {"q": "南方电网 数据库 信创 替代 时间表 2027", "source": "official", "why": "找网公司要求"},
    {"q": "分布式数据库 国产化 迁移 验收 标准", "source": "standard", "why": "找技术依据"}
  ],
  "key_phrases": ["2027年", "安可替代", "分布式数据库", "信创"],
  "must_include": ["南方电网"],
  "exclude": ["2023年旧版", "厂商软文"],
  "source_scope": ["gov.cn", "csg.cn", "国家标准全文公开系统"],
  "date_range": "2024-2026"
}
```

- **关键词/关键句**由 LLM + 模板生成：需求原文、章节要点、项目/行业术语、时间/地域/文号。
- 用户可**编辑、增删、换来源范围**，不要盲搜；默认 3 条，最多 5 条。
- 每条 query 标注"找什么"（政策/标准/数据/案例），方便判断搜不到时换路径。
- 检索计划落库，后续可复用、可审计。

### 6.2 第二步：检索（Provider 抽象）

```
SearchProvider
  ├─ 外部 Web：AAI / Serper / Tavily / Exa / Bing / 官方站点搜索
  ├─ 官方入口扫描：gov.cn / 标准平台 / 行业主管部门
  └─ 内部素材库：hybrid（关键词 + 向量）+ reranker
```

- **没有配置检索源就明确说"检索未配置"**，给"粘贴官方链接"的兜底，不假装搜过。
- 当前代码只有 Serper 适配，且环境没配 `SERPER_API_KEY`；`search_configured=false` 时只能扫官方入口。
- 检索结果统一成：`title/url/domain/publisher/published_at/snippet/trust/source`。
- 去重：URL、规范化标题、正文 hash；同一篇多路径只留一条。
- 官方域白名单 + 日期/地域过滤；聚合站、SEO 软文降权或排除。
- 缓存：query + 结果 + 抓取快照，重复需求不再重复烧检索额度。

### 6.3 第三步：抓取、抽取、重排

1. **抓取**：HTML/PDF；超时/反爬/登录墙给失败原因；保存快照 hash。
2. **抽取**：正文段落 + 标题层级 + 表格 + 图片；保留页码/URL/发布时间。
3. **重排**：相关度（命中需求/关键句）+ 权威度（官方 > 行业 > 未验证）+ 时效 + 覆盖度 + 多样性。
4. **证据卡**：不是整页结果，而是 2–3 句可引用片段 + 来源 + 命中需求 + trust。

```
[官方] 南方电网《…》（2025-03）
“到2027年，…完成…替代。”
命中：2027 安可替代要求
[打开原文] [采用为证据] [不相关]
```

### 6.4 采纳与绑定

- 用户勾选具体片段（不是整页），可一次选多段。
- 选择"满足哪条需求"（默认按命中预选），保存 `Evidence`。
- **官方来源（已确认）**：官方原文自动进入候选列表，**片段仍由用户勾选**；非官方必须确认"内容真实"并标"已确认"后才能采用。
- 图片片段：预览 → "作为图片证据"（下载入库，正文用本地路径，不放外链）；**只允许官方/可授权来源**，用户确认后使用，正文标来源。
- 表格片段：预览/纠正表头 → "作为表格证据"（结构化入库）；同样只允许官方/可授权来源，用户确认后使用。
- 失败/不相关：记录原因，不再重复推荐。

### 6.5 进入写作（关键：检索内容不是正文）

Evidence 进入编写提示词时，按类型分派：

| 证据类型 | 交给谁 | 怎么用 |
|---|---|---|
| 段落/事实/政策条款 | 正文 Agent | 作为依据；改写并保留【来源】；不得整段照抄 |
| 真实图片（证书/截图/现场） | 图片 Agent | 作为素材图插入（`:::figure`），带图注+来源；**不生成假图** |
| 结构/流程/数据关系 | 图片 Agent | 作为图示依据，生成 `:::diagram`，节点 ref 指向证据 |
| 表格 | 表格 Agent | 用结构化行列/数字，带表名+来源；不新造数字 |
| 背景资料（不可引用） | 不进入提示词 | 只用于理解，标"仅背景" |

写作提示词增加：

```
以下是已采纳的证据（只可使用这些事实）：
[E1] 来源：…；日期：…；片段：…
要求：用自己的话改写；每个事实后标注【来源：…】；禁止整段复制；
数字/标准号必须与证据一致；证据没有的不得补。
```

写后校验（与 v3 文案校验合并）：

- 正文引用的来源是否在 evidence 列表；
- 连续 30 字以上与原文重合 → 标"疑似照搬"；
- 数字/日期/文号与 evidence 不一致 → `proof`；
- 该用证据的段落没有引用 → `proof`；
- 图片是否来自素材而非凭空生成；表格数字是否有来源。

### 6.6 检索模型选型（已确认：AI 检索）

本期按 **AI 检索**落地，不等同于"关键词搜索 + 官方门户扫描"：

```
LLM 检索计划（3–5 query + 关键句 + 来源范围）
      ↓
AI 搜索 API（可插拔：Tavily / Exa / Serper / 其他 AI 检索服务）
      ↓
抓取 → 正文/表格/图片抽取 → 相关性 + 权威性重排
      ↓
证据卡（片段 + 来源 + 命中需求）→ 用户采纳 → 绑定需求
```

- **Provider 抽象**：`SearchProvider.search(query, scope) -> candidates`；不同服务只换适配器，检索计划/证据卡/绑定逻辑不变。
- **AI 检索的职责**：理解需求、给候选、覆盖官方/行业/标准等来源；**抽取、重排、证据化、引用校验仍由系统做**，不把整页结果直接塞给写作模型。
- **内部素材库**（用户上传的几十份文件）先用现有关键词/BM25 检索；后续可加 BGE-M3 hybrid + reranker 做语义召回（P1，不是本期前置）。
- **没有 API key 时**：明确显示"AI 检索未配置"，提供粘贴官方链接/上传材料兜底；不假装搜索。
- 搜索 provider 的 key/额度在配置页管理；每次检索记录 query、结果数、耗时、token/额度消耗。

> 实施前需要你提供一项配置：**用哪家 AI 检索 API（Tavily / Exa / Serper / 其他）及其 key**；没有偏好时，我先做 provider 适配层 + 官方门户兜底，接入 key 后即可切换。

## 八、数据与接口改造

### 8.1 数据模型

复用：`materials`、`material_chunks`、`chapter_materials`、`citations`、`citation_links`、`need_snippets`。

新增/扩展：

```sql
-- 证据需求（由 requirement 派生；只在待办消费）
CREATE TABLE material_needs (
  id TEXT PRIMARY KEY, project_id INTEGER, thread_id TEXT, block_id TEXT,
  section TEXT, requirement_id TEXT, kind TEXT, purpose TEXT,
  status TEXT DEFAULT 'open',          -- open | covered | waived
  created_at TEXT DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(block_id, requirement_id, kind)
);

-- 证据（上传片段/公开片段统一）
CREATE TABLE evidence (
  id TEXT PRIMARY KEY, project_id INTEGER, block_id TEXT, need_id TEXT,
  source_type TEXT,                    -- upload | web
  material_id INTEGER, citation_id TEXT,
  segment_index INTEGER,
  kind TEXT,                           -- text | table | image
  quote TEXT, summary TEXT,
  locator TEXT,                        -- {page, section, url, published_at}
  trust TEXT, verified INTEGER,
  hash TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);

-- 检索计划/候选（可审计、可复用）
CREATE TABLE search_plans (
  id TEXT PRIMARY KEY, need_id TEXT, queries TEXT, key_phrases TEXT,
  source_scope TEXT, status TEXT, created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
CREATE TABLE search_candidates (
  id TEXT PRIMARY KEY, plan_id TEXT, url TEXT, title TEXT, publisher TEXT,
  published_at TEXT, snippet TEXT, trust TEXT, score REAL,
  fetched INTEGER DEFAULT 0, hash TEXT
);
```

`materials` 扩展：`parse_progress`、`pages`、`chunk_count`、`table_count`、`image_count`、`ocr_used`、`quality`、`parse_error`、`hash`、`version`。
`requirements` 扩展：`evidence_kind` / `needs[]`（只有真正需要证据的要求才生成 need；文本要求不再默认 `material=待补`）。

### 8.2 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/projects/{pid}/materials` | 项目素材库（状态/质量/使用） |
| POST | `/api/projects/{pid}/materials` | 上传（项目库；可带 block_id 绑定） |
| GET | `/api/materials/{id}/parse` | 解析状态/进度/质量；SSE 可选 |
| POST | `/api/materials/{id}/reparse` | 重新解析 |
| POST | `/api/materials/{id}/confirm` | 核对可用 |
| GET | `/api/blocks/{bid}/needs` | 本章需求覆盖（只读摘要） |
| POST | `/api/blocks/{bid}/needs/{need_id}/plan` | 生成检索计划 |
| POST | `/api/blocks/{bid}/needs/{need_id}/search` | 执行检索 |
| POST | `/api/evidence` | 采纳片段/证据 |
| POST | `/api/evidence/{id}/bind` | 绑定需求 |
| GET | `/api/blocks/{bid}/evidence` | 本章证据列表 |
| GET | `/api/projects/{pid}/citations` | 已采纳来源（复用） |

- 检索未配置时：`POST /search` 返回 `{configured:false, message, fallback:"paste_url"}`；前端显示"检索未配置"，给粘贴链接。
- 解析进度最好用 SSE/轮询，状态落库（当前 `parse_job_store` 在内存，重启丢失）。

### 8.3 生成规则

- **只有带 `evidence_kind` 的 requirement 生成 need**；文本/表格/图示要求不再一律标"素材待补"。
- `_materials_plan` 不再硬编码"政策 2 / 条款 N / 我方材料 1"；改为读 needs 聚合。
- 素材覆盖 = `need.status=covered` 的比例；完成检查只算 open needs，不再把已覆盖/不需要证据的要求算进去。
- 旧计划兼容：没有 `evidence_kind` 的要求按"无证据需求"处理，不阻塞；后续编辑计划时补。

## 九、分期与验收

### P0（先解决"关系乱 + 上传黑盒 + 检索假可用"）

1. 需求/供给分离：素材页签去掉缺口动作列表，改覆盖摘要 + 去待办；待办补素材打开同一抽屉。
2. needs 从 requirement 派生，停用硬编码 `_materials_plan`；完成检查只算真实 needs。
3. 上传解析 UX：状态中文化/进度/质量/失败原因/重试/预览/核对；项目素材库列表。
4. 检索：检索计划（3–5 query + 关键句 + 来源范围）+ provider 抽象 + 无 key 明确提示 + 证据卡采纳/绑定。
5. 文本证据进入正文 Agent；写后引用/长段照搬校验。

### P1

1. 图片/表格证据链路：OCR/表格抽取 → 图片 Agent/表格 Agent。
2. 内部素材库 hybrid（BGE-M3/reranker）+ 外部多 provider + 重排。
3. 自动绑定建议、去重/版本、跨章批量上传。
4. 覆盖/溯源 UI：每条 need 显示证据来源/页码/使用位置。

### P2

1. 待办系统任务自动检索、失败转用户。
2. 来源订阅/监控（政策更新）、检索质量评估。
3. 证据使用分析（哪些来源被引用/被评委关注）。

### 验收（用项目 29 可测）

1. 素材页签不再有「素材缺口」动作列表；只有覆盖摘要 + "去待办"。
2. 待办「补我方材料」→ 补素材抽屉 → 上传 → 解析中→待核对→可用 → 绑定 → 待办复检消失；素材覆盖从 0/1 变 1/1。
3. 上传状态全中文，失败有原因/重试；解析完成能预览段落/表格/图片和页码。
4. 同一文件重复上传提示"已在项目库"；一份材料绑定多章不重复解析。
5. 缺「2027 安可替代原文」：检索计划至少 3 条 query + 关键句；无 key 时明确提示；有 key 时出证据卡；采纳→绑定→编写引用。
6. 检索片段不直接进正文；正文有【来源】；连续 30 字以上照搬被标出。
7. 图片证据插入为素材图（不放外链）；表格证据用结构化数据、不编数字。
8. 需求覆盖只算真实证据需求；文本/表格/图示要求不再误报"素材未满足"。
9. 现有 4 份材料/2 条引用迁移后状态正确；旧计划不炸。
10. 无控制台错误；检索/解析失败不静默。

## 十一、一句话总结

**素材不是"缺口的另一个列表"，而是"证据供应链"：**
需求在待办，供给在素材；上传要解析成带页码的证据，公开挖掘要按需求生成检索计划并抽出证据；
检索结果只做提示词，正文/图片/表格 Agent 各自整合并标注来源。
这样用户看到的素材模块只有三件事：**我有什么、从哪来、用在哪。**
