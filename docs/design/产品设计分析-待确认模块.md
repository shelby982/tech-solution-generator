# 产品设计分析：「待确认」模块该确认什么

> 依据：`/api/projects/26/split-report` 的 8 项 `confirmations` + 面板 ② 的实际渲染 + 代码里已具备的能力。
> 结论先行：**当前 ② 让用户确认的 8 项里，只有 2 项是真正的用户决策；而你说是关键的那两件事
> （目录结构完整性/可调整、技术规范书内容如何结合）在 ② 里恰恰没有呈现。**

---

## 一、现在 ② 待确认 让用户确认什么

| # | 项 | 系统给的"答案" | **该谁来回答** | 判定 |
|---|---|---|---|---|
| 1 | 按哪个标包/标的拆分？ | 编号：2 | 用户 | **决策**（但已在面板顶部「筛选·标包 → 确认标包」做过 → **重复**） |
| 2 | 评分类别识别是否正确？ | tech 8 条 | 用户 | **决策**（但已在 ② 的「要生成哪些类别」勾选框做过 → **重复**） |
| 3 | 评分点分值合计 100 分是否与招标文件一致？ | 8 个评分点，合计 100 分 | **系统** | **自检**（用户无法核对全部评分表；异常时才需人工介入） |
| 4 | 评分点清单是否正确、是否都已纳入拆解？ | 8 个评分点，合计 100 分 | 用户 | **决策**（属于第①步「评分点」，应留在①确认，不应在②再问一遍） |
| 5 | 规范书要求主题该挂到哪些章节？ | 19 个主题、153 条要求 | 用户 | **决策 ✅ 真问题**（技术规范书如何结合目录） |
| 6 | 标星项（★/▲）是否都已进入目录？ | 目录中带标星 0 个 | **系统** | **自检** |
| 7 | 目录结构（大评分点→详细评审项→子检查项）是否合理？ | 8 个评分单元、37 个详细评审项、76 个子检查项 / 结构完整 | 用户 | **决策 ✅ 最关键**（但只给了计数，没给可操作的目录） |
| 8 | 是否只按选中的这张评分表拆分？ | 选中「标的1标包2」，另 2 张未选中 | 用户/系统 | **决策**，但已在第 1 项范围内确定 → **重复** |

**统计**：8 项里 = 决策 2 项（#5 #7） + 重复决策 3 项（#1 #2 #8） + 自检 3 项（#3 #6 + #4 的一半）。

### 这带来三个具体问题
1. **用户被要求"确认"他判断不了的东西**：#3 分值合计、#6 标星覆盖率 —— 用户没有对照物，
   只能盲点「确认」。**让人对自己无法判断的事负责，就是在教他忽略这个界面。**
2. **同一件事问两遍**：#1 与顶部标包确认、#2 与类别勾选、#4 与第①步评分点确认。
   重复会让用户怀疑"我前面那次确认算不算数"。
3. **真正该决策的没有可操作界面**：#7 只给了"8 个评分单元、37 项、76 子检查项 / 结构完整"
   这样的**计数**，没有目录本身；#5 只有下拉选归属，看不到"结合之后目录长什么样"。

## 二、一个更要紧的发现（能力有，入口没了）

「目录结构是否合理、是否需要调整」——**这个能力早就实现了**：

```
mode-outline.js: function structureEditable() { … }
  · 增删章节 / 改标题 / 上下移动 / 缩进（纯逻辑在 workspace-model.mjs，有 node --test 覆盖）
  · UI 挂在**下面的目录树**上（.structure-editable + 行内「编辑」按钮）
  · 仅在 extractionState === 'gate_outline' 或 'done' 时可编辑
```

而我前几轮为了让面板成为唯一内容面，加了 `hideLaneTreeWhenPanelShows()` ——
**面板一打开就把那棵树隐藏了**。于是：

> **用户说是关键的能力（调整目录结构），在现在的面板形态下没有入口。**

（对比：② 的 #7 还在问"结构是否合理"，但用户既看不到结构，也无从调整。）

---

## 三、设计原则（建议以此为判定标准）

**待确认 = 只有满足下面三条的项才该出现**
1. **是用户的决策**（系统无法替他决定）；
2. **决定会影响产物**（不是给用户汇报"我干了什么"）；
3. **界面上有可操作的载体**（能给选项/能编辑，而不是让他在一句陈述后面点"知道了"）。

不满足的项 → 归为**检查结果（自检）**：以一行摘要展示，**只有异常时才升级为待确认**
（例如"分值合计 90 ≠ 100" → 提示"可能有评分点没解析出来"并给"重新拆分"入口）。

## 四、建议的新 ②「目录确认」（单一决策面）

把 ② 从"8 项确认清单"改成**一屏目录确认**，用户在这里只做两件事：

```
┌ ② 目录确认 ───────────────────────────────────────────────────────────────┐
│ 自检：✅ 分值合计 100/100  ✅ 结构完整（8 评分单元 / 37 详细项 / 76 子检查项）      │
│       ✅ 标星项已入目录 0 个   ⚠ 6 个评分点名下没有挂到要求  ← 异常项才需要处理      │
├──────────────────────────────────────────────────────────────────────────┤
│ 目录结构（可直接改：改名 / 增删 / 上下移 / 缩进）              [编辑模式 ▾]        │
│  ▸ 技术方案可行性        12 分   ← 评分点：技术方案可行性                        │
│      · 技术方案完整性            ← 挂载：技术规范书 3 条                         │
│      · 技术方案可行性            ← 挂载：技术规范书 4 条（含 2 条必须响应）        │
│  ▸ 财务状况 · 营业净利率   10 分  ← 评分点：财务状况/营业净利率                   │
│      · 证明材料与数据来源         ← 挂载：技术规范书 0 条（本章→ 需举证 2 项）      │
│  ▸ 未归属主题（6 个）：安全与保障体系研究及验证、埋点与低延迟…  [指到某章 ▾]        │
├──────────────────────────────────────────────────────────────────────────┤
│ [确认目录，生成产物]        ← 唯一的确认动作                                    │
└──────────────────────────────────────────────────────────────────────────┘
```

### 具体怎么落
| 现在 | 改成 |
|---|---|
| 8 项确认清单（含 3 项自检、3 项重复） | 顶部**一行自检摘要**（异常项才展开处理） |
| #7「结构是否合理」只给计数 | **目录本身**直接呈现在 ② 里，并**复用已实现的结构编辑**（改名/增删/上下移/缩进） |
| #5 主题归属只有下拉 | 归属**内联进目录**：每章显示"挂载的规范书要求条数/主题"，主题可就地改挂到别的章 |
| #1/#2/#8 已在上方或第①步确认过 | **只读回显**（"范围：标的1/标包2 · 类别：技术"），不再重复确认 |
| 结构编辑只能在下方的目录树里（且被面板隐藏） | 把 `.structure-editable` 的能力**搬进 ② 的目录视图**，去掉对下方树的依赖 |

### 与③产物的关系
- ② 确认 → 生成产物（目录 + 映射矩阵）→ ③ 只读查看 + 覆盖率。
- 「技术规范书内容结合进来后怎么改目录」的**改动入口在 ②**；③ 是结果视图（可回②再改）。

## 五、落地顺序（建议）

| 阶段 | 内容 | 收益 |
|---|---|---|
| **P0** | 自检项从"待确认"降级为**一行检查摘要**；去掉 #1/#2/#8 三处重复确认；#4 归回第①步 | 立刻去掉 5/8 的噪声，决策面变清晰 |
| **P1** | ② 主区换成**目录树 + 结构编辑**（复用 `structureEditable` 那套），并显示每章挂载的规范书要求 | 用户能真正判断"结构是否完整、要不要调整" |
| **P2** | 主题归属内联进目录（就地改挂）+ 未归属主题的显式分区（"技术规范书要求应答"章节） | 技术规范书与目录的结合变得可见、可改 |

## 六、一句话总结

> 现在 ② 是**"系统向用户汇报自己的 8 项工作，并请用户逐个点确认"**；
> 它应该是**"用户在一屏里审目录结构（可改），并看清技术规范书要求分别落到哪一章，然后确认生成"**。
> 前者把责任推给无法判断的用户，后者才是产品该承担的判断。

## 八、实施记录（两步版）+ 一次数据事故的完整复盘

### 已落地
② 待确认 = **两步**（左两步 + 右内容），确认动作只在最后一步：
1. **目录确认与调整**：自检摘要一行 + 已确认项回显 + **目录结构（121 章，只读展示）** +「调整结构（在下方目录树里改）」
2. **技术规范书确认**：19 个主题 → 归属章节下拉 + 状态 + 保存/全部保持默认
- footer：上一步 / 下一步；第②步才出现「确认目录，生成产物」

实测：`subItems=2`、结构 121 行且 `data-struct=s1`（正确 id）、第②步 19 行主题、`boot=[]` ✅

### ⚠️ 事故：面板内的结构写入破坏了项目 26 的目录（已恢复）
**原因**：面板里的结构行用的是 `b.id`（数据库行 id，如 `36873`），而目录结构接口按
**`block_id`（逻辑 id，如 `s1.1`）** 匹配已有行。发错 id → 服务端把 121 个节点当**新节点**：
一条 HTTP **200** 的请求实际做了 `created:121, updated:10, removed:116, kept:5`，
并且把请求里的 id 回写进了检查点的 `spec.toc`（第二重污染）。

**为什么没能及时发现**：接口对未知 id **不报错**、返回 200 + 统计（`created/removed` 数字很大
却没被前端展示），所以"保存成功"的假象掩盖了结构被重建。

**恢复过程**（全部有据可查）
1. 从 `blocks` 表确认：合法行是 `s1/s1.1/…`（8 条含正文，其余空）→ 我误建 131 条数字 id 空行；
2. **删掉 131 条误建行**（先核对"其中有正文 0 条"才动手）；
3. 从**检查点历史**（`ge_solution.db` 的 `checkpoints` 表，msgpack）找到 step=21 那一版
   `spec.toc`（**121 项、`s1` 系列**），用它 `sync_outline_placeholders` 重建结构；
4. 正文在 `block_revisions` 里（6 条），按"数字 id → 标题 → 逻辑 id"映射写回；
5. 修补检查点 `spec.toc`（121 项、`s1` 系列），避免将来任何一次同步又建出数字 id 的行。

**最终状态**：`blocks=121`、**5 章正文全部回来**（1848 / 1747 / 2143 / 2769 / 2250 字，
与事故前一致）、`status=done=5` ✅

### 因此做出的取舍（先不伤害）
面板内的结构**写**入口**暂停接线**（`handleStructAct` / `handleStructNew` 代码保留）：
id 已修正，但在废弃项目上验证"响应 `created:0` 且库行数不变"之前，不再开放写入。
结构展示只读 + 走**已验证可用**的目录树编辑（`.structure-editable` + 行内 `.ot-actions`）。

### 给产品的建议（这次的根因值得改接口）
`POST /outline-structure` 收到**未知 block_id** 时应 **400 拒绝**（而不是当新节点创建），
并在响应里把 `created/removed` 数量交给前端展示 —— 一次误发就毁掉一份目录，
这类破坏性语义不该用 200 + 静默统计表达。

## 九、目录调整支持批量操作

用户要求：「这里加一个批量操作的功能，可以批量地上移、下移，批量地缩进、减少缩进」。

### 交互
```
目录结构（121 章）· 点一行即可改
[已选 3 项] [批量上移] [批量下移] [批量缩进] [减少缩进] [清空选择]     ← 勾选后出现
☐ 技术条款差异性
  ☑ 优于招标技术要求的条款
  ☑ 非实质性负偏差
  ☑ 未作响应情况
```
- 每行一个复选框（勾选不算"选行"，所以不影响单行操作）
- 未勾选时操作条**不占位**；选择跨渲染保留（方便连着挪几格）

### 语义（这里有个坑，第一版写错了）
**不能"逐个调用单节点函数"**：`[s1,s2,s3]` 全选缩进时，s2 降成 s1 的子级后，
s3 的"同级前驱"变成了 level 2 → 单节点函数拒绝 → 用户看到只降了一个。
正确语义：**以这一批的"头"决定，整批一起升降**；头没有同级前驱（或已是 4 级）→ 整批不动。

- 上移：从**最上面**的开始；下移：从**最下面**的开始（否则同批互相插队）
- 缩进/减少缩进：整批一起（`_batchShiftLevel`，父子同时选中不会位移两次）
- 动不了的项**计入 skipped 并如实显示**：「批量下移 3 项（2 项动不了）」

### 实测（真机）
```
勾选 3 行 → 操作条出现「已选 3 项」
批量下移 → 这 3 章作为一组挪到「未作响应情况」之后（不插队）✅
        → 提示「批量下移 3 项 · 已保存：改名/调整 121」
批量上移 → 顺序完全还原 ✅
批量缩进 2 项 → 两章一起 l2 → l3（关键：不是只降第一个）✅
减少缩进 → 还原 ✅
每次请求都是 {"created":0,"updated":121,"removed":0}；库始终 121 行 / 5 章正文 ✅
```

### 顺手修掉一个自相矛盾
技术规范书归属行的**状态列写「已指定」、下拉却显示「默认」**：保存的章节不在当前候选列表里，
`<select>` 回落到第一项。现在把当前值补成选项并标注「（已不在当前目录）」，
状态列显示「已指定（不在目录）」—— 界面与实际保存值始终一致。

测试：后端 768 passed / 前端 **110 passed**（新增 8 个批量用例）
截图：docs/screenshots/batch-operations.png

## 十、目录调整支持上下拖动排序

用户要求：「改成可以上下拖动」。

### 交互
- 每行行首一个 `⠿` 手柄：**按住上下拖动**，拖动中显示蓝色**插入指示线**，松手即保存
- 拖动的行会变淡（`.is-drag-src`）；`Esc` 取消
- **勾选多行后拖任意一行 = 整组一起拖**（与批量按钮共用同一份选择）
- 批量按钮（上移/下移/缩进/减少缩进）保留：不需要精确落点时更好用

### 规则（放在模型层，有 node --test）
`moveOutlineNodeTo` / `moveOutlineNodesTo`：
- **连带整棵子树**一起走
- 落点层级 = **插入点后一个节点的层级**（拖到谁旁边就成为它的同级；插到最顶 = 1 级）
- **不能拖进自己的子树**、原位不动 → 返回 null，**不写库**
- 整组拖动时组内顺序不变，父子同时选中不会重复搬

### 实测（真机 pointer 事件）

## 十一、拖动改为 Notion 式（水平位置决定层级）

用户要求：「改成 Notion 那种拖动的方式，根据水平位置成为子级、同级、上级」。

### 交互
- 按住 `⠿` 上下拖动 → 蓝色指示线**按层级缩进**，旁边一个跟随指针的小标签：
  `成为子级（第 3 级）` / `同级（第 2 级）` / `上级（第 1 级）`
- 松手即保存；`Esc` 取消；勾选多行时整组一起拖

### 层级规则（模型层 `levelRangeAt` + `*ToLevel`，有 node --test）
- 水平位移每 `18px` 换算一级（与 CSS 的层级缩进一致）
- 基准 = **插入点后一个节点的层级**（不横移的手感 = 成为它的同级）
- **上限 = 插入点前一个节点的层级 + 1**（最深只能当它的子级，不会跨级）
- 插到最顶 → 只能是 1 级
- 仍连带整棵子树；原位 + 同层级 → null，不写库

### 实测（真机 pointer 事件）
```
拖 s1.4 到 s1.2 之前 + 右移两格：

  提示「拖动 1 项（第 3 级） · 已保存：改名/调整 121」，{"created":0,"removed":0}
还原（用原始目录 POST）→ created:0 / updated:121 / removed:0，结构与 5 章正文完全还原 ✅
```

### 一处 UI 细节

## 十二、批量删除

### 交互
- 操作条加 `[批量删除]`（危险色）：`已选 2 项 [批量上移][批量下移][批量缩进][减少缩进][批量删除][清空选择]`
- 弹窗**说清代价**：「删除选中的 2 章？其子树会一并删除；已写正文保留在库里。」
  （与单节删除同一语义：删的是**目录节点**，正文留在库里）
  - 选中项里**有正文的章节会单独报数**（「其中 2 章已有正文，正文保留在库里」）
- 确认按钮用 `danger` 变体（浅红底 + 深红字）✅ 可见（上一提交修好的白底白字问题）
- 删除后清空选择，提示「批量删除 2 节 · 已保存：改名/调整 116 · 删除 2」

### 模型层（有 node --test）
`removeManyOutlineSubtrees(nodes, ids)` → `{nodes, removed}`：
- 各自**连带子树**删除；`removed` = 实际删掉的**节数**（含子树）
- **父子同时选中只算一次**（取并集，不重复删）
