# 产品设计分析：「待确认」模块该确认什么

> 依据：`/api/projects/26/split-report` 的 8 项 `confirmations` + 面板 ② 的实际渲染 + 代码里已具备的能力。
> 结论先行：**当前 ② 让用户确认的 8 项里，只有 2 项是真正的用户决策；而你说是关键的那两件事
> （目录结构完整性/可调整、技术规范书内容如何结合）在 ② 里恰恰没有呈现。**

---

## 一、现在 ② 待确认 让用户确认什么

| # | 项 | 系统给的"答案" | **该谁来回答** | 判定 |
|---|---|---|---|---|
| 1 | 按哪个标包/标的拆分？ | 编号：2 | 用户 | **决策**（但已在面板顶部「筛选·标包 → 确认标包」做过 → **重复**） |
| 2 | 评分类别识别是否正确？ | tech 8 条 | 用户 | **决策**（但已在 ② 的「要生成哪些类别」勾选框做过 → **重复**） |
| 3 | 评分点分值合计 100 分是否与招标文件一致？ | 8 个评分点，合计 100 分 | **系统** | **自检**（用户无法核对全部评分表；异常时才需人工介入） |
| 4 | 评分点清单是否正确、是否都已纳入拆解？ | 8 个评分点，合计 100 分 | 用户 | **决策**（属于第①步「评分点」，应留在①确认，不应在②再问一遍） |
| 5 | 规范书要求主题该挂到哪些章节？ | 19 个主题、153 条要求 | 用户 | **决策 ✅ 真问题**（技术规范书如何结合目录） |
| 6 | 标星项（★/▲）是否都已进入目录？ | 目录中带标星 0 个 | **系统** | **自检** |
| 7 | 目录结构（大评分点→详细评审项→子检查项）是否合理？ | 8 个评分单元、37 个详细评审项、76 个子检查项 / 结构完整 | 用户 | **决策 ✅ 最关键**（但只给了计数，没给可操作的目录） |
| 8 | 是否只按选中的这张评分表拆分？ | 选中「标的1标包2」，另 2 张未选中 | 用户/系统 | **决策**，但已在第 1 项范围内确定 → **重复** |

**统计**：8 项里 = 决策 2 项（#5 #7） + 重复决策 3 项（#1 #2 #8） + 自检 3 项（#3 #6 + #4 的一半）。

### 这带来三个具体问题
1. **用户被要求"确认"他判断不了的东西**：#3 分值合计、#6 标星覆盖率 —— 用户没有对照物，
   只能盲点「确认」。**让人对自己无法判断的事负责，就是在教他忽略这个界面。**
2. **同一件事问两遍**：#1 与顶部标包确认、#2 与类别勾选、#4 与第①步评分点确认。
   重复会让用户怀疑"我前面那次确认算不算数"。
3. **真正该决策的没有可操作界面**：#7 只给了"8 个评分单元、37 项、76 子检查项 / 结构完整"
   这样的**计数**，没有目录本身；#5 只有下拉选归属，看不到"结合之后目录长什么样"。

---

## 二、一个更要紧的发现（能力有，入口没了）

「目录结构是否合理、是否需要调整」——**这个能力早就实现了**：

```
mode-outline.js: function structureEditable() { … }
  · 增删章节 / 改标题 / 上下移动 / 缩进（纯逻辑在 workspace-model.mjs，有 node --test 覆盖）
  · UI 挂在**下面的目录树**上（.structure-editable + 行内「编辑」按钮）
  · 仅在 extractionState === 'gate_outline' 或 'done' 时可编辑
```

而我前几轮为了让面板成为唯一内容面，加了 `hideLaneTreeWhenPanelShows()` ——
**面板一打开就把那棵树隐藏了**。于是：

> **用户说是关键的能力（调整目录结构），在现在的面板形态下没有入口。**

（对比：② 的 #7 还在问"结构是否合理"，但用户既看不到结构，也无从调整。）

---

## 三、设计原则（建议以此为判定标准）

**待确认 = 只有满足下面三条的项才该出现**
1. **是用户的决策**（系统无法替他决定）；
2. **决定会影响产物**（不是给用户汇报"我干了什么"）；
3. **界面上有可操作的载体**（能给选项/能编辑，而不是让他在一句陈述后面点"知道了"）。

不满足的项 → 归为**检查结果（自检）**：以一行摘要展示，**只有异常时才升级为待确认**
（例如"分值合计 90 ≠ 100" → 提示"可能有评分点没解析出来"并给"重新拆分"入口）。

---

## 四、建议的新 ②「目录确认」（单一决策面）

把 ② 从"8 项确认清单"改成**一屏目录确认**，用户在这里只做两件事：

```
┌ ② 目录确认 ───────────────────────────────────────────────────────────────┐
│ 自检：✅ 分值合计 100/100  ✅ 结构完整（8 评分单元 / 37 详细项 / 76 子检查项）      │
│       ✅ 标星项已入目录 0 个   ⚠ 6 个评分点名下没有挂到要求  ← 异常项才需要处理      │
├──────────────────────────────────────────────────────────────────────────┤
│ 目录结构（可直接改：改名 / 增删 / 上下移 / 缩进）              [编辑模式 ▾]        │
│  ▸ 技术方案可行性        12 分   ← 评分点：技术方案可行性                        │
│      · 技术方案完整性            ← 挂载：技术规范书 3 条                         │
│      · 技术方案可行性            ← 挂载：技术规范书 4 条（含 2 条必须响应）        │
│  ▸ 财务状况 · 营业净利率   10 分  ← 评分点：财务状况/营业净利率                   │
│      · 证明材料与数据来源         ← 挂载：技术规范书 0 条（本章→ 需举证 2 项）      │
│  ▸ 未归属主题（6 个）：安全与保障体系研究及验证、埋点与低延迟…  [指到某章 ▾]        │
├──────────────────────────────────────────────────────────────────────────┤
│ [确认目录，生成产物]        ← 唯一的确认动作                                    │
└──────────────────────────────────────────────────────────────────────────┘
```

### 具体怎么落
| 现在 | 改成 |
|---|---|
| 8 项确认清单（含 3 项自检、3 项重复） | 顶部**一行自检摘要**（异常项才展开处理） |
| #7「结构是否合理」只给计数 | **目录本身**直接呈现在 ② 里，并**复用已实现的结构编辑**（改名/增删/上下移/缩进） |
| #5 主题归属只有下拉 | 归属**内联进目录**：每章显示"挂载的规范书要求条数/主题"，主题可就地改挂到别的章 |
| #1/#2/#8 已在上方或第①步确认过 | **只读回显**（"范围：标的1/标包2 · 类别：技术"），不再重复确认 |
| 结构编辑只能在下方的目录树里（且被面板隐藏） | 把 `.structure-editable` 的能力**搬进 ② 的目录视图**，去掉对下方树的依赖 |

### 与③产物的关系
- ② 确认 → 生成产物（目录 + 映射矩阵）→ ③ 只读查看 + 覆盖率。
- 「技术规范书内容结合进来后怎么改目录」的**改动入口在 ②**；③ 是结果视图（可回②再改）。

---

## 五、落地顺序（建议）

| 阶段 | 内容 | 收益 |
|---|---|---|
| **P0** | 自检项从"待确认"降级为**一行检查摘要**；去掉 #1/#2/#8 三处重复确认；#4 归回第①步 | 立刻去掉 5/8 的噪声，决策面变清晰 |
| **P1** | ② 主区换成**目录树 + 结构编辑**（复用 `structureEditable` 那套），并显示每章挂载的规范书要求 | 用户能真正判断"结构是否完整、要不要调整" |
| **P2** | 主题归属内联进目录（就地改挂）+ 未归属主题的显式分区（"技术规范书要求应答"章节） | 技术规范书与目录的结合变得可见、可改 |

---

## 六、一句话总结

> 现在 ② 是**"系统向用户汇报自己的 8 项工作，并请用户逐个点确认"**；
> 它应该是**"用户在一屏里审目录结构（可改），并看清技术规范书要求分别落到哪一章，然后确认生成"**。
> 前者把责任推给无法判断的用户，后者才是产品该承担的判断。
