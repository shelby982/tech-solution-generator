# 方案：标包驱动的主流程（标包分析 → 评分点拆分 → 应答目录 → 编写）

> 本文只做核查与方案，**不改代码**。请审核后再动。
> 核查方式：读数据（SQLite 现状）+ 读代码路径（后端/前端），每条结论都附证据。

---

## 一、核查结果：现状到底是什么

### 1.1 数据模型（当前真实字段）

| 表 | 与标包相关的字段 | 现状 |
|---|---|---|
| `materials`（上传材料） | **无** | ✗ 文件与标包**没有任何关联** |
| `workflow_runs`（运行） | `target` / `package_no` | ✅ 有（本会话新加），但老运行仍为空 |
| `review_points`（评分点） | `package_no` / `category` | ✅ 有 |
| `spec_requirements`（规范书要求） | `package_no` | ✅ 有 |
| `split_answers`（确认答案） | `thread_id`（按运行作用域） | ✅ 有，答案**跟着运行走** |
| `blocks`（应答目录） | 无标包字段 | ✗ 靠 `workflow_runs` 归属 |

**实测数据（项目 26）**：
```
materials         2 行，无 package_no                    ← 问题①的根
workflow_runs     3 条：仅最新一条有归属（标的1/标包2）；另两条为空
review_points     24 行，全部 package_no='2' 且 category='tech'   ← ⚠ 只有技术
spec_requirements 459 行，带 package_no
split_answers     3 行，都绑定同一个 thread_id（答案不串标包 ✅）
```

### 1.2 ⚠️ 核查中发现一个**比三个问题更根本**的事实：评分点有**两处真相**

- **界面**显示「商务评分点 8 · 技术评分点 8 · 技术规范书要求 153」（来自检查点里的
  `scoring_map`，即解析出的评分表）
- **数据库**里 `review_points` 却只有 **24 条、全是 tech、全属标包 2**

也就是说：**解析出来的评分点**与**拆分落库的评分点**是两套数据，且当前不一致。
这解释了用户"拆分完评分点之后对应不上"的直觉 —— 界面用的是 A，落库/后续用的是 B。

**结论**：只补"标包关联"不够，必须先把**评分点的单一真相**定下来（见方案 §3.2）。

### 1.3 现有流程的真实路径

```
上传文件（materials 解析 → material_chunks）
   ↓  ← ✗ 这里没有任何"标包分析"：标包要等到解析评分表时才被识别
点「拆分评分点」→ 新起一条 workflow_run
   ↓
解析 → 从招标文件里解析评分表 → 得到 scoring_map（含各标的/标包）
   ↓
张衡拆分评分点（读 answers.categories，按类别筛点）→ 写 review_points
   ↓
派生应答目录（zhang_heng + outline_builder）
     · 输入：评分点 + 规范书 toc + topic_placement（主题归属）
     · 都**已经**接上（后端确实消费 categories 与 topic_placement ✅）
   ↓
blocks 落库 → 编写 → 评审
```

**关键结论：后端该接的都接上了**（类别 ✅、主题归属 ✅、运行按标包 ✅）。
缺的是 **①文件→标包的关联**、**②评分点的单一真相与按标包拆分**、
**③类别选择在界面上的位置与显式性**（这块我上一轮刚修复了一个"勾选框被我删掉"的回归）。

## 二、逐条对应你提的三个问题

### 问题① 标包关联缺失（重复上传文件之后，标包没有关联关系）
- **根因**：`materials` 无 `package_no`；标包是在**解析评分表时**才被识别出来的，
  而"上传文件"这条路径与标包**完全无关**。
- **证据**：`materials` 表结构；上传/解析链路里没有任何 package 相关代码。
- **后果**：重复上传后，下方标包列表仍来自**上一次拆分**跑出来的评分表 →
  看起来"新传的文件跟标包没关系"。

### 问题② 评分点关联缺失（切换标包后，评分点拆分要跟标包关联）
- **根因（两层）**：
  1. **拆分是按"运行"跑的**，不是按标包跑的；界面切换标包只是**筛选**已有数据
     → 目标标包若没跑过拆分，就没有它的评分点。
  2. 更根本：评分点**两处真相**（§1.2）→ 即使跑过，也可能只是其中一部分类别。
- **证据**：`review_points` 只有标包 2 的 tech 24 条；而界面显示商务+技术各 8。
- **已有基础**：`workflow_runs.target/package_no` + `latest_for_scope()`（本会话已加）
  → "按标包取/建运行"的地基在，缺的是"文件归属标包"和"拆分只吃该标包的文件"。

### 问题③ 目录生成逻辑缺失（要选商务还是技术评分点）
- **核到的事实**：后端**已经**消费类别选择（`zhang_heng` 读
  `answers.categories`，按类别筛点；生成结果还会写"本次目录包含：技术 N 个评分点"）
  并且**已经**消费主题归属（`outline_builder` 的 `forced_host`）。
- **真正的缺口**：**界面**上这组类别勾选框被我上一轮重构时删掉了（今天已修回），
  而且它藏在第 2 步里、与"目录结构"混在一起，**没有作为"生成目录的一个明确选项"出现**。
- **结论**：这不是"后端没逻辑"，而是"选择入口不明显/一度消失"。

## 三、优化方案

### 3.1 目标流程（按你给的四步）

```
① 上传文件  →  ② 标包分析  →  ③ 评分点拆分（按标包）  →  ④ 生成应答目录  →  ⑤ 编写
   materials      显式一步        选定标包后拆（商务+技术）    选类别 + 结合规范书      逐章
```

**界面落位**（沿用「左五步 + 右内容」的既有壳，不新增页面）：
- 第①步「评分点」里，把顺序改成：**标包（卡片/表）→ 拆分按钮 → 评分点清单**
- 顶部「筛选·标包 + 确认标包」保留（它是"切换当前标包"的入口）

### 3.2 数据模型改动（P0，先定单一真相）

| 改动 | 目的 |
|---|---|
| `materials` 增 `package_no TEXT NOT NULL DEFAULT ''` | 文件归属标包（问题①） |
| 新增 `package-analysis` 结果落库（`project_packages`：target / package_no / package_name / source_material_ids / confidence） | 标包分析的**唯一产物**，供下拉/确认/拆分使用 |
| **评分点单一真相**：确认"落库的 `review_points` 就是唯一来源" | 消除 §1.2 的两处真相：界面改为**从库里读**，`scoring_map` 只作解析中间态 |
| `review_points` 增唯一键 `(run_thread_id, point_id)`（若无） | 重复拆分不产生重复行 |

### 3.3 三个关键动作（P0）

**动作 A：标包分析（问题①）**
1. 上传后**自动**跑一次"标包识别"：
   - 文件名规则（`标的N` / `标包N` / `包N` / `第N包`）
   - 正文规则（招标文件里的"标包划分"章节、评分表表头）
   - 输出：`[{target, package_no, package_name, source_material_ids, confidence}]`
2. 第①步界面展示**标包卡片**：每个标包一行，标出来源文件、条数、置信度；
   用户可以**改名/合并/拆分/指定文件**（低置信度必须人工确认）
3. 没有解析出标包时：明确提示"未识别到标包，将按整份文件处理"（不假装有）

**动作 B：按标包拆分（问题②）**
1. 拆分输入 = **该标包关联的文件集合**（`materials.package_no = 该标包`），
   `spec.toc` 也按这些文件的规范书重建
2. 拆分产物 `review_points` 一律写入该标包的 `package_no`，
   **商务、技术都落库**（不再只落 tech）
3. 切换标包 = 按 `(project, target, package_no)` 取/建运行（已有 `latest_for_scope`）；
   目标标包没有运行 → 明确提示"该标包还没拆过，点拆分"

**动作 C：生成目录时显式选类别（问题③）**
1. 在「待确认」第①步（我上一轮已把顺序调成：技术规范书确认 → 目录确认与调整）之上，
   加一个**明确的"要生成哪些类别"区块**，默认勾选该标包**实际存在的类别**
   （`review_points` 里有哪些 category 就列哪些），并显示各类别的评分点数与分值
2. 「确认目录，生成产物」的动作里，把类别写入**该标包的运行**（已有 ✅），
   生成后把后端那句"本次目录包含：技术 N 个评分点 / 商务 M 个"回显到③产物页
3. 只选技术 / 只选商务 / 两者都选，三种组合都要有可预期的结果（后端已支持 ✅）

### 3.4 分期

| 阶段 | 内容 | 收益 |
|---|---|---|
| **P0-1** | `materials.package_no` + 标包识别（规则版）+ 第①步标包卡片与人工修正 | 问题①闭环 |
| **P0-2** | 评分点单一真相（界面改读库）+ 拆分按标包、商务技术都落库 | 问题②闭环 |
| **P0-3** | 「要生成哪些类别」显式区块 + 结果回显 | 问题③闭环 |
| **P1** | 材料条明细里逐文件标包下拉；标包置信度低时的引导 | 日常可用性 |
| **P2** | 老数据迁移（`materials.package_no=''`、老运行归属补全） | 历史项目可用 |

## 四、验收标准（每条都能实测）

1. **标包分析**：上传含 3 个标包的文件 → 第①步出现 3 个标包卡片，标出来源文件；
   仅上传 1 个标包的文件 → 只出现 1 个，不虚报。
2. **按标包拆分**：选定标包 2 → 得分点只含标包 2 的商务+技术；
   库里 `review_points` 的 `package_no` 全为 '2'，且 **commerce 与 tech 都有行**。
3. **切换标包**：切到标包 1 → 界面立即只显示标包 1 的评分点/目录/正文；
   若标包 1 没拆过 → 提示"该标包还没拆过，点拆分"（不显示别的标包内容）。
4. **生成目录**：「要生成哪些类别」明确可见、默认勾选实际存在的类别；
   只勾技术 → 产物只含技术章节；勾两者 → 产物含两类且回显"技术 N / 商务 M"。
5. **重复上传**：追加/替换文件后再看标包 → 标包列表反映**新文件**（不是上一次拆分的旧列表）。
6. 全程 `__bootErrors` 为空；后端/前端测试全绿。

## 五、边界（这次不动的东西）

- 不动「左五步 + 右内容」的外观与交互约定（你多次强调的）
- 不动顶部「筛选·标包 + 确认标包」的位置
- 不动待确认的两步顺序（上一轮刚按你的要求调成：技术规范书确认 → 目录确认与调整）
- 不引入新的页面跳转（仍在同一壳内）
- 不重写评审链路

## 六、需要你定的三个选择

1. **标包识别的来源**：只认文件名/正文规则（快、可预期），还是要用 LLM 辅助识别（准、有成本）？
2. **标包与文件的关系**：一个文件**只属于一个标包**，还是可以属于多个（例如通用招标文件同时适用多个标包）？
3. **P0 的落地顺序**：先做 ①（文件→标包）还是先做 ②（评分点单一真相）？
   我建议先 ② ——它是数据基础，不做的话 ① 做完界面还是对不上。
