## 一、现状诊断（都有实测证据，不是感觉）

### 1. 上传区只有 **56px 高**，却塞了 6 件事
```
材料 2 · 技术规范书 1 · 招标文件 1   [＋ 添加文件] [解析标包] [明细 ▾]   多选·类型按文件名建议，可在「明细」里改
└─计数─┘ └────类型摘要────┘         └─3 个按钮─┘                     └───────一句说明文案───────┘
```
实测：`document.getElementById('materials-panel').getBoundingClientRect().height === 56`。

**后果（今天就撞到）**：我加「解析标包」按钮时，因为所有按钮共用一个 `flex:1` 的样式，
「＋ 添加文件」被**挤成两行**。这不是像素问题，是**一行里没有主次**的必然结果。

### 2. 文件状态全部藏在「明细」后面
一个文件有 5 个维度要表达，现在**一个都不在面上**：

| 维度 | 现在怎么看 | 问题 |
|---|---|---|
| 文件类型（招标文件/技术规范书/素材） | 点开「明细」看下拉框 | 类型决定文件进哪条链路，是**关键信息** |
| 解析状态 | 点开「明细」看徽标 | 最要紧的"到底读没读到内容" |
| **正文是否为空** | 完全看不到 | 今天才发现：`parse_status='done'` 但 0 个 chunk |
| 标包归属 | 点开「明细」再点按钮 | 这是本模块的业务核心 |
| 文件是否还在磁盘 | 完全看不到 | 今天新加的检测 |

### 3. 没有"下一步"的指引
上传完，用户不知道要**解析标包**（我昨天才补上按钮，它现在和另外两个按钮并排，没有主次）。
更早的版本连按钮都没有。

### 4. 展开「明细」会把整个五步工作台**顶下去**
`明细 ▾` 是同行的折叠面板，展开后页面内容整体下移 —— 违反你反复强调的
「左五步 + 右内容、不要跳」的稳定感。

### 5. 空状态（第一次用）没有任何引导
没有任何"先传招标文件、再传技术规范书"的顺序提示，也没有拖放区（只能点按钮选文件）。

## 二、设计目标（这次要解决的）

| # | 目标 | 验收方式 |
|---|---|---|
| 1 | **文件状态一眼可见** | 不点任何东西，就能看出每个文件的类型/解析/标包 |
| 2 | **下一步无可争议** | 界面上只有**一个**主按钮，且它就是当前该做的事 |
| 3 | **不挤** | 任何按钮都不换行；信息按主次分层，不是平铺 |
| 4 | **展开不跳** | 展开详情不推挤下面的内容（就地展开或侧滑） |
| 5 | **第一次用也知道干嘛** | 空状态给出顺序 + 拖放区 |

## 三、三个方向

### A) 文档台面（Document Desk）— 横向文件卡片
```
材料 2 · 3 份文件 · 共 4.8 MB                              [＋ 添加文件]  [解析标包]
┌───────────────────┐ ┌───────────────────┐ ┌───────────────────┐
│ [招标文件]         │ │ [技术规范书]       │ │ [素材]             │
│ 1_2026年南网…pdf   │ │ 2_标的1：2026…docx │ │ 资质证明.pdf       │
│ ● 已解析           │ │ ⚠ 未解析出正文     │ │ ● 已解析           │
│ 标的1 标包2        │ │ 未指定标包         │ │ —                 │
│           查看 ›   │ │        重新解析 ›  │ │           查看 ›   │
└───────────────────┘ └───────────────────┘ └───────────────────┘
解析标包 = 读取已上传文件的正文，检索「标的 / 标包 / 标段」，只按原文事实列出            ⌄
```
- **每张卡自带状态与操作**：状态跟着文件走，不用点开
- 主按钮只有一个（解析标包），次按钮降级
- 高度约 130-150px，可折叠
- 视觉：圆角卡片、浅灰底、蓝色主色、Inter/系统字体

### B) 左栏收件台（Intake Table）— 密集表格
```
左栏：「① 上传与解析」与既有五步风格一致
┌ 拖入文件或点击选择 · 支持多选 ────────────────────────────┐  [解析标包]
├────────────┬──────────┬──────────┬──────────┬──────────────┤
│ 文件名      │ 类型      │ 解析      │ 标包      │ 操作          │
│ 1_2026…pdf │ 招标文件 ▾│ ● 已解析  │ 标的1标包2│ 重新解析 删除 │
│ 2_标的1…docx│ 技术规范书▾│ ⚠ 未解析出正文│ 未指定   │ 重新解析 删除 │
│ …（5 行）   │          │          │          │              │
└────────────┴──────────┴──────────┴──────────┴──────────────┘
```
- **信息密度最高**：几十份文件一屏看完，可逐列比对
- 行高 28-30px、方角、表格化、绿色状态点
- 适合"先批量上传、再逐条核对"的重度用法

### C) 三步向导（Stepper Wizard）— 引导式
```
① 拖入文件 ──── ② 确认识别结果 ──── ③ 解析完成
              （当前）
 ✓ 1_2026…pdf    类型 [招标文件 ▾]   标包 [标的1 标包2 ▾]   忽略
 ✓ 2_标的1…docx  类型 [技术规范书 ▾]  标包 [标的1 标包2 ▾]   忽略
 ⚠ 资质证明.pdf  类型 [素材 ▾]       标包 [未识别到标包 — 请选择 ▾]
                              [上一步]        [确认并解析标包]
```
- **把"上传完还要确认"变成流程的一部分**，第一次用的人不会漏
- 竖排清单 + 每行确认、字号偏大、暖色（琥珀/青）、进度条明显
- 代价：熟练用户每次上传都要走三步

## 四、怎么选（我的判断）

| 你的真实工作方式 | 选 |
|---|---|
| 一次传 2-5 份，想看清每份状态、不想被表格感压住 | **A** |
| 一次传十几份、经常核对"哪份没解析/没归标包" | **B** |
| 主要给不熟悉系统的人用，或者"标包确认"是必须卡住的环节 | **C** |

**我倾向 A**，理由是这个系统的上传量本来就小（招标文件 + 技术规范书 + 几份素材），
而"每份文件是什么、读到没有、归哪个标包"恰恰是用户的三个真实困惑 ——
卡片形态最贴合。B 的密度优势在这个使用量下用不着，C 的强制确认对熟练用户是负担。

**但 B 有一个 A 没有的价值**：它以列的形式强制暴露「解析 / 标包」两列，漏项一眼可见 ——
如果你更在意"绝不漏"，B 更稳。

## 五、三个方向都保持的硬约束

- **不新增页面**：仍在「左五步 + 右内容」的同一个壳里
- **不动待确认的两步顺序**（技术规范书确认 → 目录确认与调整）
- **不动顶部「筛选·标包 + 确认标包」**
- 上传区的产出仍然是同一套数据（`materials` / `material_packages` / `project_packages`）

## 八、核实「明细 / 收起」逻辑（用户要求）

### 核实发现的真 bug（已修）
```
初始                : mrow2 collapsed 「明细 ▾」 aria=false h=0    ✅
点「明细」           : mrow2 expanded  「收起 ▴」 aria=true  h=54   ✅
再点 / 三次          : 正常来回切换                                ✅
明细开着时点卡片徽标  : collapsed（被关掉了）✗✗  ← BUG
```
**根因**：我加卡片时，"查看明细"和"类型徽标"的处理里调了
`mat-manage.click()` —— 那是个**切换**，明细开着时点它反而**关掉**；
另一处又直接改 `classList`，和按钮文案/aria 不同步。

**修法**：收口成单一入口 `setDetailsExpanded(open)` —— 类名、按钮文案、aria、摘要一起改；
卡片动作用**展开**（不是切换）。实测：明细开着点徽标 → **仍展开** ✅。

### 顺带补上设计稿 A 承诺、但第一版漏做的能力
- **台面收起/展开**（`setDeskCollapsed`）：头部新增「收起台面 ▴ / 展开台面 ▾」
- 状态记 `localStorage['ge.matDesk.collapsed']`，刷新后保持
- 两个折叠按钮**不再重名**：一个是「明细」，一个是「台面」
  （第一版两个都叫「收起」会混淆）

### 实测
```
按钮文案：明细 ▾ / 收起明细 ▴ ｜ 收起台面 ▴ / 展开台面 ▾   ✅
明细开着点卡片徽标 → 仍展开                                ✅  （bug 已修）
收起台面 → 卡片区与说明行一起隐藏，localStorage 写入 '1'    ✅
__bootErrors=[]
```

### ⚠️ 我没能验证的一点（如实说明）
**"刷新后保持收起"我无法用自动化验证** —— 我的 CDP 工具每次都是全新浏览器配置，
用探针键实测 `localStorage.getItem('probe')` 在第二次启动时也是 `null`。
所以：`localStorage` 写入**已验证** ✅，"跨刷新读回"**未验证** ✗。
不过这套写法与本项目既有的折叠状态完全一致（`matching:laneCollapsed`、
`workbench:reqBar` 都是这个模式），风险很低。**请你在浏览器里刷新一次确认**（收起台面 → 刷新 → 应仍是收起）。
