# 章节编写方案 · 修订版：19 个问题与最优解

> 本文是对《章节编写方案-计划为中心》的**自我批判 + 修订**。
> 原则：宁可现在暴露矛盾，也不要把矛盾带进实现。

---

## 一、问题清单（按严重度）

### 严重（会直接导致做错）

**P1｜"章"的定义不唯一**
现状：p29 有 124 个节点，层级是 一级目录 → L2 → L3 → L4；有些 L3 章**自己写正文、同时还有子节**
（如"对项目的理解"7127 字，下面还有"项目背景现状目标/建设范围/建设内容"）。
方案原写"章是单位"，但没说清是"叶子"还是"每个可写节点"。

**最优解**：单位 = **可写节点（有正文的节点）**，不区分 L3/L4。
- 叶子 = 独立计划；
- 父章 = 自身要求 + 子章要求（**嵌套计划**，父章自己的要求单列一栏）；
- 纯目录节点（无正文、无要求、无子单元）→ 不出计划。

**P2｜"要求"的来源没定义，草稿容易变成"通用套路"**
现状：requirements 由 8 类模板/配方**确定性起草**。
问题：真实的要求来自"主编 + 评分点要素 + 招标条款"，模板只是兜底；否则每章要求都像复制品。

**最优解**：三级来源，优先级明确
```
① 评分点要素（强相关，来自 review_points.item/criterion）→ 直接转成要求
② 规范条款（spec_requirements：强制性/★ 优先）
③ 8 类章模板（兜底，保证结构完整）
```
- 每条要求标注来源（`from: point|clause|template`），用户在计划里能看到"这条要求依据哪来的"
- LLM 起草作为**可选的第四档**（针对特殊章节），不默认开

**P3｜依据与要求是多对多，方案按"列表显示"处理了**
现状：方案里 `basis` 是「依据：对项目的理解·10分」这类**展示文本**，而实际关系是：
一条要求可依据多个评分点/条款；一个评分点可对应多条要求。

**最优解**：
- 数据上：`requirement.basis_ids[]`（多对多）；默认继承本章的全部依据（省事），逐条可覆盖
- 界面：要求行显示 `依据 2 条 ▾`，展开可看；**依据页/条款不单独维护**，都以"要求"为锚点

**P4｜素材"已补/待补"的判定太粗**
现状：只要绑定了 ≥1 个片段就叫"已补"。
问题：一条政策要求绑一行业新闻也能"已补"，但实际仍不可用。

**最优解**：给每类需求设**最小门槛**（可配置）
| 需求类型 | 最小门槛 |
|---|---|
| 政策/制度依据 | ≥1 条**官方来源**片段（trust=official）|
| 标准条款 | ≥1 条标准发布机构原文片段 |
| 行业数据 | ≥1 个可引用的数值/表格片段 |
| 案例佐证 | ≥1 条完整案例描述片段 |
| 我方证明 | ≥1 份我方材料（非外部）|
| 图片示意 | ≥1 张入库图片 |
- 状态改为三档：`已满足 / 已补不足 / 待补`（不足时说明差什么）

**P5｜F（还差什么）与 D（素材需求）重复**
现状：D 列素材需求，F 又列"素材待补"→ 同一个问题出现两遍。

**最优解**：**D 只显示"需求与状态"，F 只显示"未解决项"**
- F = 所有未达成项的**去重汇总**（素材未满足 + 要求未回应 + 图表缺失 + 格式问题）
- D 的每条"未满足"在 F 里有一条对应动作；F 里不重复展示 D 的完整列表

**P6｜"一个数字一个 owner"被违反**
现状：B 段写「12 页 · 已写 8.4 页」，进度里也写「已写 8.4 页」。

**最优解**：
- **计划（B）只显示"计划多少页"**（可调，编辑态）
- **进度只显示"已写多少、差多少"**（结果态）
- 章头（中间）可同时显示"8.4/12 页"的进度条 —— 但那是**进度**的展示，不重复在计划里编辑

### 中等（影响体验与可维护性）

**P7｜章节状态与"完成"的判定没有规则**
现状：S4 说"系统判定完成"，但没定义。

**最优解**：
```
待验收 = 有正文 且（要求未回应 或 素材未满足 或 图表缺 或 有 high 问题）
已完成 = 要求全回应 + 素材全满足 + 图表齐 + 无 high/medium（或人工确认覆盖，留痕）
```

**P8｜F 的"标为已处理"与计划变更会互相失效**
现状：标了已处理，之后改了要求 → 旧标记不该继续生效。

**最优解**：finding 记录"关联的要求指纹"（requirement 文本 hash）；要求变了 → 旧 finding 自动置为 `stale`（重新出现）

**P9｜计划变更没有影响面**
现状：改了要求/篇幅/图表规则，正文不会提示重写。

**最优解**：计划每次保存 → 记录版本；若与"当前正文生成时用的计划版本"不同 → 章头提示「计划已变更，建议重新生成」（类似编写规范的版本留痕，已有先例）

**P10｜生成时"计划全塞进提示词"不现实**
现状：A~E 全进提示词，token 会爆。

**最优解**：分层注入
```
必带：A 要求（逐条，带类型）+ D 已绑定片段（每条 ≤3 个，每个 ≤600 字）+ E 图表清单
选带：C 写法要点（取 3 条最相关）+ B 篇幅（换算成字数区间）
不带：依据原文全文（只带标题）、素材池全量
```

**P11｜父章（有子节）的正文与子节正文会打架**
现状：父章既有正文又有子节 → 生成时父章可能重复写子节内容。

**最优解**：
- 父章计划里明确「本章只写总述（≤N 页），细节见各子节」
- 生成父章时，子节内容作为"已知上下文"（避免重复），提示词写"不重复子节已覆盖的内容"
- 验收：父章正文里出现子节标题的关键词 → 提示"疑似重复子节内容"

**P12｜确认粒度与效率**
现状：目录级确认（一次确认 5~7 章）效率高，但用户要"章级"。

**最优解**：**双粒度**
- 章级确认（默认，每章一个"确认本章计划"）
- 目录级"批量确认"（把目录下所有章一起确认）→ 状态上：目录已确认 = 其下所有章都确认

**P13｜空章/纯目录不出计划，需要规则**
纯目录节点（无正文、无要求、无子单元）→ 不出计划；但"有子单元的父章"要出（见 P11）。

**P14｜素材的"反向导航"缺失**
现在只能"给某条要求选片段"，无法回答"这段素材被哪些要求用了"。

**最优解**：素材池里每条来源/片段标注「被 N 条要求使用」（点开可见），支持解绑。

**P15｜同目录下要求可能重复/冲突**
问题：7 个理解类章节的要求可能大段重复（如都写"政策依据"）。

**最优解**：同一级目录下做**要求去重提示**（相同文本或高相似 → 提示"与第 X 章重复，可改成呼应写法"）；不做强制合并。

### 轻（可后置）

**P16｜角色权限未定义**：主编确认要求、编写人员写正文 —— 至少留字段（`confirmed_by`/`edited_by`），不做权限系统。

**P17｜老数据迁移**：现有 2 份**目录级计划**要拆成章级计划；做法：读旧计划 → 按 chapter 拆成章计划（保留 requirements/tasks/pages）→ 目录确认状态映射为"其下章全确认"。

**P18｜导出门槛**：导出前提示 + 高优未解决时二次确认（不做硬拦）。

**P19｜S1 的范围偏大**：原 S1 包含"面板 + 可编辑 + 质检并入"，实际是 3 块工作。

**最优解**：切成
- **S1a**：本章计划**只读**面板（A 要求+依据 / B 计划页数 / D 需求状态 / E 图表清单 / F 还差什么）—— 纯展示，不改数据
- **S1b**：要求可编辑 + 素材绑定入口
- **S1c**：质检并入（F 的数据源）+ 右栏收敛

## 二、修订后的最优方案（一次说清）

### 2.1 单位与结构

```
标包
└ 应答文件
   └ 一级目录（批量确认/汇总）
      └ 可写节点（章/节，同一套规则）
         ├ 本章计划
         │   A 要求（三级来源 + 依据多对多 + 类型）
         │   B 计划页数（就一个数，可调）
         │   C 写法要点（读自规范）
         │   D 素材需求（类型 + 门槛 + 已满足/不足/待补）
         │   E 图表清单（表 N 张/图 M 张 + 用途 + 来源）
         │   F 未解决项（去重汇总 + 动作）
         └ 子节计划（若有子节，嵌套；父章只写总述）
```

### 2.2 每次进章，用户只面对一个面板（六段，按需折叠）

- 顶部一行：`计划 12 页 · 要求 3 条（1 未落点）· 素材 2 条不足 · 图表 2表1图`
- A~F 六段默认折叠，**A 与 F 默认展开**（要求 + 还差什么，是最高频的两件事）
- 底部：`AI 编制本章`、`确认本章计划`

### 2.3 生成与验收的闭环

```
计划确认（章级） → 生成（分层注入 A/D/E）→ 正文
                                    ↓
                     验收（F）= 要求落点 + 素材满足 + 图表齐 + 格式
                                    ↓
              未达成 → F 出现（钩子：去补/重生成/标已处理）
              达成   → 章状态"已完成"（系统判定 + 人工可覆盖留痕）
```

### 2.4 一致性与留痕

| 事项 | 规则 |
|---|---|
| 计划版本 | 每次保存递增；章头记录"正文生成时用的计划版本" |
| 计划变更 | 与正文版本不一致 → 章头提示「计划已变更」 |
| 已处理标记 | 绑定要求指纹；要求变了自动 stale |
| 素材绑定 | 反向可查（素材 → 被哪些要求用） |
| 完成判定 | 由规则算，可人工覆盖并记录 |

### 2.5 数据补齐（在现有基础上）

| 需要 | 现状 | 补法 |
|---|---|---|
| 要求来源标记 | 无 | `requirement.source: point/clause/template` |
| 要求↔依据多对多 | 无 | `requirement.basis_ids[]`（默认继承本章） |
| 素材门槛 | 无 | 需求类型 → 门槛配置（表） |
| 图表用途/来源 | 只有数量 | `chapter.figures_plan[{kind,name,purpose,source}]` |
| 计划版本 | 无 | `writing_plans.version` |
| 已完成判定 | 纯人工 | 规则 + `completed_by` |

### 2.6 分期（修订）

| 期 | 内容 | 可验收 |
|---|---|---|
| **S1a** | 本章计划只读面板（A/B/D/E/F 全部展示，含"还差什么"） | 一屏看全这一章要写什么、缺什么 |
| **S1b** | 要求可编辑 + 素材绑定 + 素材门槛（已满足/不足/待补） | 能改要求、能看到"补了但不够" |
| **S2** | C 写法要点 + E 图表用途/来源 | 图表能说清"干什么用、从哪来" |
| **S3** | 质检并入 F + 右栏收敛 + 全局降级为进度中心汇总 | 章内不再有独立质检入口 |
| **S4** | 章级确认（批量保留）+ 计划版本/变更提示 + 完成判定 | 计划变更可追溯、完成有依据 |

## 三、与原方案的关键差异（一句话对照）

| 维度 | 原方案 | 修订后 |
|---|---|---|
| 单位 | "章"（含糊） | **可写节点**；父章嵌套 + 只写总述 |
| 要求来源 | 模板起草 | **评分点→条款→模板**三级，标注来源 |
| 依据关系 | 展示文本 | **多对多**（requirement.basis_ids） |
| 素材判定 | 有绑定就算补 | **按类型设门槛**（已满足/不足/待补） |
| D 与 F | 重复 | **D 看状态、F 看未解决项** |
| 页数归属 | 计划与进度都写 | 计划只写"计划页数"；进度写"已写" |
| 完成 | 人工点 | 规则判定 + 人工覆盖留痕 |
| 变更 | 无 | 计划版本 + "建议重新生成"提示 |
| 提示词 | A~E 全塞 | **分层注入**（必带/选带/不带） |
| S1 | 面板+编辑+质检 | **S1a 只读 → S1b 可编辑 → S1c 并入** |

## 四、还需要产品确认的 5 个决策点

1. **父章（有子节）的正文要不要写总述？** 我的建议：要，≤2 页，且明确"不重复子节"。
2. **素材门槛谁来定？** 我的建议：内置一套默认（上表），项目级可调（先不做 UI，先按默认跑）。
3. **章级确认后还允许改要求吗？** 我的建议：允许，但改后章状态回"待验收"。
4. **"已完成"能否人工覆盖？** 我的建议：能，且记录"谁在何时覆盖、理由"。
5. **右栏"编制进度"页签保留吗？** 我的建议：保留（它是结果），但只展示"已写/耗时/角色进度"，不重复计划信息。
