# 待办：从「检查结果列表」变成「可执行的交付清单」（方案 v3）

> 用户反馈：目前只有「上传素材」看得懂是要去上传东西；其他条目看不懂怎么改。
> 「阻塞 / 非阻塞」没有说清需要用户做什么；点进去只跳到页面，看不出哪里有问题。
>
> 本方案不改检查能力本身，改**待办的表达、责任归属、动作和 UI**；目标只有一个：
> **每一行都能让用户知道「现在要我做什么、去哪儿做、做完怎么算好」。**

---

## 一、结论先行

现在的待办是**检查器的输出列表**，不是**用户的任务列表**。要改成可执行清单，收敛为 5 条：

1. **待办只放"系统做不了、必须人做"的事**：上传、决定、确认。
   系统能做的（补依据、补图表、改术语、统一格式）移到「系统处理中」，不要让用户逐条点"一键检索/一键修复"。
2. **每张卡必须回答四问**：哪里有问题 / 为什么重要 / 你要做什么 / 做完怎么算好。
   标题必须是「动词 + 对象」，不能是 `口径未定：出现「待明确」` 这种检查器语言。
3. **「阻塞」改成「影响什么」**：`不处理不能导出` / `不处理不能确认完成` / `影响评分` / `建议优化`。
   没有上下文的"阻塞"一律不显示。
4. **所有条目必须可定位**：章 → 节 → 段 → 原句 + 高亮；缺内容定位到"该出现的位置"。
   点条目 = 打开处理面板 + 定位原文，不是只跳章节。
5. **项目级不做 114 条待办**，做「交付检查」：按根因汇总 + 批量入口；同一材料缺口跨章只出现一次。

一句话：**用户不需要理解检查器，只需要知道"下一件事是什么"。**

## 二、现状诊断（用项目 29 的真实数据）

### 2.1 现在用户看到的 14 项

以「项目背景现状目标」为例（`todo_items` 实测；界面见 [project-todo.png](<docs/screenshots/project-todo.png>)）：

| 用户看到的标题 | 用户的实际困惑 |
|---|---|
| 还有 3 项未满足完成条件 | "3 项"是哪 3 项？和下面重复；且正文明明有 9880 字，却写"还没有正文" |
| 补 1 份「我方材料（数据/案例/业绩）」 | 补什么材料？用在哪一节？什么格式？为什么是我？ |
| 口径未定：出现「待明确」 | 哪句话？改成什么？"去选择"点开只定位到节，没有选项 |
| 口径未定：出现「有待明确」 | 同上，两条几乎一样的卡片 |
| 依据核对：缺少AI与营销业务融合的64个智能场景清单及2027年… | 标题 50+ 字；这是公开能查的还是内部材料？"一键检索"搜什么？ |
| …另外 9 条「依据核对：缺少…」 | 11 条同样形态，用户要逐条点 11 次"一键检索" |
| 缺表格「政策依据映射表（文件/要求/对应工作）」 | 这是系统该生成，为什么让我"一键修复"？修完去哪看？ |
| 缺图示「趋势或现状对比图」 | 同上 |
| 篇幅超建议（9521 / 3000 字） | 怎么精简？精简成什么样？点"一键修复"为什么去补写正文？ |

项目级（`/api/projects/29/todo` 实测）：**96 章有阻塞、284 项、114 章空、124 章未确认**。
用户看到的是一串章节 + "还有 3 项"，仍然不知道该做什么。

### 2.2 根因（不是文案问题，是模型问题）

| # | 根因 | 表现 |
|---|---|---|
| 1 | **标题来自检查器规则，不是任务描述** | `口径未定：出现「待明确」`、`承诺强度：出现「保证」`、`依据核对：缺少…` |
| 2 | **只报"有问题"，不报"为什么找我"** | 所有条目都标"阻塞交付"，但阻塞的是导出、确认完成还是评分，没人知道 |
| 3 | **动作是泛化的"去处理"** | `去选择` / `一键检索` / `一键修复` / `去处理` 都没有说明点完会发生什么、做完在哪看结果 |
| 4 | **系统工作被伪装成用户待办** | 11 条依据检索、2 个图表生成、格式统一，本应由系统做，现在让用户逐条点 |
| 5 | **没有定位数据** | 条目只有章级归属，没有节/段/原句；点击只能打开章节 |
| 6 | **汇总项和叶子项重复** | "还有 3 项未满足完成条件" 与下面的具体项重复，计数对不上 |
| 7 | **动作没有闭环** | 上传只是打开素材面板，没有绑定到缺口、没有复检；忽略只是 localStorage，服务端导出仍然拦截 |
| 8 | **项目级是章节列表，不是任务列表** | 96 章 / 284 项 / 114 空章，没有根因归并和批量动作 |
| 9 | **同一缺口跨章重复** | 「我方材料（数据/案例/业绩）」在近百章各出现一次，没有去重和"上传一次全部生效" |
| 10 | **内部术语当分组名** | "系统去挖的""要你拍板的""交付门槛"——用户要翻译一遍才知道是什么意思 |

### 2.3 现状动作的真实效果| 按钮 | 实际行为 | 问题 |
|---|---|---|
| 上传 | 打开右栏「素材」页签 | 不针对这条缺口，不告诉用户传什么；传完不复检，条目还在 |
| 去选择 | 只有"承诺/极限表述"有选项弹窗；"口径未定"只定位到节 + toast | 用户没有可选项；原文长句夹在 evidence 里，读不懂 |
| 一键检索 | 打开引用检索弹窗 | 11 条各自点一次；不知道搜什么；内部材料根本搜不到 |
| 一键修复 | 提取标题里的「…」当节名，调用**补写正文** | 缺图/缺表却去写文字，动作与问题不匹配 |
| 定位 | 滚动到节标题 | 不到段、不到句、不高亮 |
| × 忽略 | localStorage 记下，前端隐藏 | 服务端不知道，导出检查仍会拦；刷新/换设备失效 |

## 三、用户心智模型与设计原则

用户打开待办时只问五个问题：

1. **我离交付还差什么？**（总体）
2. **哪几件必须我做？**（责任）
3. **现在先做哪件？**（优先级）
4. **具体在哪儿、怎么做？**（可执行）
5. **做完怎么知道好了？**（闭环）

设计原则：

| 原则 | 落地 |
|---|---|
| 责任分流 | 用户只做"系统拿不到的信息 / 授权 / 决策"；系统工作不出现用户按钮 |
| 一卡一动作 | 每张卡只有一个主按钮，动词明确；次按钮最多两个（定位/稍后） |
| 四问齐全 | 标题、位置、原因、动作、完成判据缺一不可 |
| 可定位 | 每条都有 `locator`（章/节/段/字符区间/原句）；没有 locator 的条目不允许进入待办 |
| 可验证 | 动作完成 → 服务端复检 → 通过才消失；不通过显示"还差什么" |
| 去重/批量 | 同一缺口跨章合并；同一章同类问题合并成一张卡 |
| 说人话 | 标题 ≤ 24 字，动词开头；不出现规则名、字段名、技术缩写 |

### 3.1 责任分配表（先定"谁做"，再谈 UI）

| 检查项 | 谁做 | 用户要做什么 | 系统要做什么 |
|---|---|---|---|
| 缺业绩/资质/合同/内部数据 | **用户** | 上传或从素材库选；没有就选"改用拟实施" | 绑定到缺口、复检、跨章复用 |
| 口径未定、承诺强度、角色混用 | **用户** | 从 2–3 个说法里选，或自己写 | 按定位替换、写 revision、复检 |
| 要求未回应、正文为空、章节没写 | 系统 | 只在生成后确认/抽查 | 补写、按占位符插入、复检 |
| 缺图/缺表 | 系统 | 预览后确认插入，或要求重生成 | 按交付物生成、校验、落位 |
| 术语/引用格式/数字不一致 | 系统 | 预览 diff，可撤销 | 批量替换、复检 |
| 篇幅超建议 | 系统/用户 | 选择精简或保留 | 生成精简预览 |
| 确认本章完成 | **用户** | 点确认（有阻塞时先看清单） | 提供完成检查与原因 |
| 全书空章节/未确认 | 用户授权 + 系统 | 选择批量范围、确认代价 | 批量编写/生成清单 |

**判断规则**：只有用户独有的信息（材料、授权、决策）才进「需要你」；其余进「系统处理中」或「建议」。这是本方案与现状最大的区别。

## 四、新的信息架构

### 4.1 三个区（替代现在的 A–F 五组）

```
待办
├─ ① 需要你处理（N）        ← 唯一计入角标的
│    上传 / 决定 / 确认
├─ ② 系统处理中（N）        ← 不需要你操作，可查看进度
└─ ③ 建议优化（N）          ← 不影响交付，愿改就改
```

- **交付门槛不再是一个待办组**，改成顶部「可交付状态条」；展开后指向下面的叶子任务，不重复计数。
- **「系统去挖的」改名为「系统处理中」**，且默认收起；系统失败才转为「需要你」。
- **「要你拍板的」改名为「需要你决定」**，每条必须有 2–3 个可选项。
- **「你要给的」/「要你核对的」** 合并进「需要你处理」，用标签区分（上传/决定/确认）。

### 4.2 右栏线框（窄栏只放"下一件"和摘要）

```
┌ 待办 ──────────────────────────────┐
│ 距交付还差 3 件需要你 · 2 件系统处理中 │
│ ┌ 下一件 ────────────────────────┐ │
│ │ 定「个人信息保护」的口径          │ │
│ │ 项目现状描述 · 不处理不能确认完成  │ │
│ │ [选一种说法]        [定位]       │ │
│ └────────────────────────────────┘ │
│                                     │
│ 需要你处理 3                        │
│ ▸ 上传 1 份业绩材料          [上传]  │
│   用于本章 2 处 · 影响 3 章          │
│ ▸ 定 2 处口径                [选择]  │
│ ▸ 确认「现状分析」补写结果    [查看]  │
│                                     │
│ 系统处理中 2（不用你操作）           │
│ ▸ 补 11 条依据 · 3/11        [查看]  │
│ ▸ 生成 2 个图表 · 等待        [查看]  │
│                                     │
│ 建议 2（不影响交付）                 │
│ ▸ 本节 9521 字，建议 3000     [精简]  │
└─────────────────────────────────────┘
```

要点：

- 卡片只显示：**动词标题 + 位置 + 影响 + 一个动作**。证据原文点开再看。
- 「下一件」= 影响最高 + 动作最快的一件；不是简单按组排序。
- 系统任务不计入角标，避免"14 项"压垮用户；角标只显示需要用户处理的件数。

### 4.3 处理抽屉（点卡片打开，不离开正文）

以「定口径」为例：

```
┌ 处理：定「个人信息保护」的口径 ──────────────── × ┐
│ 位置：项目背景现状目标 › 项目现状描述 › 第 3 段      │
│ 原文：“…采集范围与操作记录机制待明确…”             │
│                                                    │
│ 为什么：这句话是交付前的口径承诺，评委会认为方案未定； │
│        不处理不能确认本章完成。                      │
│                                                    │
│ 选一种（可改）：                                    │
│  ○ 改为“拟按最小必要原则明确采集范围与操作记录…”     │
│  ○ 改为“采集范围将在实施阶段结合调研确定”            │
│  ○ 删除这句话                                       │
│  ○ 自己写：________________________________         │
│                                                    │
│ [应用并重新检查]        [只定位到原文]              │
└────────────────────────────────────────────────────┘
```

**动作完成后的反馈**：

```
已应用。重新检查中…
✓ 这条已消除（本章还需要你处理 2 件）
```

不通过时：

```
已改成“拟…”，但检查发现这句话还缺【来源】→ 新增一条待办（已高亮）
```

### 4.4 项目级「交付检查」（替代 96 章列表）

```
┌ 全书交付检查 ──────────────────────────────────── × ┐
│ 可交付度：3 / 5 项就绪                              │
│ 阻断导出：正文为空 114 章 · 未确认 124 章            │
│ 需要你：上传 2 类材料 · 定 6 处口径                  │
│                                                    │
│ ▸ 正文为空 114 章          [查看清单] [批量编写…]    │
│ ▸ 未确认 124 章            [查看清单]                │
│ ▸ 缺「业绩材料」96 章       [上传一次，全部生效]      │
│ ▸ 缺依据 38 条             [系统先查] [查看失败项]    │
└────────────────────────────────────────────────────┘
```

- 按**根因**汇总，不按章节列；章节只作展开后的定位。
- 批量动作必须显示代价（预计调用次数/时间）和范围。
- "114 章空"不是 114 条待办，是 1 个进度事实 + 1 个批量入口。

## 五、任务卡规范

### 5.1 统一 schema

```jsonc
{
  "id": "stable-hash",                 // 不用标题生成，避免改文案后忽略失效
  "scope": "chapter",                  // chapter | project
  "block_id": "s1.2.1.1",
  "category": "upload",                // upload | decide | confirm | system | suggestion
  "owner": "user",                     // user | system
  "title": "上传 1 份业绩/案例材料",     // 动词 + 对象，≤24 字
  "target": {                          // 定位，必填
    "section": "项目现状描述",
    "paragraph": 3,
    "quote": "…采集范围与操作记录机制待明确…",
    "char_start": 1280,
    "char_end": 1320
  },
  "why": "评分点「同类项目经验」要求 3 个业绩，当前只有 1 个",
  "impact": "completion_block",        // export_block | completion_block | quality | suggestion
  "impact_text": "不处理不能确认本章完成",
  "action": {
    "type": "upload_material",         // 见第六节
    "label": "上传",
    "payload": {"kind": "业绩材料", "formats": ["pdf", "docx", "png"], "bind_requirements": ["r3"]}
  },
  "options": [],                       // decide 专用：label + replacement + tradeoff
  "evidence": [{"label": "计划要求", "text": "…"}],
  "affected": [{"block_id": "s1.2.1.1"}, {"block_id": "s1.2.1.2"}],
  "dedupe_key": "material:业绩材料",
  "status": "open",                    // open | in_progress | resolved | ignored | snoozed
  "resolution": {"type": "upload|apply|confirm|system_done", "at": "…", "recheck": "passed|failed"}
}
```

### 5.2 标题模板（必须动词开头）

| 类型 | 差 | 好 |
|---|---|---|
| 上传 | 补 1 份「我方材料（数据/案例/业绩）」 | **上传 1 份业绩/案例材料** |
| 决定 | 口径未定：出现「待明确」 | **定「个人信息保护」的 1 处口径** |
| 决定 | 承诺强度：出现「保证」 | **改 1 句「保证」承诺** |
| 决定 | 项目角色口径不一致（牵头/参与/支撑混用） | **统一项目角色说法（牵头/参与/支撑）** |
| 确认 | 缺表格「政策依据映射表」 | **确认系统生成的「政策依据映射表」** |
| 确认 | 缺图示「趋势或现状对比图」 | **确认系统生成的「趋势对比图」** |
| 系统 | 依据核对：缺少AI与营销业务融合的64个… | **系统补 11 条依据（3/11）** |
| 建议 | 篇幅超建议（9521 / 3000 字） | **本节偏长：精简到约 3000 字（可选）** |
| 门槛 | 还有 3 项未满足完成条件 | **（删除，不是任务）** 顶部显示"完成条件还差 3 项" |

### 5.3 `impact` 文案（替代裸"阻塞"）

| impact | 显示文案 | 用户理解 |
|---|---|---|
| `export_block` | 不处理不能导出 | 硬门 |
| `completion_block` | 不处理不能确认完成 | 章级门 |
| `quality` | 影响评分/可读性，不影响交付 | 建议修 |
| `suggestion` | 可选优化 | 可忽略 |

- 不允许只显示"阻塞"两个字；必须带"阻塞什么"。
- 同一章内按 `impact` 排序：导出 > 确认完成 > 评分 > 建议；同级按动作耗时升序。

### 5.4 定位规则

- 文本类：`block_id + section + paragraph + char_start/end + quote`；点击后滚动到段落、选中原句、高亮 2 秒。
- 缺失类（缺图/表/占位）：定位到"应该出现的位置"（节末/占位处），并打开对应的生成/预览面板。
- 材料类：定位到使用处 + 打开上传；`affected` 列出所有受影响章节。
- 项目类：打开「交付检查」并展开对应根因，不直接跳第一章。
- **没有 locator 的条目不能进待办**，降级为"章节级提示"或回到检查器日志。

### 5.5 状态与生命周期

```
open ──动作──▶ in_progress ──复检通过──▶ resolved（消失）
  │                └──复检不通过──▶ open（显示"还差什么"）
  ├──稍后──▶ snoozed（到期回来）
  └──忽略──▶ ignored（服务端记录原因；导出时仍提示"你忽略了 N 项阻塞"）
```

- **忽略必须服务端化**：现在只写 localStorage，服务端导出仍拦截，用户以为消掉了。
- 忽略阻塞项要给二次确认："这条不处理，导出时会再次提醒；确定忽略？"
- 复检用内容 hash/计划版本判断；用户重写某节后自动重算，不残留已消除项。

## 六、动作设计（这是"看不懂"的核心）

### 6.1 上传

```
上传：业绩/案例材料
用在哪：本章「现状分析」第 2 段；同时影响 3 个章节
需要什么：合同 / 验收单 / 客户证明（PDF、Word、图片）
[选择文件] [从素材库选] [我没有，改用「拟实施」]
```

- 上传后：绑定到具体 requirement/段落 → **立即复检** → 通过则消失；不通过显示"已上传，但仍缺：…"。
- 同一 `dedupe_key` 的跨章缺口合并；上传一次默认应用到全部受影响章节，用户可取消勾选。
- "我没有"不是死路：提供降级动作（改用拟实施/标【待补充】），并说明后果。

### 6.2 决定

每条决策必须有**原句 + 2–3 个可选项 + 应用后效果**：

- 承诺强度：`保证` → `按合同约定…` / `通过…保障` / 删除。
- 口径未定：`待明确` → `改为拟实施…` / `保留但标【待确认】` / 删除该句 / 自己写。
- 角色不一致：按出现位置列 3 种说法，选一种统一；可"逐处确认"。
- 应用由**服务端按 locator 替换**（不要前端字符串匹配），写 revision 可撤销；替换后复检。

### 6.3 确认（系统做完，用户点头）

- 系统生成图表/补写后不直接塞正文，先给预览：
  `确认「政策依据映射表」` → 预览（表/图）→ [插入正文] [重新生成] [不要]。
- 这样"系统处理中"完成后自然转成一张"需要你确认"的卡，而不是无声改稿。

### 6.4 系统处理（用户不需要逐条点）

- 依据缺口：一个批次任务"补 11 条依据"，系统先查公开来源；查到的自动带入待确认，查不到的**才**转成用户卡"这条只能你提供"。
- 图表缺失：系统按计划生成，完成后转"确认"卡。
- 术语/引用/格式/数字：系统批量修，预览 diff，用户可撤销。
- 进度可见（3/11、失败 2 条），但**不占用待办角标**。

### 6.5 忽略 / 稍后

- 服务端存 `todo_states`（scope、reason、until、user），跨设备生效。
- 忽略阻塞项：二次确认 + 导出前汇总提醒；稍后：1 天/3 天/本章完成前。

### 6.6 批量与去重

- 同一 `dedupe_key`：项目级合并成一张卡（"缺业绩材料 · 影响 96 章"）。
- 同类格式问题：一张卡"统一 12 章的引用格式"。
- 空章节：项目级一个"批量编写空章节"入口，展开才是章节清单。
- 批量动作必须显示：影响范围、预计调用次数/时间、是否可撤销。

## 八、数据与接口改造

### 8.1 后端

- `todo_items` 统一 schema（第五节），新增：`title_action`、`locator`、`impact/impact_text`、`action_payload`、`options`、`affected`、`dedupe_key`、`resolution`。
- **文案层**：把检查器输出映射成任务文案（模板表），不要在检查函数里直接拼给用户看的句子；规则名只进 `source`。
- **locator 生成**：`todo_checks` 的正则匹配记录 `match.start/end`；交付物/缺口记录 `block_id + section + position`；没有 locator 的条目降级。
- **决策选项**：`pending`/`role` 也要生成 2–3 个候选；应用由服务端按 locator 替换并写 revision。
- **忽略/稍后服务端化**：新表 `todo_states(todo_id, scope, block_id, status, reason, until, updated_at)`。
- **复检**：动作完成后按 `source_version` 重算该章；`resolved` 仅在复检通过时写入。
- **项目聚合**：按 `dedupe_key` 合并跨章条目，返回"影响章节数"；不返回逐章重复项。
- **接口**：
  - `GET /api/projects/{pid}/todo?scope=chapter&block_id=…` → `{summary, sections:{need_user:[], system:[], suggestion:[]}}`
  - `GET /api/projects/{pid}/todo?scope=project` → 根因汇总 + 批量入口
  - `POST /api/todo/{id}/apply` → 决策替换（服务端 locator）
  - `POST /api/todo/{id}/upload` → 绑定材料并复检（或复用上传后 bind）
  - `POST /api/todo/{id}/ignore|snooze` → 记录原因/时间
  - `POST /api/todo/recheck` → 章节/项目重算

### 8.2 前端

- 右栏改成三区 + "下一件"；条目卡片按 5.2 模板；详情抽屉按 4.3。
- 点击卡片：打开抽屉 + 定位高亮；动作完成后局部刷新，不整页刷新。
- 角标只数 `owner=user`；系统任务显示进度点，不显示数字。
- 项目级用「交付检查」弹窗/面板，不再 96 行章节列表。
- 移除当前 `todo2Act` 的泛化分支（`go`/`autofix` 写文字）；按 `action.type` 分发。
- 忽略/稍后改为调接口；不再 localStorage。

## 十、验收（用项目 29 可测）

1. 打开 41828 章：不再出现「还有 3 项未满足完成条件」；顶部只显示"完成条件还差 3 项"。
2. 14 项 → 3 件需要你 + 2 件系统 + 2 条建议（数量可按数据，但不得有 summary 重复项）。
3. 每条标题以动词开头，≤24 字；不出现"口径未定：出现「…」""依据核对：缺少…"这类检查器句式。
4. 每条都有：位置（节/段/原句）、影响文案（不能只写"阻塞"）、一个主动作。
5. 点「上传」→ 打开针对该缺口的抽屉（说明材料类型/用途/格式）→ 上传后自动绑定并复检；通过则消失，不通过显示还差什么。
6. 点「选择」→ 抽屉里有原句 + 2–3 个选项；应用后正文替换、写 revision、复检。
7. 点「定位」→ 滚动到段落并高亮原句；不是只切章节。
8. 11 条依据缺口 → 1 个系统任务 + 失败项才转用户；用户不需要点 11 次。
9. 缺图/缺表 → 系统生成/预览/确认；不再触发"补写正文"。
10. 项目级：96 章/284 项 → 按根因汇总，不出现 96 行；"114 章空"有批量入口 + 代价提示。
11. 忽略 → 服务端记录；刷新/换设备仍生效；导出前仍提示"你忽略了 N 项阻塞"。
12. 动作完成后条目状态正确（resolved/仍存在），角标和计数同步；无控制台错误。

## 十一、待你确认（会影响方案取舍）

1. **系统任务默认自动跑，还是必须用户点"开始"？**（自动跑体验好，但会消耗模型/检索额度；我建议：依据检索自动跑，生成图表/补写按用户已点"编写整章"的上下文自动跑。）
2. **空章节是否提供"批量编写"？** 96/114 章规模下，逐章点不现实；批量必须显示预计调用次数/时间，并可中止。
3. **阻塞项允许忽略吗？** 建议允许，但服务端记录 + 导出前再次提示；否则用户会以为已经解决。
4. **「待办」是否改名「交付清单」？** 我倾向保留"待办"入口，标题写"距交付还差什么"，减少导航变化。

## 十二、一句话总结

用户不是不会改，是**待办在说检查器的语言，而不是用户的语言**。
把系统能做的收回系统、把用户要做的写成"动词 + 对象 + 位置 + 影响 + 一个动作"，
再把项目级从"章节列表"改成"根因 + 批量入口"，这个模块才真正可用。
