# 「待办」模块梳理与优化方案

> 用户判断：**进度**模块逻辑清晰（基于编写计划执行）；**待办**这块需要重新梳理。
> 初步想法：待办应补充"按章节写完之后还缺什么"，主要是 ①需要用户提供的内容 ②需要去挖掘的素材。
> 并追问：**其他还有没有需要补充的？**

---

## 一、先说结论

**现在的待办回答的是「计划做完没有」，它应该回答的是「能不能交」。**

这两个问题不一样：

| 问题 | 谁造成 | 谁来解 | 该不该挂成待办 |
|---|---|---|---|
| 计划做完没有 | 系统没写完/没引用/缺图 | **系统**（一键补写/补图/加引用）| ❌ 不该让用户干 |
| 能不能交 | 缺真实数据/缺资质/口径没定/承诺没确认 | **只能用户或外部** | ✅ 这才是待办 |

所以待办要按 **"谁来消除"** 重构，而不是按"内容/来源/篇幅/图表"这种文档维度。

**回答"还有没有其他需要补充的" —— 有，而且不止两类，是四类。**
除了你说的「你要给的」「要去挖的」，还有：「要你拍板的（决策）」「要你核对的（校对）」，
以及交付前的「硬门槛检查」。

## 二、现状：待办是怎么算出来的

### 2.1 数据来源（后端）

`writing_plans.chapter_plan()` 里拼出来的 `todo` 列表 + 两个独立清单：

| 来源 | 内容 | module |
|---|---|---|
| 交付物对比（计划 vs 正文）| 文字没写/不足、表/图未产出 | `content` / `figure` |
| 引用检查 | 正文引用处没有【来源】| `source` |
| 字数检查 | 超建议字数 | `budget` |
| 素材缺口 | 缺 N 份某类材料 | `material` |
| 依据核对（`chapter_gaps`）| 生成时记下的"缺少某依据" | 独立分组 |
| 素材缺口三分法（`material_gaps`）| 已有/公开可补/必须上传 | **素材页签**，不进待办 |

### 2.2 界面现状

```
待办 15
内容模块 2
  1 写清楚「背景」：不足（已写 6 / 目标 833 字）        [去补写]
  2 写清楚「现状」：不足（已写 6 / 目标 833 字）        [去补写]
来源模块 …
篇幅模块 …
图表模块 1
  缺 1 张「趋势对比图」                              [去生成]
依据核对 11
  · 缺少…测算依据原文                                  [去核对]
```

### 2.3 这套逻辑的四个问题

| # | 问题 | 说明 |
|---|---|---|
| 1 | **维度是"文档"，不是"责任"** | 用户看到"内容/来源/篇幅"，但真正要问的是"这活儿该谁干" |
| 2 | **把系统自己的活挂给了用户** | "字数不足""缺图"其实是系统没写够，应该一键补，而不是让用户手工写 |
| 3 | **缺"决策"与"校对"两类** | 口径选择、是否承诺时限、数字前后一致——目前完全没有 |
| 4 | **和素材页签重复** | 素材缺口在待办和素材里各出现一次（虽然待办已过滤 `material`，但语义上仍重复）|

## 三、新模型：待办 = 距离"可交付"还差什么

### 3.1 六类（按"谁来消除"分）

| 组 | 谁来解 | 典型条目 | 动作 | 是否阻塞交付 |
|---|---|---|---|---|
| **A 你要给的** | 用户上传/填写 | 「补 3 个同类项目业绩」「确认项目经理与联系方式」「提供 2024 年运维合同」| `上传` / `填写` | 常阻塞 |
| **B 系统去挖的** | 检索（系统代劳）| 「政策原文缺失：《…》第 X 条」「行业数据缺失：省级市场增速」| `一键带入检索` | 不阻塞 |
| **C 要你拍板的** | 用户决策 | 「口径：写"牵头"还是"参与"」「是否承诺 7×24 响应」「是否量化为指标」| 选项 A/B/自定义 | 常阻塞 |
| **D 要你核对的** | 用户确认（定位到原文）| 「数字与来源不一致：14.5 亿 vs 15 亿」「术语不统一：营销系统/营销管理系统」| `定位` / `接受建议` | 不阻塞 |
| **E 系统自己修的** | 系统自动 | 「本节缺一张对比图」「表格列数不一致」「表名缺失」| `一键修` | 不阻塞 |
| **F 交付门槛** | 系统检查 | 「未确认本章完成」「必备表缺失：政策依据映射表」「目录/页码未生成」| `去处理` | **阻塞导出** |

**关键取舍**
- **E 类不该占用户的注意力**：默认折叠成一句「系统可自动修复 3 项 · [一键修复]」，不做成待办行。
- **素材缺口只在「素材」页签**维护（三分法），待办里只出现它的**结论**：「缺 1 类材料（要你给）」+ 跳转链接，**不重复计数**。
- **F 类是唯一的"硬门"**：导出按钮上显示「还有 1 项阻塞」，导出前拦截并说明原因（不静默失败）。

### 3.2 每类条目的标准形态（同构，便于扫读）

```
① 标题（一句话说清缺什么）
② 证据（为什么这么判：计划要求 X / 正文只有 Y / 来源缺失）
③ 动作（一个主按钮 + 可能的次按钮）
④ 来源与级别（来自 计划/依据/审校/导出检查 · 阻塞/建议）
```

示例：

```
A  补 2 个同类项目业绩                            [上传]
   评分点「同类项目经验」要求 3 个，当前素材池 1 个
   来自：计划 · 阻塞交付

B  政策原文：《加快建设全国统一大市场的意见》         [一键检索]
   正文引用了该文件但未取到原文，无法核验条款
   来自：依据核对 · 不阻塞

C  本项目在集团中的角色：牵头 / 参与 / 支撑           [选: 牵头][选: 参与]
   正文出现两处不同表述（第 3 节/第 6 节）
   来自：一致性检查 · 阻塞交付

D  数字口径不一致：消费缴费 14.5 亿笔 vs 15 亿笔      [定位]
   来自：交叉核对 · 不阻塞
```

### 3.3 状态与生命周期

```
待处理 ──(做了动作)──▶ 处理中 ──(校验通过)──▶ 已消除
   └────────(用户点忽略)────────▶ 已忽略（记录原因，不再出现）
```

- 「已消除」不直接删：下一次重算时**校验式消除**（例如：字数够了、图生成了、数字统一了）
- 「已忽略」要记住（避免反复骚扰）

### 3.4 排序与计数

- 排序：**F（阻塞）> A（要你给）> C（要你定）> B（可检索）> D（校对）> E（自动，折叠）**
- 页签徽标计数：**只数 A~D + F**（E 折叠不计）
- 章头不再显示待办数（已在页签）——与之前定的一致

### 3.5 批量动作

| 组 | 批量 |
|---|---|
| B | 「全部带入检索」（一次搜多条）|
| E | 「一键修复全部」|
| D | 「定位到第一条」逐条走 |

## 四、六类各自的判定规则（可实现）

| 组 | 判定来源 | 说明 |
|---|---|---|
| A 你要给的 | 素材缺口里 `availability=upload` + 决策项里"需要事实"的 | 业绩/资质/合同/客户/内部数据/联系人 |
| B 系统去挖的 | 依据核对（`chapter_gaps`）中判断为"公开可得"的 + 素材缺口 `availability=public` | 政策/标准/行业数据/统计口径 |
| C 要你拍板的 | 一致性检查（跨节表述冲突）+ 高风险表述（承诺/极限词）+ 无依据断言 | 每类给 2~3 个候选项 |
| D 要你核对的 | 数字一致性（正文 vs 来源 vs 表）+ 术语表偏差 + 引用格式 | 定位到段落 |
| E 系统自己修的 | 交付物对比（字数/图表）+ `normalize_tables` + 表名/图注缺失 + 无效图块 | 可全自动 |
| F 交付门槛 | 必备章节/必备表/完成确认/目录页码/图片渲染检查 | 导出前拦截 |

## 五、和现有模块的分工（一个概念一个位置）

| 概念 | 位置 | 理由 |
|---|---|---|
| 写了没有、写了多少、要不要重写 | **进度** | 基于编写计划的执行 |
| 缺什么材料（三分法：已有/公开可补/必须上传）| **素材** | 材料本身的管理 |
| 谁来补齐材料、要不要拍板、对不对 | **待办** | 责任与决策 |
| 质量问题的正式意见（评分/失分点）| **评审阶段** | 不进编写页 |
| 系统能自动修的 | **待办折叠区**（一键修复）| 不占用户注意力 |

## 六、验收标准

1. 待办按 **A/B/C/D/F** 五组呈现（E 折叠为「可自动修复 N 项」）
2. 每条有：标题 + 证据 + 一个主动作 + 来源与级别
3. 素材类**不重复**：待办只出现结论 + 跳素材；素材页签仍用三分法
4. 「已消除」是校验式（做了动作、重算通过才消失）；「已忽略」记住不复发
5. B 组支持「全部带入检索」；E 组支持「一键修复全部」
6. F 组阻塞导出：导出按钮显示「还有 N 项阻塞」，点击给出原因清单
7. 页签徽标只数 A~D + F
8. 同一章的待办在"重写某节"后自动重算（不残留已消除项）
9. 无控制台错误；自检覆盖 1/3/5/6

## 七、实施拆分

| 步骤 | 内容 | 量 |
|---|---|---|
| T1 | 后端：待办统一 schema（group/source/severity/evidence/action/status）| 中 |
| T2 | 前端：五组渲染 + 每类条目形态（标题/证据/动作）| 中 |
| T3 | A/B 组接入（素材缺口三分法映射 + 依据核对分类）| 中 |
| T4 | C/D 组（一致性检查 + 数字/术语核对）—— 新增能力 | 大 |
| T5 | F 组（交付门槛检查 + 导出拦截）| 中 |
| T6 | E 组折叠 + 一键修复（复用 normalize/补表名/补图）| 中 |
| T7 | 状态机（已消除校验、已忽略记忆）+ 自检 | 小 |

**建议顺序**：T1 → T2 → T3（把你说的两类先落地）→ T5（交付门槛，价值高）→ T6 → T4。
