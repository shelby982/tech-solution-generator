# 架构分析：以「评分点」为主线的拆解 → 编写 → 审核

> 用户口径（原话）：
> 「从架构上面分析一下当前这两块的逻辑，目前拆分完评分点之后后续审核按道理也是按照评分点审核，
>  另外素材库这部分应该是按照对应章节到时候补充编写内容时需要，有些内容是不需要素材的，
>  这块应该在编写时按需补充，请按照此逻辑详细分析，要求界面能够简单、逻辑清晰」

---

## 一、两个红框在做什么（现状）

| 红框 | 元素 | 现在显示什么 | 数据来自 |
|---|---|---|---|
| 1 | 顶部共享壳状态条 `#workspace-status` | 「第 N 轮 · 阶段」+「正文 0/530 · 已通过 0 · 待处理 0」+ 处理待办/版本记录/运行详情 | `workspace.js renderChrome()`（按**章节**汇总） |
| 2 | 页面状态栏 `#status-bar` | 「已解析 530 个章节，可继续提炼」+ `0/530 模块 · 0%` + 重新提炼/重新拆分目录/继续提炼 | `mode-outline.js`（按**章节**进度） |

**结论**：两块都在表达"运行进度"，**信息重叠**（一个说"正文 0/530"，一个说"0/530 模块"），
而且**都是"章节维度"**——不是评分点维度。这正是与你的口径冲突的地方：
**后面的审核是按评分点给分的**，但整个进度/状态表达只有章节数。

---

## 二、当前流程（以章节为中心）

```
拆分评分点 → 待确认 → 产物（目录）
   → 素材匹配（全量：把素材切成 chunk，挨个挂到每一节）
   → 逐节提炼（每章一次模型调用，产出 8 字段：key_points / score_items /
                veto_items / evidence_required / …）
   → 逐章编写（8 字段作为写作约束）
   → 逐章评审（王安石技术评审 / 包拯合规评审，逐 block）
   → 报告（覆盖矩阵）
```

问题：
1. **审核粒度错位**：得分是按**评分点**（一条评审项 5 分、10 分…）给的，但评审结果是
   **逐章节**存的 —— 报告里"这一章写得不错"回答不了"**这个评分点能不能拿满分**"。
2. **素材全量预匹配**：530 节 × N 个素材切片，提前把所有章节都挂满素材。
   - 很多章节**根本不需要素材**（写"项目理解""技术方案思路"不需要企业资质扫描件）；
   - 真正需要的是**举证类**章节（业绩、证书、财务），而这些需求其实**已经算出来了**
     —— 逐节提炼的 8 字段里就有 `evidence_required`（投标方需提供的证明材料）。
   - 也就是说：**"需不需要素材、需要什么"是已知的，只是没有被用来驱动按需挂载。**

## 三、目标架构（以「评分点」为主线）

```
① 拆分评审点（商务/技术 + 技术规范书）
      ↓
② 待确认（范围 / 类别 / 主题归属）
      ↓
③ 产物：目录（评分点 → 章节骨架） + 技术与评分点映射矩阵
      ↓
④ 编写（逐章）
     · 每章先看它承载哪个评分点、该评分点的得分口径是什么
     · 该章需要什么举证 → 看提炼出来的 evidence_required
     · 需要素材时**当场按需挂载**；不需要就不挂（避免噪声与成本）
      ↓
⑤ 审核（**按评分点**）
     · 一个评分点一行：分值 / 承载章节 / 满足度 / 缺失得分要点 / 举证是否齐备
     · 点开看该评分点下每一章的评审明细
```

### 数据模型：已经有的 vs 缺的

| 需要的东西 | 现状 | 结论 |
|---|---|---|
| 章节 → 评分点 的关联 | `blocks.review_point_ids`、`criterion_text`、`score_weight` | **字段已有**（当前库里为空，因为上次运行中断） |
| 审核的评分点口径 | `reviews.criterion_text / satisfied / covered_points / missing_points` | **字段已有**（按 block 存，口径是评分点） |
| 评分点级风险聚合 | `services/scoring_risk.py`（per review_point 汇总 risk/缺失） | **已有基础**，可直接做审核页的数据源 |
| 编写时的"需要什么举证" | 逐节提炼 8 字段里的 `evidence_required` | **已有**（只是没用在素材上） |
| 评分点级**审核结论**（谁写、满足度、举证齐否、可否重写） | 只有 block 级 | **缺**（聚合 + 状态机） |
| 素材的**按需**入口 | 只有"素材匹配"全量流程 | **缺**（按章节/按评分点检索素材的接口 + UI） |
| 章节"是否需要素材"标记 | 无显式标记（可由 `evidence_required` 是否为空推导） | **缺**（推导即可，不必新增列） |

## 四、界面提案（简单、逻辑清晰）

### 一条主线，五个阶段

```
拆分评审点 → 待确认 → 产物 → 编写 → 审核
```

- 现在已实现的：① ② ③（左侧竖条三阶段 + 右侧切换）
- 后续补：④ 编写、⑤ 审核，**沿用同一套"左侧阶段 + 右侧内容"**，不要另起一套导航

### 编写页（按章）

```
┌ 章节：技术方案 › 技术方案可行性            [上一个] [下一个] ┐
│ 本章回应：技术方案可行性（12 分）                             │
│ 得分口径：1…得 5 分；2…每处扣 1 分；本项最低 0 分             │  ← 评分点口径常驻
│ 需提供举证：项目合同关键页 / 服务内容页（来自 evidence_required）│  ← 一眼知道要不要素材
├──────────────────────────────────────────────────────────────┤
│ 正文编辑区                                                    │
│                                              [按需插入素材 ▸] │  ← 默认收起，需要时才开
└──────────────────────────────────────────────────────────────┘
```
**素材面板默认收起**：点「按需插入素材」才展开检索；本章 `evidence_required` 为空时，
直接显示「本章无需强制举证」，用户不必去素材库翻。

### 审核页（按评分点）

```
评分点                             分值  章节  满足度   缺失要点        举证
技术方案可行性                     12    1     部分满足  第 2 条扣分项…  齐备
财务状况 › 营业净利率              10    1     满足      —              缺审计报告
项目业绩 › 项目业绩                30    3     部分满足  缺 2 个合同…    缺合同关键页
```
点一行 → 展开该评分点下**每章**的评审明细（现有 block 级 reviews）。

### 两条状态栏合并成一条

现在顶部两条（红框 1、2）表达同一件事。合并为**一条**：
```
当前阶段 ｜ 一个主动作 ｜ 进度（按阶段的口径：拆分=材料/目录；编写=章节；审核=评分点）
```
并且进度口径**随阶段变**：拆分阶段说"已解析 N 章"，编写阶段说"已写 M/N 章"，
审核阶段说"已审 K/M 个评分点"——而不是永远只报章节数。

## 五、落地顺序（建议）

| # | 事项 | 风险 | 说明 |
|---|---|---|---|
| 1 | **合并两条状态栏**为一条 | 低 | 纯前端；解决"信息重叠" |
| 2 | **审核页改为按评分点** | 中 | 数据基本齐（`reviews` + `scoring_risk`），主要是聚合与展示 |
| 3 | **素材改为按需**（编写时插入） | 中 | 新增"按章节检索素材"的接口；全量匹配降级为可选项 |
| 4 | **章节举证提示**（evidence_required 驱动） | 低 | 纯展示；"本章无需强制举证"能省掉大量无谓操作 |
