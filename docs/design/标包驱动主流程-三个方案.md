# 标包驱动主流程：三个优化方案

> 诊断见 [标包驱动主流程-诊断.md](标包驱动主流程-诊断.md)。
> 三个方案的**共同前提**：标包是整条链路的根 —— 招标文件 → 标包 → 该标包的商务/技术评分点
> → 结合该标包的技术规范书 → 应答目录 → 编写 → 评审。

---

## 方案 1「标包工作台」——标包是**空间**

### 一句话
把标包做成**工作区**：选一个标包进去，五步只对这个标包生效；切换标包 = 换一整套内容。

### 信息架构
```
项目
└─ 标包切换器（顶部常驻）
   ├─ 标的1 / 标包2 · 高可靠技术专题      ← 当前工作区
   │    ├─ 本标包文件（招标文件 / 技术规范书）  [＋ 添加文件]
   │    └─ 五步：①评分点 ②待确认 ③产物 ④编写 ⑤评审
   ├─ 标的1 / 标包3
   └─ ＋ 新建标包
```

### 用户流程
1. 进项目 → 若还没有标包：空白态引导「上传招标文件 → 解析标包」
2. 标包解析出来 → 顶部出现标包标签页，默认进第一个
3. 在该标包工作区里上传/归属文件（默认归当前标包；也可从"未归属"里拉进来）
4. 走完五步；切到另一个标包 → **完全另一套**文件/评分点/目录/正文/评审

### 关键界面
- 顶部第二行：标包标签页（当前实心蓝、其他描边、末尾虚线「＋ 新建标包」）
- 标签页下一行说明：每个标包是独立的一份应答
- 当前标包上下文头：`当前标包：标的1/标包2 · …` + 一行元信息（商务 8 / 技术 8 / 规范书 1 份 / 正文 12-38 章）
- 上传条属于工作区内部，视觉上明确"这些文件只属于本标包"

### 数据模型改动
| 改动 | 说明 |
|---|---|
| `project_packages` 扩展 | 现在只有"解析事实"（target/package_no/name/confidence/evidence）；需要加**用户确认状态**、显示名、排序 |
| `workflow_runs.target/package_no` | 已有 ✅ —— 每个标包一条运行 |
| `material_packages` | 已有（文件↔标包多对多）✅ |
| `review_points.package_no` | 已有 ✅ |

**结论**：后端地基基本齐了，主要工作在**前端 IA 改造**与"进标包时绑定 scope"。

### 迁移与风险
- 现有 41 条运行中只有 1 条有归属 → 其余按「未分配」处理，首次进入时提示归属
- 风险：五步从"项目级"变"标包级"，所有读数据的入口都要带 scope，改动面大

### 验收
1. 切换标包 → 文件 / 评分点 / 目录 / 正文 / 评审**全部只属于该标包**
2. 在标包 A 里上传的文件，切到标包 B 后**不可见**（除非显式归属到 B）
3. 新建标包后，它的五步从零开始，不影响其他标包

### 改造量
**最大**（前端 IA + scope 贯穿；天级）

## 方案 2「准备阶段 + 标包矩阵」——标包是**进度**

### 一句话
在现有五步**之前**加一个显式的「准备」区（上传 → 解析招标文件 → 逐标包拆评分点 → 就绪），
再用一张矩阵看每个标包走到哪一步。

### 信息架构
```
项目
├─【准备】① 上传文件 → ② 解析招标文件（拆标包）→ ③ 逐标包拆评分点（商务+技术）→ ④ 就绪
├─【标包矩阵】行 = 标包，列 = 文件 / 商务评分点 / 技术评分点 / 目录 / 正文 / 评审
└─ 点任意标包 → 进入该标包的五步
```

### 用户流程
1. 上传文件 → 点「解析招标文件」→ 系统拆出标包（带原文出处）→ 用户在准备区确认/改名/合并
2. 对每个标包：点「拆评分点」→ 分别得到商务、技术两套评分点（来源 = 该标包的评分表 + 该标包的技术规范书）
3. 矩阵实时反映进度；缺项（如"缺商务评分点"）高亮
4. 点进入 → 该标包的五步

### 关键界面
- 「准备」卡片：横向 4 步流水线（①完成 ②当前 ③待进行 ④待进行）
- 「标包进度」矩阵：每格是状态 chip（✅ 完成 / ⏳ 进行中 / ⚠ 缺项 / — 未开始）
- 卡片脚注：准备完成后，点任意标包进入五步

### 数据模型改动
| 改动 | 说明 |
|---|---|
| 标包阶段状态 | 可由现有数据**推导**（文件数 / 评分点数 / 目录状态 / 正文章数 / 评审）→ 先做视图，不急着建表 |
| `project_packages` 同方案 1 | 需要"用户确认过的标包清单" |
| 评分点按标包+类别 | `review_points.package_no` + `category` 已有 ✅；需保证**商务也落库**（已有"一键对齐"✅） |

### 迁移与风险
- 五步内部**不用改**（门槛最低的改造）
- 风险：多一层"准备"，用户需理解"准备完才能进五步"；矩阵列多时在窄屏会挤

### 验收
1. 新增一个标包 → 矩阵立刻多一行，状态为「未解析」
2. 某标包缺商务评分点 → 矩阵对应格显示 ⚠ 而不是空白
3. 点矩阵任意格 → 进入该标包对应阶段，且内容只属该标包

### 改造量
**中**（新增准备区 + 矩阵；五步不动）

## 方案 3「文件驱动」——标包是**文件派生物**

### 一句话
以文件为锚：每份招标文件解析后**就地展开**它包含的标包；每个标包带自己的进度；
技术规范书**明确挂到标包**（补上现在完全缺失的关系）。

### 信息架构
```
项目
├─ 材料条：【招标文件.pdf】● 已解析  → 展开：标的1/标包2 · 标的1/标包3 · 标的2/标包1
│           【技术规范书.docx】● 已解析 → 挂到：[标的1 标包2 ▾]
└─ 每个标包：评分点(商务/技术) · 目录 · 正文 · 评审  → [进入 ›]
```

### 用户流程
1. 上传招标文件 → 点「解析招标文件」→ 文件卡**就地展开**它包含的标包
2. 每个标包子项显示：商务 N 个 / 技术 M 个 · 目录状态 · 正文章数 → 点「进入」做五步
3. 上传技术规范书 → 在文件卡上选「挂到标包」（可挂多个，默认一个）
4. 标包尚未拆评分点时，子项显示「拆评分点 ›」直接可点

### 关键界面
- 文件卡（含状态）→ 卡片内缩进的标包子卡（这就是本次要补的"文件→标包"关系）
- 文件头下一句：从这份招标文件里解析出 3 个标包
- 技术规范书卡内一行：挂到标包 [标的1 标包2 ▾] + 说明"一份技术规范书通常只属于一个标包"

### 数据模型改动
| 改动 | 说明 |
|---|---|
| `project_packages.source_material_ids` | **已有** ✅（哪个标包来自哪些文件）→ 界面直接用它做"文件展开标包" |
| `material_packages`（文件↔标包） | **已有** ✅ → 技术规范书挂标包直接落这张表 |
| 标包唯一性 | `project_packages` 主键 (project_id, target, package_no) ✅ → 跨文件同名标包天然合并 |
| `materials.package_no` | **不加**（保持多对多；一个文件可属多个标包）✅ |

**结论**：这个方案的**数据层已经就绪**，主要是把它**呈现出来**。

### 迁移与风险
- 风险最低：不引入新概念，只是把已有的 `project_packages` / `material_packages` 显示出来
- 风险点：标包特别多时文件卡会很长（需要折叠/搜索）；标包名仍需用户确认（不编造）

### 验收
1. 上传一份含 3 个标包的招标文件 → 解析后**立刻出现 3 个子项**，各自带评分点数
2. 技术规范书挂到标包 2 → 该标包的工作区能看到它；挂到多个 → 都可见
3. 标包子项点进入 → 评分点/目录/正文只属该标包

### 改造量
**最小**（数据层已就绪；主要改上传区与进入逻辑）

## 对比表

| | 方案 1 空间 | 方案 2 进度 | 方案 3 文件派生 |
|---|---|---|---|
| 标包的心智 | 工作区 | 进度行 | 文件的子项 |
| 入口 | 顶部标签页 | 矩阵格子 | 文件卡展开 |
| 五步是否改 | **要改**（降到标包级） | 不改 | 不改（进入时绑定 scope） |
| 数据改动 | 中（确认状态/排序） | 中（阶段状态，可推导） | **几乎为零**（已有字段够用） |
| 改造量 | 大 | 中 | **小** |
| 最贴合用户描述 | 概念上最正 | **顺序上最贴合** | **场景上最贴合**（一份文件多标包） |
| 最大风险 | 改动面大、要迁移 41 条运行 | 多一层准备界面 | 标包多时列表长 |
| 适合 | 长期把"标包独立推进"作为骨架 | 先要全局可见、不想推翻五步 | 想尽快见效、风险最低 |

### 一句话建议
**先做方案 3（风险最低、当天可见效、还顺手补上"技术规范书挂标包"这个完全缺失的关系），
把方案 2 的矩阵作为它的"全局视图"叠加，方案 1 作为长期骨架。**
三个不是互斥的：3 是入口，2 是总览，1 是终局。
