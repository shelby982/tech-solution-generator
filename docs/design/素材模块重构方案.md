# 素材模块重构方案：上传/搜索 → 解析 → 确认 → 素材库 → 按章节应用

> 用户口径（本次）：
> 1. **两路来源都要"解析 + 用户确认"**：上传的参考文件、联网搜到的公开素材；确认后方可应用。
> 2. **编写过程中产生的素材需求**：让用户直接上传，走同一套上传流程。
> 3. **解耦**："上传与解析"是独立模块；只有"解析完成 + 用户确认引用"的才是真素材；素材库确定后，编写时**按章节挑素材**完善内容。
>
> 本文先给体系架构 + 交互逻辑，确认后再动代码。

---

## 一、现在为什么乱（对着截图逐条对）

当前素材页签里混着 5 类东西，没有统一状态机：

| 界面上看到的 | 问题 |
|---|---|
| 「素材缺口 / 没有缺口 / 计划要求的素材已齐」 | 这是**计划**的素材需求，不是素材本身 |
| 「外部依据 2 / 已引用 0 · 未引用 2」+ 每条的「片段 40 / 打开原文 / 未引用」| 搜索结果是**直接可用**的，没有"确认"这一步 |
| 「这些来源还没被正文引用：重新生成本章即可用」 | 把"引用"和"生成"绑在一起，逻辑不清 |
| 「本章素材 0 / 上传素材」 | 上传后**直接入库**，没有解析结果的确认 |
| 底部「已关联素材与外部依据」折叠 | 又一套列表，和上面重复 |

**根因**：没有把"**原料 → 解析片段 → 已确认素材 → 章节引用**"这四级分开，全都塞在一个页签里。

## 二、目标模型：四级数据 + 三态流转

```
① 原料 Source        上传文件 / 搜索命中的网页
        │  解析（段落级，带页码/URL/位置）
        ▼
② 解析片段 Chunk     文件段落、网页正文片段（可能有几十条）
        │  用户确认（逐条勾选，可批量/过滤）
        ▼
③ 已确认素材 Material 只有确认过的片段才算"素材"——**唯一可引用对象**
        │  按章节选择应用
        ▼
④ 引用关系 Binding   素材 ↔ 章节/小节 + 正文里的【来源：…】
```

### 状态机（两路来源统一）

```
uploaded / fetched        ──解析──▶  parsed
parsed                    ──用户确认──▶  confirmed   ← 只有这里能进素材库、能被编写使用
parsed                    ──用户丢弃──▶  rejected
confirmed                 ──被某章引用──▶  used（可多章）
```

**关键约束（写进代码）**
- 编写引擎**只读 `confirmed` 的素材**；`parsed` 未确认的一律不注入提示词。
- 素材库里的"素材"= 已确认片段的集合；`parsed` 的进"待确认"视图。
- 「素材缺口」从素材页签移走（回计划面板/编写页签），素材页签只说"素材"。

## 三、模块架构

```
素材（独立一级模块）
├── 素材库       已确认素材：列表 / 检索 / 按类型 / 被哪些章节引用
├── 待确认       解析完待你确认的片段（两路来源都在这里）
├── 上传解析     上传文件 → 解析进度 → 结果预览
└── 搜索入库     联网搜索 → 结果片段 → 勾选确认

编写（章节内）
├── 本章素材     已经应用到本章的素材（可移除）
└── 选素材       从素材库按"本章需求"推荐 + 搜索，勾选即应用（插入引用/段落）
```

**解耦点**：
- 「上传/搜索 + 解析」完全不依赖章节；
- 「应用到章节」只依赖"已确认素材"；
- 编写过程中缺材料 → 直接在章节内触发上传，**落回素材模块**的"待确认"，确认后回到章节应用。

## 四、交互逻辑（四条主流程）

### 流程 A：上传参考文件 → 确认

```
拖入/选择文件
  ↓
解析（页/段，显示进度）→ 得到 N 个片段
  ↓
「待确认」视图：
   ┌ 文件：XX招标文件.pdf · 解析出 38 段 · 已选 6
   │  ☑ 第 12 页 · 「本项目须在验收阶段提交…」      [看原文]
   │  ☐ 第 13 页 · 「等级保护三级要求…」
   │  （支持按关键词筛选、只看含数字/条款的段、全选当页）
   ↓ 点「确认引用 6 段」
素材库 +6（类型：招标文件；可标注用途：政策依据/技术条款/现状数据）
```

**要点**：确认以"片段"为单位（不是整份文件）——这样引用才精准、正文【来源】才能落到页/段。

### 流程 B：联网搜索 → 确认

```
输入检索词（或由"章节依据缺口"自动带入）
  ↓
结果列表（标题/来源/日期/摘要）→ 展开正文片段
  ↓ 勾选需要的片段（可多选）
「确认引用」
素材库 +n（类型：公开来源；带 URL/标题/发布时间）
```

**要点**：搜索到的**默认是待确认**（不能直接进库）；确认后才可被编写使用。

### 流程 C：编写时按章节选素材

```
章节「编写」页签 → 本章素材
  ↓ 点「选素材」
推荐（按本章节标题/要点/依据关键词匹配已确认素材） + 搜索框
  ↓ 勾选 → [应用到本章]
  ├ 插入引用：【来源：XXX（2025）】
  ├ 插入段落：把素材原文作为引用句/数据依据
  └ 或仅"记为本节素材"，生成时作为上下文注入（不插入正文）
```

### 流程 D：编写中缺材料 → 就地补

```
编写页签/素材页签提示「本节缺业绩举证」
  ↓ [上传]
走流程 A（文件上传 + 解析 + 确认）
  ↓ 确认后自动回到本节的「本章素材」，勾选应用即可
```

## 五、界面结构（素材模块）

```
素材
┌ 概览条：已确认 42 · 待确认 17 · 本章已用 6 ──────────────┐
├ 分段切换：[素材库] [待确认 17] [上传/搜索]
├───────────────────────────────────────────────────────┤
│ 素材库                                              [搜索] │
│  类型：全部 / 招标文件 / 公开来源 / 我方材料 / 内部数据      │
│  ┌ 卡片：标题 · 类型 · 位置（第 12 页 / URL）              │
│  │       摘要（可展开原文）                               │
│  │       被引用：3 章（项目背景现状目标 …）  [应用/移除]     │
│  └                                                      │
├ 待确认：按来源文件/搜索批次分组，逐段勾选 → [确认引用] [丢弃] │

```

章节内（编写页签）：
```
本章素材 6        [选素材]
· 招标文件 · 第 12 页「本项目须在验收阶段…」  [移除]
· 公开来源 · 国家发改委（2026-10-10）「…」     [移除]
本章缺：业绩举证（招标要求提供）→ [上传] → 落回素材模块待确认
```

## 六、数据模型（新增/改造）

```sql
-- ① 原料：一份上传文件或一次搜索批次
sources(
  id, project_id, kind ('file'|'search'), title, url, file_path,
  status ('parsed'|'failed'), meta_json, created_at)

-- ② 解析片段（确认的对象）
source_chunks(
  id, source_id, ordinal, page_no, locator,        -- 位置：页码/URL+锚点
  text, tokens, tags_json,                          -- tags: 政策/条款/数据/资质
  status ('pending'|'confirmed'|'rejected'),
  confirmed_by, confirmed_at)

-- ③ 素材（= 已确认片段的视图；也可直接引用 chunk）
materials(
  id, project_id, chunk_id, kind,                   -- 招标文件/公开来源/我方材料/内部数据
  title, summary, source_label,                     -- 正文【来源：…】用的标签
  status ('active'|'archived'), created_at)

-- ④ 章节引用（原文里已有 chapter_materials，改造）
material_bindings(
  id, project_id, block_id, section, material_id,
  mode ('cite'|'context'|'paste'),                  -- 插入引用 / 仅作上下文 / 粘贴原文
  created_at)
```

迁移：现有 `citations`（搜索）→ `sources(kind=search)` + `source_chunks`；`materials`（上传）→ `sources(kind=file)` + `source_chunks`；`chapter_materials` → `material_bindings`。
旧的"已关联/未引用"状态改用 `material_bindings` 计算。

## 七、与编写链路的接口

| 环节 | 用到的素材 |
|---|---|
| 生成某节 | 只注入：`confirmed` 且绑定到本章（或全项目通用）的素材 `text` + `source_label` |
| 生成后校验 | 正文里的【来源：X】必须能匹配到某个已确认素材的 `source_label`，否则提示（不阻断）|
| 交付门 | 不再检查"素材缺口"；只检查"引用是否有据" |

## 八、分期与验收

| 期 | 内容 | 验收 |
|---|---|---|
| **M1** | 上传 → 解析 → 待确认列表（逐段勾选）→ 素材库 | 上传一份 PDF，能勾选 6 段确认，素材库出现 6 条，未确认的进"待确认" |
| **M2** | 搜索 → 片段确认入库 | 搜索一次，确认 2 段，素材库出现 2 条带 URL |
| **M3** | 章节内「选素材」+ 应用（引用/上下文/粘贴）| 章节挑 2 条素材 → 正文出现【来源：…】或上下文注入 → 「本章素材 2」 |
| **M4** | 编写中缺材料 → 就地上传 → 回流确认 | 从章节点上传 → 素材模块待确认 → 确认后本章可用 |
| **M5** | 编写引擎只读已确认素材；引用可追溯 | 未确认素材**不会**进入生成提示词（可用日志证明）|

## 九、需要你拍板的 3 件事

1. **确认粒度**：按"片段"确认（推荐，引用精准），还是按"整份文件"确认（省事、引用粗）？
2. **素材是否分项目级/章节级**：我倾向"项目级素材库 + 章节引用关系"，即一份素材可被多章引用。
3. **素材页签放在哪**：作为右栏一级页签（当前），还是左侧导航独立"素材"页面（更适合以后管理几十份文件）？
