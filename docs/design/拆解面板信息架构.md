# 拆解面板信息架构（分析 + 方案）

> 场景（用户口径）：**基于招标文件的评分点，结合技术规范书，输出整体的应答目录。**
> 本文只做分析与设计，不改代码。

---

## 一、先把"数据从哪来"查清楚

代码事实（`services/split_report.py` 模块说明、`agents/zhang_heng.py` 派生流程、`infra/parser/*`）：

| 面板上看到的东西 | 来自哪份文件 | 是否天然按标包 | 现状 |
|---|---|---|---|
| **评分点**（评分因素/详细评审项/分值/类别/评分口径） | **招标文件**的评分表 | ✅ 标包 × 类别 | 已入库，带 `package_no` + `category` |
| **评分单元**（L1 评分因素 → L2 详细评审项 → L3 细项） | **招标文件**评分表的**层级展开**（不是技术规范书） | ✅ 随"本次生成目录"的标包 | 只有当前那一次派生的结果 |
| **技术要求矩阵**（按主题分组） | **技术规范书** | ⚠️ 抽取时按标包筛过（`package_id` + 交付物表跨包过滤），**但入库丢了标包与来源文件** | `spec_requirements` 表**没有** `package_no` 列；`source_file` 有一列但**恒为空**（`TechRequirement` 无此字段） |
| **映射矩阵**（评分点 ↔ 要求） | 上面两者的**连接**（通过章节链上的 id） | 依赖当前标包的目录 | 只在"该标包目录已生成"后才有内容 |
| **应答目录**（章节树） | 骨架 = 招标文件评分点；挂载物 = 技术规范书要求 | ✅ 标包 × 类别 | 每次生成覆盖前一版 |
| **覆盖率** | 目录 vs 评分点/分值/要求 | 同上 | — |

**结论**：`评分单元与技术要求映射矩阵` 不是一类东西：

- **评分单元 → 招标文件**（评分表的层级）
- **技术要求矩阵 → 技术规范书**
- **映射矩阵 → 两者的连接**

### 回答你的两个判断

**1. 能不能按标包做成下拉？**
- **评分点 / 评分单元 / 目录 / 覆盖率 / 映射**：能，而且**本来就是**按（标包 × 类别）的。
- **技术要求**：**能，但要先补两件事**——① 抽取结果落库时保留 `package_no` 与 `source_file`；② 定义"技术规范书是全项目一份"时的归属规则（下面 §四）。

**2. 并列的逻辑有没有问题？**
有，而且是当前"看不懂"的根因：**同一排标签页混了三种不同性质的数据**——
按标包的一次派生结果（评分单元/映射）、全项目共享的输入（技术要求）、以及待办（待确认）。
它们的"范围"不一样，却并排展示，用户无法判断"我现在看的是哪个标包、这是输入还是产物"。

## 二、当前 UI 的三个结构性问题

| # | 问题 | 表现 |
|---|---|---|
| 1 | **范围不统一却并列** | 矩阵列 3 个标包，明细页却只有当前标包（用户已反馈） |
| 2 | **切换标包没有入口** | 只能回「① 拆解结果」重选 → 重新生成，视角跳变、旧目录被换掉 |
| 3 | **信息混层** | 输入（依据）、产物（目录/覆盖率）、待办（待确认）挤在一条标签线上，并列关系掩盖了因果关系 |

## 三、方案：把"并列"改成"流水线 + 范围前置"

**心智模型**：输入 A（招标文件评分点）＋ 输入 B（技术规范书要求）→ 结合 → 产物（本标包应答目录）→ 自检（覆盖率/映射）

### 布局

```
┌─ 范围（决定下面所有内容）──────────────────────────────────────────┐
│ 标包 [标的1 / 标包2 ▾]        类别 ☑技术  ☐商务  ☐报价              │
│ 当前目录 = 标的1/标包2 · 技术 · 100 分   [按此范围生成 / 重新生成目录]  │
└──────────────────────────────────────────────────────────────────┘
┌─ 依据（只读输入；各自写清来源）────────────────────────────────────┐
│ ① 招标文件 · 本标包评分点                     13 个 · 合计 100 分   │
│    按「评分因素 → 详细评审项」表格（分值 / 类别 / 评分口径）           │
│ ② 技术规范书 · 技术要求        本标包相关 153 条 / 全项目共享 M 条    │
│    按主题分组；每条标注来源文件与「本标包 / 共享」                     │
└──────────────────────────────────────────────────────────────────┘
┌─ 产物（本标包目录的派生结果）──────────────────────────────────────┐
│ ③ 应答目录结构   评分因素 → 详细评审项 → 细项（每项挂了几条要求）      │
│ ④ 覆盖率自检     评分点 x/y · 分值 x/y · 要求 x/y                   │
│ ⑤ 映射矩阵       评分点 ↔ 要求 ↔ 章节                               │
└──────────────────────────────────────────────────────────────────┘
┌─ 待确认（只有需要你决定的事）──────────────────────────────────────┐
│ 投标范围确认 · 类别确认 · 主题归属（下拉选择章节）                    │
└──────────────────────────────────────────────────────────────────┘
```

### 关键规则（防止再次"对不上"）

1. **范围前置、全局可见**：标包 + 类别选择器固定在顶部，下方所有内容的范围都由它决定，每块标题都带上当前范围（如「本标包（标的1/标包2 · 技术）」）。
2. **切换标包 = 切"查看视角"，不自动重跑**：
   - 若该（标包×类别）**已生成过目录** → 直接展示它的目录/评分单元/映射（需要存下每份派生结果，见 §四-3）。
   - 若**没生成过** → 明确空态：「该标包还没生成目录（评分点已拆出 13 个），点『按此范围生成目录』」，**绝不能**继续显示上一个标包的目录。
3. **技术规范书侧标"共享池"**：给出「本标包相关 / 全项目」两个数字 + 来源文件，解释"为什么会有别的要求"。
4. **输入与产物分区**：输入是只读依据（灰底），产物是派生结果（白底、可操作），不要混在一排标签页里。

## 四、要落地必须先补的三个数据缺口

| # | 缺口 | 现状证据 | 修法 |
|---|---|---|---|
| 1 | 技术要求**没有标包** | `spec_requirements` 表无 `package_no` 列（实测） | 加列并在落库时写入（`TechRequirement.package_id` 已有值，只是没落库） |
| 2 | 技术要求**没有来源文件** | `source_file` 列存在但实测**全空**：`TechRequirement` 数据类没有这个字段，落库取 `getattr(r,"source_file","")` 恒为空 | 数据类加字段 + 抽取时按"当前节"写入（本轮我已改好随后按你的要求撤回，未提交） |
| 3 | **每个标包的目录只保留一份** | `blocks` 按项目存，新生成覆盖旧的 | 两种取舍：**a)** 存每（标包×类别）的派生结果（可秒切视角，存储增长）；**b)** 不存，切换时按需重派生（几秒~几十秒，消耗模型额度） |

另外一处**已有冲突**需要一并定规则：技术规范书的**交付物表会跨标包**列出全部标的的任务域
（代码里已有 `known_domains` 白名单在过滤，避免"凭空多出别的标包的要求"）。
所以"按标包筛要求"这件事**已经在做**，只是筛选结果没有落库、面板也说不清。

## 五、需要你拍板的三个决定

| # | 决定 | 选项 A（推荐） | 选项 B |
|---|---|---|---|
| A | 切换标包时的行为 | **仅切查看视角**；没生成过就显示空态 + 一键生成（需要 §四-3a） | 切换即自动重派生（慢、烧额度，但不用存多份） |
| B | 技术要求如何展示 | **按标包筛 + 标"共享"**（本标包相关在前，全项目共享折叠在后） | 直接展示全项目共享池（不筛） |
| C | 「评分单元」这个词 | 改成**「目录骨架」**（它本质是评分表层级的展开，叫"评分单元"容易和技术规范书混淆） | 保留原名 |

## 六、落地顺序（等你确认后再改代码）
