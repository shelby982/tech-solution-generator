# 标包优先流程：三套产品优化方案

> 角色：本轮产品经理  
> 结论日期：2026-10-15  
> 范围：只做产品设计审查与方案，不修改业务代码  
> 核心约束：上传文件后，必须先从招标文件识别并确认标的/标包/标段；确认某个标包后，后续五步骤才展开，评分点、技术规范、目录、正文与评审全部按当前标包隔离。

---

# 一、结论先行

当前产品已经具备“解析标包”、文件—标包多对多关系、标包范围运行等技术零件，但产品骨架仍然是：

```text
项目 → 直接进入五阶段 → 在拆分面板里选择/筛选标包
```

正确骨架应调整为：

```text
项目 → 上传并解析招标文件 → 形成标包清单 → 用户确认当前标包
     → 当前标包独立的五步骤
```

问题不在于少一个“解析标包”按钮，而在于标包尚未真正成为后续任务的父级对象。目前它同时被当作文件标签、面板筛选条件、运行范围和本地记忆，四种语义混在一起。

本方案给出三种真正不同的产品模型：

| 方案 | 产品模型 | 主要入口 | 适合场景 | 实施成本 |
|---|---|---|---|---:|
| A 标包工作空间 | 标包是独立工作空间 | 先选标包，再进入五步 | 长期产品主架构 | 高 |
| B 项目准备台 | 标包是项目任务行 | 准备台矩阵进入对应阶段 | 多标包统筹、管理视角 | 中 |
| C 向导式投标准备 | 标包是一次受控任务 | 逐步向导完成选择和拆分 | 新用户、低频使用、快速落地 | 中低 |

**明确推荐方案 A「标包工作空间」作为目标架构。**

它与真实业务对象完全一致，能从根上解决跨标包串数据、五步状态混用、切换后上下文不清等问题。若希望分阶段交付，可先用方案 C 的向导完成“上传—识别—确认”入口，再落入方案 A 的标包工作空间；方案 B 更适合作为方案 A 上层的项目总览，而不宜单独成为长期主工作界面。

# 二、业务模型重新定义

## 2.1 核心业务对象

| 对象 | 定义 | 生命周期 | 是否跨标包共享 |
|---|---|---|---|
| 项目 | 一次投标任务的总容器 | 创建至归档 | 是 |
| 招标文件 | 用于识别标的、标包、标段和评分规则的权威输入 | 可更新版本 | 是，但解析结果必须归到标包 |
| 标包 | 后续生产链路的最小业务单元 | 识别 → 确认 → 执行 → 完成 | 否 |
| 技术规范书 | 某一或多个标包的技术要求来源 | 上传后绑定标包 | 默认不共享，显式多选才共享 |
| 我方素材 | 用于支撑章节写作的证据和内容 | 上传后匹配章节 | 可显式绑定多个标包 |
| 标包运行 | 某个标包的一次拆分/生成版本 | 创建 → 处理中 → 完成/失败/废弃 | 否 |
| 评分点 | 从当前标包对应招标内容提取的商务/技术/报价要求 | 随运行版本化 | 否 |
| 技术要求 | 从绑定到当前标包的技术规范书提取 | 随运行版本化 | 否 |
| 应答目录、正文、评审 | 当前标包的下游产物 | 五步骤逐步生成 | 否 |

## 2.2 不可破坏的产品规则

1. **没有确认标包，不创建后续运行。**
2. **每个运行只属于一个项目和一个标包。**
3. **切换标包等于切换整套工作上下文**，不是在同一结果上做过滤。
4. 商务评分点、技术评分点、技术规范要求都必须显示来源文件、页码/条款和当前标包。
5. 文件允许属于多个标包，但属于多个必须是系统识别后经用户确认，或由用户显式操作。
6. 重新解析招标文件不能静默改写已确认标包；必须生成差异并让用户处理。
7. 标包的五步骤分别保存状态和版本，标包 A 的完成度不能推进标包 B。
8. 项目级只保存共享输入、标包清单和聚合进度；业务产物全部进入标包作用域。

## 2.3 后续五步骤的统一定义

为避免当前“四阶段进度条”和“五阶段业务面板”同时存在，产品只保留一套业务阶段：

| 步骤 | 名称 | 核心产物 | 完成门槛 |
|---|---|---|---|
| 1 | 拆分要求 | 商务评分点、技术评分点、技术规范要求 | 三类结果完成或明确标记“不适用” |
| 2 | 确认范围与规则 | 评分点确认、类别选择、主题归属 | 所有强制确认项已处理 |
| 3 | 生成应答结构 | 应答目录、评分点—技术要求—章节映射 | 覆盖率通过或用户确认例外 |
| 4 | 编写与举证 | 分章节正文、引用素材、证据缺口 | 必填章节完成 |
| 5 | 评审与修订 | 评分点风险、问题清单、修订记录 | 阻断问题关闭或接受风险 |

上传、解析标包和确认标包属于五步骤之前的**项目准备阶段**，不能再混入步骤 1。

# 三、当前产品设计审查

## 3.1 当前链路

当前页面将材料条、四阶段顶栏、五阶段拆分面板和三模式页面叠在一个工作区：

```text
上传文件
  → 材料条上的“解析标包”
  → 打开拆分面板
  → 面板内选择标包并点“确认标包”
  → 五步骤展开
```

代码层已经出现正确意图：`confirmedPkg`、`project_packages`、`material_packages`、`workflow_runs.target/package_no`。但确认标包仍主要依赖 URL 与 `localStorage`，产品结构没有把“确认标包”提升为进入工作区的正式闸门。

## 3.2 七个产品结构问题

### 1. 标包识别发生得太晚

用户已经进入五步骤所在页面，才在内部找到标包选择。页面先展示过程，再补业务主语，认知顺序相反。

### 2. “解析标包”与“拆分评分点”并列，因果关系不清

两者视觉上都是操作按钮，但业务上必须严格串行：先识别并确认标包，才能拆该标包评分点。

### 3. 当前标包缺少全局、持久的上下文

当前标包只在面板局部显示。用户进入编写、评审或切换页面后，难以确认自己正在处理哪个标包。

### 4. 项目状态和标包状态混在一起

顶部四阶段用项目级 `sessionStorage` 记录最远阶段，五步骤又按标包运行。多标包情况下，一个标包进入编写可能让另一个标包看起来也推进了。

### 5. 文件归属和工作范围不是同一个动作

文件卡可多选标包，面板又要确认当前标包。用户不清楚是在说明“这份文件属于谁”，还是在选择“现在要做谁”。

### 6. 切换标包的风险提示不足

切换后会换运行、评分点、目录和正文，但交互像普通筛选器，用户可能认为只改变列表显示。

### 7. 解析失败和业务上未识别混为一类

需要区分：文件未完成解析、正文为空、正文中没有标包表述、识别到低置信度候选、候选待用户确认。它们对应的修复动作完全不同。

# 四、三套方案共同的底线设计

无论选择哪套方案，都必须具备以下能力。

## 4.1 标包确认卡

每个候选标包展示：

- 标的、标包/标段号、原文名称；
- 置信度与识别状态；
- 来源文件、页码、原句；
- 关联的技术规范书；
- `确认`、`合并重复项`、`不是标包`、`手动补充`；
- 不能用模型推断出的名称替代原文事实。

## 4.2 全局标包上下文条

进入后续五步骤后，页面顶部始终显示：

```text
当前标包：标的 1 / 标包 2 · 高可靠技术专题研究
版本：第 2 次拆分    招标文件 1    技术规范书 2    [切换标包]
```

用户切换标包时弹出的不是普通下拉，而是带进度的工作区切换器。

## 4.3 强门控

| 当前状态 | 后续五步骤 |
|---|---|
| 尚未上传招标文件 | 不展示；引导上传 |
| 文件解析中 | 不展示；显示解析进度 |
| 未识别到标包 | 不展示；提供查看正文/手动创建 |
| 有候选但未确认 | 不展示；聚焦标包确认 |
| 已确认当前标包 | 展示该标包的五步骤 |
| 当前标包已失效 | 只读展示，提示选择替代标包 |

## 4.4 数据隔离规则

所有请求和缓存都使用统一作用域：

```text
project_id + package_id + run_id/version
```

其中 `package_id` 应是稳定主键，`target + package_no` 作为业务字段，而不是长期依靠字符串拼接做身份。

以下对象必须带标包作用域：

- 文件关联；
- 评分点；
- 技术要求；
- 确认答案；
- 目录和章节；
- 素材匹配；
- 正文；
- 评审结论；
- LLM 用量、日志和导出文件。

# 五、方案 A：标包工作空间

## 5.1 产品模型

标包是项目下的独立工作空间。项目负责发现和管理标包；进入某个标包后，所有内容和阶段都只属于它。

```text
项目
├─ 项目准备：文件、解析记录、标包清单
├─ 标包 A 工作空间：五步骤 + 全部产物
├─ 标包 B 工作空间：五步骤 + 全部产物
└─ 标包 C 工作空间：五步骤 + 全部产物
```

## 5.2 信息架构

```text
项目首页
├─ 项目准备
│  ├─ 招标文件
│  ├─ 解析与标包确认
│  └─ 未归属文件
└─ 标包工作空间
   ├─ 标包概览
   ├─ 1 拆分要求
   ├─ 2 确认范围与规则
   ├─ 3 生成应答结构
   ├─ 4 编写与举证
   └─ 5 评审与修订
```

## 5.3 完整用户流程

1. 用户创建项目，进入“项目准备”。
2. 上传招标文件；系统逐文件显示上传、转文本、建立索引、识别标包四段状态。
3. 系统生成候选标包清单，并展示原文证据。
4. 用户确认、合并、删除或补充标包。
5. 用户给技术规范书和其他文件设置标包归属；系统可推荐，用户确认。
6. 点击某个标包的“进入工作空间”。
7. 系统创建或恢复这个标包的活动运行。
8. 用户依次完成五步骤；每一步只能消费当前标包的数据。
9. 用户通过顶部切换器进入另一个标包，整页工作上下文替换。
10. 返回项目首页可查看各标包进度和异常。

## 5.4 页面与组件布局

### 项目准备页

```text
┌ 项目名称 ─────────────────────────────── 项目总进度 2/5 标包就绪 ┐
│ [1 上传与解析] ─ [2 确认标包] ─ [3 关联技术规范书]                │
├──────────────────────────────────────────────────────────────────┤
│ 左：文件台面                         右：标包确认台               │
│ 招标文件.pdf  已识别 3 个标包          标的1/标包1  高  [确认]    │
│ 技术规范书A   建议归属标包2            标的1/标包2  高  [确认]    │
│ 补充说明.docx 未归属                    标的2/标段1  中  [查看]    │
├──────────────────────────────────────────────────────────────────┤
│ 已确认标包 [标包1 进入] [标包2 进入] [标段1 进入]                │
└──────────────────────────────────────────────────────────────────┘
```

### 标包工作空间

```text
┌ 项目名 / 标的1·标包2 ▾ ─────────────── 保存状态 · 运行版本 ┐
│ [1 拆分要求] [2 待确认] [3 结构] [4 编写] [5 评审]         │
├─────────────────────────────────────────────────────────────┤
│ 当前阶段内容                                                 │
└─────────────────────────────────────────────────────────────┘
```

## 5.5 状态与异常

| 异常 | 产品处理 |
|---|---|
| 招标文件正文为空 | 文件卡红色阻断，提供重新上传/查看解析日志 |
| 没找到标包字样 | 展示已检索范围，允许从原文手动创建并标记“人工录入” |
| 识别到重复标包 | 并排证据，用户合并；合并后保留别名 |
| 技术规范书未归属 | 标包进入步骤 1 前阻断或让用户明确选择“不需要” |
| 同一文件属于多个标包 | 多选归属，后续抽取仍按标包上下文过滤 |
| 重新上传招标文件 | 生成标包差异：新增/删除/改名，不自动覆盖已确认工作区 |
| 标包运行失败 | 只影响当前标包，其他标包可继续工作 |

## 5.6 跨标包切换

- 切换器展示每个标包的阶段、未保存修改和阻断数。
- 有未保存修改时先保存或放弃。
- 切换后 URL、运行、阶段、数据请求、缓存同步替换。
- 切换成功后页头用 1 秒上下文提示：“已进入标的 1 / 标包 3”。
- 不保留上一个标包的列表骨架或数字，加载期间使用当前标包专属 skeleton。

## 5.7 优缺点

**优点**

- 心智模型最准确：一个标包就是一份独立投标内容。
- 数据隔离天然清晰，最不容易跨包串写。
- 五步骤可长期扩展版本、协作、权限和交付物。
- 标包切换语义明确，不会被理解成普通筛选。

**缺点**

- 需要重构项目级与标包级页面边界。
- 历史数据需要归属迁移。
- 当前四阶段导航、三模式路由和五阶段面板需要统一。

## 5.8 实施成本与适用场景

- 成本：**高，约 3–5 个前后端迭代**。
- 适用：中长期正式产品、多标包并行、同一项目持续数周、多人协作。

# 六、方案 B：项目准备台 + 标包矩阵

## 6.1 产品模型

项目是主空间，标包是项目中的任务行。用户先在一张矩阵中看所有标包的准备度和五步骤进度，再点具体单元格进入详情。

```text
项目控制台
└─ 标包矩阵：每行一个标包，每列一个准备项或业务阶段
```

## 6.2 信息架构

```text
项目控制台
├─ 文件与解析
├─ 标包清单
├─ 标包进度矩阵
└─ 右侧详情抽屉/全屏详情
```

矩阵列：

```text
标包 | 文件就绪 | 1 拆分要求 | 2 待确认 | 3 结构 | 4 编写 | 5 评审 | 异常
```

## 6.3 完整用户流程

1. 上传文件，系统解析标包。
2. 用户在矩阵上方的“待确认标包”区完成确认。
3. 确认后矩阵新增标包行。
4. 每行先处理“文件就绪”：绑定技术规范书，处理缺失文件。
5. 点击该行“拆分要求”单元格，侧边详情打开并启动该标包任务。
6. 完成一个阶段后回到矩阵；系统更新状态。
7. 用户可以逐标包推进，也可以先批量拆分所有就绪标包。
8. 点任一矩阵单元格进入该标包该阶段，不经过额外筛选。

## 6.4 页面与组件布局

```text
┌ 项目控制台 ────────────────── [上传文件] [重新解析标包] ┐
│ 待确认标包 2      文件异常 1       已完成 1/4           │
├─────────────────────────────────────────────────────────┤
│ 标包              文件  要求  确认  结构  编写  评审  异常│
│ 标的1/标包1       ✓     ✓     ✓     ✓    12/20  —    2  │
│ 标的1/标包2       ✓     ✓     !     —     —     —    1  │
│ 标的2/标段1       !     —     —     —     —     —    1  │
├─────────────────────────────────────────────────────────┤
│ 点击单元格后，右侧抽屉展示该标包当前阶段详情             │
└─────────────────────────────────────────────────────────┘
```

小屏幕将矩阵转换为标包卡列表，每张卡显示五阶段进度条。

## 6.5 状态与异常

- 矩阵格只显示六类状态：未开始、准备不足、进行中、待确认、完成、失败。
- 鼠标悬停或点击格子解释阻断原因。
- 缺技术规范书时，“拆分要求”格显示准备不足，点击进入文件绑定抽屉。
- 批量任务失败时按标包独立重试，不回滚其他行。
- 标包被重新解析删除时，该行进入“来源已变化”，不直接消失。

## 6.6 跨标包切换

矩阵本身就是切换器：关闭详情回到全局；点击另一行即切换标包。详情页头固定标包名，并提供“上一个/下一个异常标包”。

批量操作必须明确范围，例如：

```text
批量拆分 3 个已就绪标包
[标包1] [标包2] [标段1]
```

用户确认后，为每个标包分别创建运行，不允许一个运行覆盖多行。

## 6.7 数据隔离

矩阵只是聚合视图，所有格子的状态均从标包级数据推导。批量动作是多个标包任务的编排，不产生共享的评分点或目录。

## 6.8 优缺点

**优点**

- 全局进度和异常最清楚，适合多标包项目。
- 可逐个推进，也能安全批量处理。
- 对项目经理、团队负责人最友好。
- 可复用当前五步骤内容，主要新增外层控制台。

**缺点**

- 矩阵信息密度高，对只做一个标包的用户显得复杂。
- 详情抽屉和完整工作页之间可能形成双层导航。
- 若长期只停留在矩阵，编写场景的沉浸感较弱。

## 6.9 实施成本与适用场景

- 成本：**中，约 2–3 个迭代**。
- 适用：项目经理统筹、多标包并行、需要批量处理和异常总览。

# 七、方案 C：向导式投标准备

## 7.1 产品模型

把“上传—识别—确认—拆分”做成一次受控向导。系统每次只让用户解决一个决策，完成后落入当前标包五步骤。它强调顺序正确和低学习成本。

```text
向导任务
1 上传招标文件 → 2 识别标包 → 3 绑定文件 → 4 选择一个标包 → 5 开始五步骤
```

## 7.2 信息架构

```text
项目
├─ 开始/继续向导
├─ 已创建的标包任务
└─ 当前标包五步骤
```

向导完成后不长期占据主界面；用户可通过“新增标包任务”再次进入。

## 7.3 完整用户流程

1. **上传招标文件**：只接收权威招标文件，其他文件暂存到待关联区。
2. **解析与检查**：展示各文件解析质量，失败必须先处理。
3. **确认标包**：逐卡确认候选标包、查看证据、合并重复。
4. **绑定技术规范书**：系统建议归属，用户逐标包确认。
5. **选择要先处理的标包**：默认推荐材料最完整的标包。
6. **预览本次范围**：列出将使用的文件、标包、预计拆分类型。
7. **创建标包任务**：进入该标包五步骤。
8. 完成或退出后，可从项目页选择另一个标包继续向导。

## 7.4 页面与组件布局

```text
┌ 投标准备  3/5 绑定技术规范书 ─────────────────────┐
│ ● 上传文件 ─ ● 识别标包 ─ ● 绑定文件 ─ ○ 选择标包 │
├───────────────────────────────────────────────────┤
│ 当前只处理一个问题                                 │
│                                                   │
│ 技术规范书A.docx                                  │
│ 系统建议：标的1/标包2    证据：第1页“适用于…”      │
│ [确认] [选择其他标包] [此文件不参与]               │
├───────────────────────────────────────────────────┤
│ [上一步]                               [下一步]    │
└───────────────────────────────────────────────────┘
```

向导结束前提供范围确认单：

```text
将创建：标的1 / 标包2
使用：招标文件 1 份、技术规范书 2 份
拆分：商务评分点、技术评分点、技术规范要求
[确认并开始]
```

## 7.5 状态与异常

- 每步只有一个主操作，错误就地解决。
- 解析失败不能跳过；没有标包字样时允许手动创建。
- 低置信度标包必须查看证据后确认。
- 文件归属不完整时允许保存草稿退出，但不能创建后续运行。
- 用户关闭浏览器后，从最近未完成步骤恢复。
- 已创建标包任务后再次修改范围，生成新版本并显示影响预览。

## 7.6 跨标包切换

向导内不允许边拆边切。创建任务后，项目页展示已创建标包任务卡；用户选择另一标包时先离开当前任务，再进入或创建另一任务。

这种限制牺牲效率，换取低出错率。切换确认文案明确写出：“将离开标包 2，进入标包 3；两者内容相互独立。”

## 7.7 数据隔离

向导最后一步才创建 `run`，因此未确认候选不会污染评分点和目录。向导草稿只存项目准备数据；创建任务时将确认范围固化成标包运行快照。

## 7.8 优缺点

**优点**

- 最容易理解，严格阻止错误顺序。
- 能显著减少“没确认标包就拆评分点”。
- 对现有页面改造较小，可以快速验证业务流程。
- 适合把解析异常、低置信度和文件归属逐一讲清楚。

**缺点**

- 多标包连续处理时步骤重复，效率不如矩阵。
- 熟练用户会觉得向导拖慢操作。
- 它解决入口顺序，但不是最终的信息架构；长期仍需稳定的标包工作空间。

## 7.9 实施成本与适用场景

- 成本：**中低，约 1–2 个迭代**。
- 适用：产品早期验证、新用户占比高、标包数量较少、希望先控制风险。

# 九、推荐方案与落地路径

## 9.1 推荐：A 标包工作空间

推荐理由不是它界面更漂亮，而是它把业务父子关系放对了：

```text
项目拥有标包；标包拥有五步骤和全部产物。
```

只要这个关系成立，评分点、技术规范、目录、正文、评审和导出都能自然隔离。方案 B 和 C 都能解决一部分交互问题，但如果底层仍以项目级五阶段为主，后续会继续出现状态、运行和缓存串包。

## 9.2 建议分三期交付

### 第一期：先建立硬门控

- 项目进入后先显示准备页，不直接展示五步骤。
- 上传招标文件后自动进入解析状态。
- 候选标包必须确认。
- 确认后创建标包任务并进入五步骤。
- 当前标包全局常驻。

这期可复用方案 C 的向导式交互，快速阻断错误流程。

### 第二期：完成标包工作空间

- 所有五步骤接口、页面状态和缓存统一使用 `project + package + run`。
- 移除项目级“最远阶段”状态。
- 切换标包时整套替换上下文。
- 文件、评分点、技术要求、目录、正文和评审支持按标包版本追踪。

### 第三期：增加项目矩阵

- 将方案 B 的矩阵作为项目首页的管理视图。
- 支持批量拆分、异常聚合和团队协作。
- 点击矩阵单元格进入方案 A 的标包工作空间。

最终组合为：

```text
项目矩阵（B，总览）
   ↓
标包工作空间（A，主作业界面）
   ↑
首次准备向导（C，新建入口）
```

这里不是同时实现三个竞争界面，而是用 A 作为产品骨架，C 负责首次创建，B 负责多标包管理。

# 十、实施前必须确定的产品决策

1. “标包、标段、标的”的统一展示名称是否统称为“投标单元”，界面保留原文类型。
2. 一个招标项目没有显式标包时，是否自动创建“整项目”投标单元；建议允许，但必须标注“人工确认”。
3. 技术规范书一份属于多个标包时，是整份复用还是按章节归属；建议第一版整份多选，抽取时保留来源章节。
4. 招标文件更新后标包发生变化，旧工作空间如何处理；建议保留只读旧版本，让用户选择迁移或继续。
5. 批量拆分是否开放；建议先完成单标包链路，再开放多任务编排。

# 十一、验收标准

## 11.1 主流程

1. 新项目进入后看不到可执行的五步骤，只看到上传与标包准备。
2. 上传招标文件后，能看到独立的解析阶段和文件级状态。
3. 系统识别出的每个标包都有原文证据。
4. 用户未确认标包前，不能创建评分点拆分运行。
5. 确认标包后，五步骤标题和所有页面都显示当前标包。

## 11.2 数据隔离

1. 标包 A 和标包 B 分别拆分，评分点数量、目录和正文互不影响。
2. 切换到未生成过的标包，显示空状态，绝不保留上一标包内容。
3. 标包 A 进入编写后，标包 B 的阶段仍保持未开始。
4. 标包 A 的重新拆分只产生 A 的新版本。
5. 导出文件名称、审计记录和模型用量都能追溯到标包和运行版本。

## 11.3 异常

1. 文件解析失败、正文为空、未发现标包、候选待确认分别显示不同状态和动作。
2. 技术规范书未绑定标包时，在步骤 1 前得到明确阻断或“不适用”确认。
3. 招标文件重新解析产生标包差异时，不静默覆盖已有工作区。
4. 标包切换发生网络错误时保留原工作区，不进入半切换状态。

# 十二、本轮设计判断

当前新增的“解析标包”“确认标包”和文件归属能力应保留，但需要从拆分面板内部上移到项目准备层。现有五步骤也不需要推翻，关键是把它们整体下沉到标包工作空间，并统一阶段状态。

如果本轮只选择一套方案进入开发，选择 **方案 A**；如果只能做一个短迭代，先交付 **方案 C 的入口门控**，但数据模型和路由必须按方案 A 设计，避免做成一次性流程补丁。
