# 产品与架构分析：评分点驱动的投标应答作业系统

> 说明：本文是**系统级 / 产品级**分析，不针对某一个项目的数据。
> 所有"现状"结论都对应代码事实（表结构、编排节点、服务模块、接口）。

---

## 一、产品定位：这是什么产品

| 维度 | 内容 |
|---|---|
| 输入 | 招标文件（评分办法）、技术规范书（技术内容）、企业素材（业绩/资质/方案底稿） |
| 输出 | **应答投标文件**（章节正文）+ **可追溯的评分点覆盖证据**（哪一章为哪个评分点得分、引用什么素材、评审结论） |
| 用户 | ① 投标负责人（拆解、确认范围、把控结构）② 写手（按章编写）③ 复核者（按评分点把关） |
| 替代什么 | 人工"读招标文件 → 列目录 → 分工写 → 逐条对照评分表"的作业方式 |
| **差异化** | **以评分点为主线的闭环**：拆解评分点 → 目录承载 → 按需举证写作 → 按评分点评审 → 缺口修订。不是"AI 写文档"，而是"**按得分口径组织并证明**的作业系统 |

一句话：**产品卖的是"得分确定性"，不是"文字生成"。**

## 二、领域模型

### 2.1 对象链（用户已确定的核心关系）

```
招标评分点  ↔  技术规范要求  ↔  应标章节  ↔  企业素材  ↔  生成内容  ↔  审查结果
   ①            ②             ③           ④           ⑤           ⑥
```

### 2.2 一等公民 vs 派生

| 类别 | 对象 | 说明 |
|---|---|---|
| **一等公民**（有独立生命周期） | 项目 / **标段（标的×标包）** / **评分点** / 技术规范要求 / 章节 / 素材 | 每个都有自己的状态、版本、责任人 |
| **派生**（可重算） | 评分地图、映射矩阵、覆盖率、风险、评审结论、目录 | 由一等公民推导，不应作为人工维护的主数据 |

**关键判断**：
- **评分点**是"得分口径"的载体（分值 + 得分条件 + 否决项 + 举证要求）→ 是**评分与评审的锚**。
- **章节**是"得分的承载"→ 它的第一属性不是"写得好不好"，而是"**为哪个评分点得多少分**"。
- **素材**是"举证"→ 它只在**被引用**时有意义（不是"越多越好"）。

### 2.3 生命周期（产品视角的完整闭环）

```
① 立项/建项目
② 上传（招标文件 / 技术规范书 / 企业素材）
③ 拆解评审点（商务 / 技术 / 技术规范书）
④ 待确认（标段范围 · 类别 · 主题归属 · 分值合计自检）
⑤ 产物：目录（评分点 → 章节骨架） + 评分点↔要求映射
⑥ 编写（按章）：按需挂素材、按证据要求写作
⑦ 评审（按评分点）：满足度 / 缺失得分要点 / 举证齐否
⑧ 修订（针对缺失要点重写该章）→ 回到 ⑦（收敛）
⑨ 定稿与导出（Word/PDF，章节树 + 附件清单）
```

现状对应（代码事实）：
- ③④⑤ 已实现（三段式面板）
- ⑥ 逐章编写已实现（诸葛亮），但**素材是全量预匹配**（沈括），不是按需
- ⑦ 评审**按章节存**（`reviews.block_id`），虽已带评分点口径字段
- ⑧ 收敛回路已实现（生成 → 技术评审 → 合规评审 → 聚合 → 缺口 → 收敛判定 → 反馈重写）
- ⑨ **导出已实现**（`GET /api/projects/{id}/export` → .docx）

## 三、系统架构现状

### 3.1 分层

```
┌ 前端  six 页面 ─────────────────────────────────────────────┐
│ three-mode(合并工作台: 要求与大纲/素材库/方案编辑) · review(质量检查) │
│ projects(项目列表) · project-init/workbench/diff-review(旧页,待清理) │
├ 编排层  LangGraph StateGraph + 3 个人工闸门 + 评审收敛回路 ──────┤
│ parse → outline_draft →〔闸门1〕→ extract → match →〔闸门2〕      │
│   → generate → 技术评审 → 合规评审 → 聚合 →〔闸门3〕→ 缺口/收敛/重写 │
├ 智能体层 ───────────────────────────────────────────────────┤
│ 张衡(解析·拆解·提炼) 沈括(素材匹配) 诸葛亮(写作)                 │
│ 王安石(技术评审) 包拯(合规评审)                                 │
├ 服务层 ────────────────────────────────────────────────────┤
│ scoring_map(评分地图) point_store(评分点/要求) split_report(拆分清单)│
│ scoring_risk(评分点级风险) split_answers(作答) block_store(章节/素材)│
│ usage_store(模型成本) config_store                              │
├ 基础设施 ───────────────────────────────────────────────────┤
│ 解析器(PDF/DOCX/OCR/TOC) · LLM 调度(mock/冷却/成本) · SQLite(业务+checkpoint)│
└────────────────────────────────────────────────────────────┘
```

### 3.2 数据表（业务对象）

| 表 | 承载 | 关键字段 | 现状 |
|---|---|---|---|
| `projects` | 项目 | scope_target/package_no/name（投标范围） | ✅ 已用 |
| `materials` / `material_chunks` | 素材与其切片 | role / file_path / content / page | ✅ 已用（chunks 仅匹配时生成） |
| `blocks` | 章节 | title/level/content/**review_point_ids**/criterion_text/score_weight/status | ✅ 主载体 |
| `review_points` | **评分点** | point_id/package_no/category/clause/factor/item/criterion/points/bands | ✅ 已用 |
| `spec_requirements` | 技术规范要求 | requirement_id/topic/title/package_no/source_file | ✅ 已用 |
| `reviews` | 评审结果 | block_id/criterion_text/**satisfied/covered_points/missing_points** | ✅ 已用（**按章节存**） |
| `split_answers` | 用户作答（范围/类别/归属） | key/value | ✅ 已用 |
| `block_revisions` | 章节版本 | revision_no/content/source | ⚠️ 有 API，**UI 未用** |
| `project_snapshots` | 项目快照 | — | ⚠️ 建表未启用 |
| `llm_usage` | 模型成本 | call_site/model/tokens/cache/latency | ✅ 已用（示例：770 次调用 / 138 万 token） |
| `workflow_runs` / `checkpoints` | 运行与图状态 | stage/thread_id | ✅ 已用 |

### 3.3 能力矩阵（产品要求 vs 实现）

| 能力 | 状态 | 缺口 |
|---|---|---|
| 拆解评审点（多标段/多类别） | ✅ | — |
| 范围/类别确认（人机协同） | ✅ | 闸门位置可再对齐"决策点" |
| 目录 = 评分点骨架 + 规范书要求挂载 | ✅ | — |
| 覆盖率自检（评分点/分值/要求） | ✅ | 未按阶段呈现（已删覆盖率模块，待回归） |
| **编写时按需挂素材** | ❌ | 现在是**全量预匹配** |
| **评审按评分点为主视图** | ⚠️ | 结果按章节存，未做评分点级聚合展示（`scoring_risk` 已有基础） |
| 评审 → 缺口 → 重写收敛 | ✅ | 收敛阈值/轮次策略需产品化 |
| 多轮修编 / 版本 | ❌ | 有 `block_revisions` 表与 API，UI 未用 |
| 导出 | ✅ | 仅 Word；缺 PDF/附件清单/差异导出 |
| 成本可见 | ✅（后端） | 前端未展示"这份标书花了多少" |
| **得分预估**（当前能拿多少分） | ❌ | 评审结论已有字段，可聚合 |

## 四、结构性议题（产品级，逐条给判断）

### 议题 1：**双中心冲突 —— "章节中心" 与 "评分点中心"**

- 现象：进度条报"正文 0/530"、评审按 block 存、报告按章节列；而**得分是按评分点给的**。
- 影响：用户读到的是"写了多少章"，但决策需要的是"**13 个评分点里还有几个拿不到分**"。
- 判断：**评分点必须是主视图**，章节是它的承载与明细。这是全系统口径统一的根。

### 议题 2：**标段（标的×标包）是筛选还是聚合根**

- 现象：现在 `projects.scope_*` 存**一个**投标范围；一次生成一份目录；旧标段结果会被覆盖。
- 影响：多标段投标（本项目实测 3 个标包）无法并行管理，切回旧标段只能重跑。
- 判断：**标段应升级为聚合根**（`bid_sections`），产物、章节、素材引用、评审都挂在它下面。

### 议题 3：**素材：一次性匹配 vs 企业知识资产**

- 现象：素材按项目存（`materials.project_id`），匹配是"把 chunk 挂到每章"的全量动作。
- 影响：① 跨项目无法复用企业业绩/资质；② 大量章节不需要素材，全量匹配是纯浪费；
  ③ "匹配结果"沉在章节里，形成不了可检索的资产。
- 判断：素材应分两层 —— **企业级素材库（跨项目复用）** + **项目级引用（按需检索）**；
  检索的触发点是章节的 `evidence_required`（"需要什么"已经算出来了）。

### 议题 4：**评审颗粒度与"得分"的表达**

- 现象：`reviews` 有 `satisfied/covered_points/missing_points`（很好的评分点口径），但按 block 存。
- 影响：无法回答"这个评分点现在能拿几分、差在哪"。
- 判断：新增**评分点级 verdict**（可得分 / 缺口 / 举证齐否 / 责任人），章节级作为下钻明细。

### 议题 5：**版本与修编（投标的真实工作方式）**

- 现象：`block_revisions` 有 API，没有 UI；没有"这一版 vs 上一版改了什么"。
- 影响：投标是多轮（初稿→内部评审→定稿→盖章版），没有版本就没有交付节奏。
- 判断：引入**定稿基线 + 版本树 + 章节 diff**；定稿后锁定，修改走"修订版"。

### 议题 6：**人机协同的闸门该放在哪**

- 现象：闸门在"流程节点"上（outline / materials / report）。
- 影响：有些闸门用户其实无从判断（素材匹配结果好不好），有些关键决策点却没有闸门（定稿）。
- 判断：闸门应对齐**用户能判断的决策**：① 范围与类别 ② 目录结构 ③ 主题归属
  ④（可选）素材引用 ⑤ 定稿。评审结果不需要"确认"，需要"处理"。

### 议题 7：**可追溯链必须闭合**

- 现象：链条字段齐了（章节带 `review_point_ids`、评审带 `criterion_text`），但素材 chunk 引用未持久化。
- 影响："这段正文引用了哪条素材"回答不了 → 出证、复核、追责都断。
- 判断：**引用关系落库**（章节 → 素材 chunk 的引用表），导出时附"证据清单"。

### 议题 8：**成本与确定性的边界**

- 现象：每章一次模型调用（示例：530 章 ⇒ 530+ 次调用，已记录 770 次 / 138 万 token）。
- 影响：一次全量重跑的成本与文化，决定了产品能不能被反复使用。
- 判断：**确定性骨架优先**（已有）＋**增量生成**（只重写受影响的章节）＋**按评分点触发**
  （没缺口的章节不重写）。这也是"按评分点为主线"的成本红利。

### 议题 9：**最后一公里（交付物）**

- 现象：导出 .docx 已有；缺 PDF、附件清单、评分点对照表、版本差异。
- 判断：交付物应包含**正文 + 评分点响应索引 + 附件清单**，这才是"能直接交"的文件。

### 议题 10：**质量度量**

- 现象：覆盖率有；成本有（后端）；**得分预估没有**。
- 判断：产品首页/看板应回答三件事：**能拿多少分（预估）· 缺什么（缺口）· 花多少钱（成本）**。

## 五、目标架构

### 5.1 领域与流程

```
项目 Project
 └─ 标段 BidSection(标的×标包)          ← 聚合根
     ├─ 评分点 ScoringPoint(分值/口径/否决/举证)
     ├─ 技术规范要求 SpecRequirement
     ├─ 章节 Chapter(承载评分点, 版本化)
     │    └─ 引用 Citation → 素材 Chunk
     └─ 产物 Artifact: 目录 / 映射 / 评审verdict / 导出文件
素材库 KnowledgeBase(企业级) ──引用──▶ 标段
```

状态机（每标段独立）：

```
拆解 → 待确认 → 产物 → 编写 → 评审 → 修订(循环) → 定稿 → 导出
```

### 5.2 UI 拓扑（简单、逻辑清晰）

**一条主线，五个阶段，左侧竖条（已实现的做法沿用）**

```
拆分评审点 → 待确认 → 产物 → 编写 → 评审
```

| 阶段 | 主视图（以评分点为准） | 右侧内容 |
|---|---|---|
| 拆分评审点 | 评分点清单（商务/技术/规范书） | 结构化评分口径（逐条得分条件） |
| 待确认 | 需要用户决定的项 | 范围/类别/主题归属/分值自检 |
| 产物 | 目录 + 映射 | 章节骨架、评分点↔要求矩阵 |
| 编写 | **按章**，章头常驻"本章回应哪个评分点 + 需什么举证" | 正文；素材**按需**插入（默认收起） |
| 评审 | **按评分点**的 verdict 列表 | 下钻到章节明细；对缺口一键重写 |

**状态信息只保留一条**（现在两条重复：`#workspace-status` + `#status-bar`），
且**口径随阶段变**：拆分报材料/目录、编写报章节、评审报评分点。

### 5.3 交付出口

导出内容 = 正文（章节树）+ **评分点响应索引**（每个评分点 → 章节 → 引用素材）+ 附件清单；
支持 Word / PDF；定稿后出"版本差异"。

## 六、关键架构决策（建议）

| # | 决策 | 选项 A（建议） | 选项 B | 理由 |
|---|---|---|---|---|
| 1 | 主视图 | **评分点为中心** | 章节为中心 | 得分口径决定一切 |
| 2 | 标段 | **升级为聚合根**（多标段并行、产物按标段存） | 继续作为筛选 | 多标包投标是常态 |
| 3 | 素材 | **企业库 + 按需引用** | 项目内全量预匹配 | 复用 + 成本 + 准确 |
| 4 | 评审 | **评分点 verdict + 章节明细** | 仅章节评审 | 直接回答"能不能得分" |
| 5 | 版本 | **定稿基线 + 修订版** | 无版本 | 投标是多轮交付 |
| 6 | 闸门 | 对齐**决策点**（范围/类别/归属/定稿） | 对齐流程节点 | 用户只在该拍板处拍板 |
| 7 | 生成策略 | **增量**（按缺口章节） | 全量重跑 | 成本与文化 |

## 八、产品健康度度量（建议纳入看板）

| 指标 | 定义 | 现状 |
|---|---|---|
| 覆盖率 | 评分点/分值/要求 的落点比例 | ✅ 已有 |
| **得分预估** | 按评审 verdict 估算当前可得分数 / 满分 | ❌ 待做 |
| 缺口数 | 未满足的得分要点数量（按评分点） | 部分（`scoring_risk`） |
| 举证完备率 | 有 `evidence_required` 的章节中，已引用素材的比例 | ❌ 待做 |
| 单标成本 | 该标段的模型 token / 金额 | 后端有数据，前端未展示 |
| 一次通过率 | 首轮评审即满足的评分点占比 | ❌ 待做 |
