# 标包驱动的主流程：产品诊断（第二轮，聚焦"解析顺序"）

> 用户口径（本次）：
> 「上传完文件之后，第一需要筛选出对应的标包、标段或标的信息，然后基于这个信息，
> 再去进行后续 5 个步骤的拆分，主要是评分点和文书内容的拆分。
> 基本上技术规范书都是基于某一个标包来的，所以重点在于招标文件的解析。
> 招标文件的解析需要先拆分出对应的标包，然后基于标包再去拆分对应的商务、技术评分点。」

---

## 一、当前实现的三个硬证据

### 证据 ①：技术规范书与标包**完全没有绑定**
```
materials 表字段：id, project_id, filename, type, file_path, role, parsed_at,
                  size_bytes, file_size, parse_status, deleted_at
                  ↑ 没有 package_no
material_packages（文件↔标包多对多表）行数：0
```
用户说"技术规范书都是基于某一个标包来的" —— 而**系统里根本不存在这个关系**。

### 证据 ②：一个项目 41 条运行，40 条 aborted，只有 1 条知道自己的标包
```
ca95f573 aborted  ''      ''      ← 不知标包
…（39 条同样 aborted、无归属）
53d6533d done     标的1    2       ← 唯一有归属的一条
```
标包信息只挂在**零星的运行**上，而不是挂在这个项目/这批文件的**根**上。

### 证据 ③：标包在下拉里被当成"筛选器"
`#sr-view-pkg`（顶部「筛选 · 标包」）—— 位置在**整页顶部**，语义是"看哪个标包"，
而五步（评分点 / 待确认 / 产物 / 编写 / 评审）是**项目级**的。于是：
- 标包 = 一个**视图过滤条件**，不是**内容的归属**
- 拆评分点时并不要求先确定标包（后端有容错回退：过滤为空就放宽标包）
- 切标包只是换**看**的内容，不会"进入该标包自己的工作区"

---

## 二、为什么这与用户的心智冲突（问题的本质）

用户的心智模型是一条**单向依赖链**：
```
招标文件 → 解析出【标包/标段/标的】 → 对某个标包 → 拆【商务评分点 + 技术评分点】
        → 结合该标包的技术规范书 → 生成应答目录 → 编写 → 评审
```
**标包是这条链的根**：没有标包，后面的每一步都无从谈起（因为内容是按标包分开的）。

而现在产品把它做成了**并列的一个筛选条件**，等于把"根"降级成了"视图开关"。
结果就是用户看到的：标包和文件没关系、切标包评分点还是那些、拆解结果对不上。

**一句话**：现在的 IA 是「项目 → 五步 →（用标包过滤）」，
应该是「项目 → 标包 → 五步（每个标包各走一遍）」。

## 三、三个待选方向（下一步出图 + 对比）

### 方案 1「标包工作台」——标包作为**空间**
```
项目
├─ 标包切换器（顶部常驻：标的1/标包2 ▾ ｜ ＋ 新建标包）
└─ 【当前标包】的工作区
     上传（本标包的文件）→ ①评分点 → ②待确认 → ③产物 → ④编写 → ⑤评审
```
- 标包是**容器**：进去之后所有东西都属于它，五步在每个标包内各走一遍
- 上传时就要选标包（或上传后逐文件归属，一份文件可属多个标包）
- **优点**：概念最干净，完全对应"每个标包是单独的内容"
- **代价**：五步要从"项目级"改成"标包级"，改造量最大

### 方案 2「准备阶段 + 标包矩阵」——标包作为**进度**
```
【项目级】
  ① 上传文件 → ② 解析招标文件（拆出标包/标段/标的）→ ③ 逐标包拆评分点（商务/技术）
                ↓
  标包进度矩阵           文件   评分点   目录   正文   评审
    标的1 / 标包2        ✅     ✅      ⏳     —      —
    标的1 / 标包3        ✅     ⚠ 缺商务  —      —      —
    标的2 / 标包1        ⏳     —       —      —      —
```
- 在现有五步**之前**加一个显式的「准备」区：先出标包，再逐标包拆
- 用**矩阵**展示每个标包走到哪一步；点格子进入该标包该阶段
- **优点**：最贴合用户说的顺序；进度一眼可见；五步内部不用改
- **代价**：多一个"准备"界面，信息架构多一层

### 方案 3「文件驱动」——标包作为**文件派生物**
```
【招标文件.pdf】解析结果
  ├─ 标的1 / 标包2   →  [评分点 商务8 / 技术8]  [目录 ✅]  [正文 12/38]   进入 ›
  ├─ 标的1 / 标包3   →  [评分点 商务6 / 技术9]  [目录 ⏳]  [正文 —]        进入 ›
  └─ 标的2 / 标包1   →  [评分点 待拆]                                     进入 ›
【技术规范书.docx】  → 挂到：[标的1 / 标包2 ▾]（一拖即挂；一份可挂多个）
```
- 以**文件**为锚：每份招标文件解析后就地展开它包含的标包
- 技术规范书**明确挂到标包**（解决证据 ①）
- **优点**：上传即见结果；文件与标包的关系最直观；最省改造
- **代价**：标包多时列表会长；同一标包跨文件时需要合并规则

---

## 四、我的倾向（供参考）

**方案 3 最省、方案 1 最正、方案 2 最直观。**

- 如果你的真实情况是"**一份招标文件里有多个标包**"（用户描述的场景）→ **方案 3** 的"文件展开标包"正好对上，
  而且能顺手把技术规范书挂到标包（补上现在完全缺失的关系）
- 如果你希望**长期**把"每个标包独立推进"作为产品骨架 → **方案 1**
- 如果你想先看**全局进度**、又不推翻现有五步 → **方案 2**
