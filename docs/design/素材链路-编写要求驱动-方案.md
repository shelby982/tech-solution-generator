# 编写要求驱动的素材链路：发现 → 输入 → 应用（方案）

> 立论：**每章先有编写要求（主编写人员输出），素材是"为满足这些要求而补充的内容"。**
> 所以素材不是"有就收集"，而是"缺什么补什么、补完用在哪一条要求上"。
> 本方案把"编写要求"提升为一等对象，素材链路的三段（发现 / 输入 / 应用）全部围绕它组织。

---

## 一、现状与问题（按链路三段拆）

| 段 | 现在怎么做 | 问题 |
|---|---|---|
| **发现** | 依据栏/素材页签 → 官方来源抽屉，按章节标题+`evidence_required` 推导检索词，扫官方入口给候选 | 检索词来自**系统猜的缺口**，不是"这条编写要求需要什么" → 找到的常与要求错位 |
| **输入** | 抓取核验 → 接受为引用（trust）→ 关联本章；老引用可"提取片段" | 输入的是"一条来源"，不是"满足某条要求的素材"；片段与要求没有关系 |
| **应用** | 选片段 → 生成整章时注入 | 注入是**整章级**的，AI 不知道"第 3 条要求该用哪个片段"；生成完也没有"逐条要求是否被满足"的验收 |
| **贯穿** | 编写要求只存在于主编写人员的脑子里/文档外 | 要求不可见、不可核对、不可追溯 → 素材再多也"看不出关系" |

一句话：**链路缺"准绳"。** 没有逐条要求，素材就无法被组织成"为要求服务"的形态。

---

## 二、核心模型：一条准绳、三层对象

```
① 编写要求（Brief，章级、逐条、可编辑、可版本化）
     ↓ 每条要求派生
② 素材需求（Need，条目级）
     · 类型：政策依据 / 标准条款 / 行业数据 / 案例佐证 / 我方证明 / 图片示意
     · 状态：待补 | 已补（关联了素材片段）| 不适用
     ↓ 满足需求
③ 素材（Source：我方材料 / 外部来源；及其可用片段 Snippet）
     · 段落 / 表格 / 图片，可勾选、可改写、必须带来源标注
```

**关键规则**
1. **要求是唯一的准绳**：没有对应要求的素材，不主动收集（避免"素材很多但用不上"）。
2. **需求必须条目化**：一条要求 → 0..n 条需求；需求有类型、有状态、可指派。
3. **素材片段挂需求**：片段不是"给本章用"，而是"给某条要求用"。
4. **逐条验收**：编写完成后，按"要求 × 是否回应 × 是否引用到素材"出结论。

## 三、链路三段的重构

### 3.1 发现（Discovery）——从"猜缺口"到"读要求"

```
当前章（或当前节）
   ↓
① 编写要求：主编输出/LLM 起草 → 人工确认（逐条）
   ↓
② 系统把每条要求拆成素材需求（类型 + 关键词）
   ↓
③ 按需求检索：官方入口优先 → 候选（标"命中哪条需求"）
   ↓
④ 抓取核验 → 片段抽取 → 与需求匹配打分（相关度：命中需求关键词/表格/图）
```

**交互**：需求卡片上一键「找素材」，检索词=该需求的（要求原文 + 关键词），不再混成一个词；
优先展示"可能满足这条需求"的片段（按相关度排序），其余折叠。

### 3.2 输入（Input）——从"接受来源"到"装配需求"

```
抓取核验 → 片段列表（段落/表格/图）
   ↓ 勾选片段 → 选择"满足哪条需求"（默认按相关度预选）
   ↓ 「补到需求」→ 该需求状态：待补 → 已补
   ↓ 图片片段：「下载为我方素材」→ 进项目素材库（正文不放外链）
```

**交互**：接受来源时可以一次勾选多个片段，并批量指定"用于需求 1 / 需求 2"；
需求卡片显示「已补 2 个片段（段落×1、表格×1）」。

### 3.3 应用（Apply）——从"整章注入"到"按条注入"

```
生成某一节时，上下文 = 该节对应的编写要求 + 满足这些需求而被选中的片段
   · 提示词：逐条要求回应；可基于片段改写，但必须保留来源标注
   · 未满足的需求 → 正文写【待补充：<需求类型>】
```

**补写与重生成**：
- 某条需求"待补"仍想先写 → 允许生成，但正文该处写【待补充】并在质检里挂账
- 补到素材后 → 「按新素材重写该条要求对应的段落」（局部重写，不整章重跑）

---

## 四、验收（Quality）——按"要求"而非按"章"

| 检查 | 判定 | 输出 |
|---|---|---|
| 要求覆盖 | 每条要求是否在正文里有着落 | 「要求 3 未回应」 |
| 素材引用 | 已补片段的来源是否出现在正文（带【来源】） | 「要求 2 已补素材但正文未引用」 |
| 需求缺口 | 待补需求的数量 | 「2 条素材需求待补，正文可能大量【待补充】」 |
| 表格/图示 | 按要求的类型核（要求要表→有表；要求要图→有图） | 「要求 4 需要图示，未提供」 |

质检清单从"章级/节级"升级为**"要求级"**，每条可跳转到正文对应位置。

## 五、界面（IA）

### 5.1 编写工作台三栏

```
┌ 目录树（结构） ─┬ 正文（节视角） ──────────────┬ 编写要求 + 素材（准绳） ─┐
│ 项目理解        │  ### 一、营销管理系统运行现状   │ 编写要求（7 条）  [主编起草/编辑] │
│  ├ 项目背景现状 │  ……（正文）                   │ ① 说明政策依据       已补 2 片段 │
│  ├ 建设范围     │                               │   · 需求：政策/文件   ✓ 已补     │
│  └ …            │                               │ ② 给出行业数据       待补 1       │
│                 │                               │   · [找素材]                     │
└─────────────────┴───────────────────────────────┴────────────────────────────────┘
```

- **要求面板**：逐条要求 + 每条下的需求状态 + 「找素材」/「查看已用片段」
- **素材页签**（保留）：全部外部依据 / 我方材料，含"正文已引用/未引用"状态
- 生成按钮旁显示「要求覆盖 5/7 · 需求待补 2」

### 5.2 素材抽屉（发现 → 输入）改造

```
官方来源
[检索词（= 当前选中的需求）        ] [自动找来源]
官方入口 chips
素材缺口（需求）列表：① 政策依据 未补 [检索]  ② 行业数据 已补 2 条
候选（标"命中需求①"）→ 抓取核验 → 片段勾选（默认按相关度选）→ [补到需求①]
```

### 5.3 命名与归属（避免重复）
- 「编写要求」= 章级属主（**唯一**）
- 「编写规范」= 全局纪律/模块配方（P0.5，**方法论层**，不逐条）
- 「编写计划」= 一级目录级（任务清单/篇幅/表图安排）
- 三者的关系：**规范给方法 → 计划给安排 → 要求给这一章的具体标准 → 素材给弹药**

## 六、数据模型与接口

### 新增表

```sql
-- 编写要求（章级，逐条）
CREATE TABLE writing_briefs (
  id TEXT PRIMARY KEY, project_id INTEGER, thread_id TEXT, block_id TEXT,
  version INTEGER, status TEXT,            -- draft | published
  items TEXT,                              -- [{"id":"b1","text":"说明政策依据","type":"policy","needs":[...] }]
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
-- 需求 ↔ 片段（片段挂需求）
CREATE TABLE need_snippets (
  need_id TEXT, citation_id TEXT, segment_index INTEGER, block_id TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (need_id, citation_id, segment_index)
);
```

### 新接口

| 方法 | 路径 | 作用 |
|---|---|---|
| GET/PUT | `/projects/{id}/writing-briefs?threadId=&blockId=` | 读/写本章编写要求（版本化） |
| POST | `/writing-briefs/{id}/draft` | LLM 起草编写要求（供主编改） |
| GET | `/writing-briefs/{id}/needs` | 要求 → 需求拆解 + 状态（已补/待补） |
| POST | `/needs/{need_id}/bind` | 片段绑定到需求（接受来源时批量） |
| POST | `/writing-briefs/{id}/check` | 要求级质检（覆盖/引用/表格图示） |

### 与现有代码的衔接
- 复用：`citations` + `segments`/`selected`、`citation_links`、`chapter_materials`、`writing_specs`（L0/L1）、`writing_plans`（计划）、`quality_check`
- 扩展：`citations_for_prompt(block, need_id)` 按需求取片段；`build_writing_prompt` 增 `brief_items` + `need_snippets`
- 迁移：`writing_briefs` / `need_snippets` 建表 + `citations.segments` 已有

## 七、分期实施

| 期 | 内容 | 验收 |
|---|---|---|
| **P6（先做）** | 编写要求对象（章级、可编辑、版本化）+ 要求面板；要求 → 需求拆解（LLM 一次起草，人工确认） | 每章能看到"要求 5 条 + 需求状态" |
| **P7** | 素材抽屉改造：按需求检索 + 候选标"命中需求" + 片段勾选默认按相关度 + 「补到需求」 | 一条需求的"已补"能点开看到用了哪几个片段 |

| 可选 | 图片一键入库（已做后端）、跨章复用要求模板（项目理解 7 章同构） | — |

## 八、边界与风险

1. **不破坏既有"素材分开"原则**：我方材料=证据，外部来源=依据，仍在素材模块分区展示。
2. **要求由人确认**：LLM 只起草，逐条由主编写人员确认/修改，避免"模型替你定要求"。
3. **合规**：外部素材一律带来源（官方/非官方+用户确认），正文引用保留标注；外部图片入库后仍标"来源：XX"。
4. **不阻断写作**：需求待补也允许生成（正文写【待补充】），只在质检挂账，避免卡死手工修正。
5. **版本与留痕**：要求、素材片段、生成各自版本化，成稿可回答"用了哪版要求/哪些片段"。

---

## 九、一句话总结

> **把"编写要求"做成每章的一等对象**：要求 → 需求 → 素材片段 → 正文，四段一一对应；
> 素材的发现（按需求找）、输入（补到需求）、应用（按需求注入）、验收（按需求核）
> 全部围绕这条准绳 —— 这样"素材与正文的关系"才是可解释、可追溯、可优化的。
