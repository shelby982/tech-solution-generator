# 章节文本与当前标包要求/技术规范书匹配度分析

> 视角：产品经理
> 对象：章节正文生成链路（章节计划 → `chapter_sse` 分节写作 → 素材/依据注入）
> 结论：**不是模型“写得不好”，而是写作时模型根本没有拿到当前标包的技术规范书条款、本章要求和可用素材。** 它拿到的是章节标题、几个要点和依据名称，于是只能写“正确的废话”。

---

## 1. 先看证据

### 1.1 技术规范书里有明确要求，但写作时没进 Prompt

`blocks.spec_requirement_ids` 已经保存了本章对应的技术规范条款：

- 章节 `s1.3.2 方案总体架构设计` 绑定了 3 条规范要求；
- 实际条款包括：
  - 基于 DDD 划分微服务集群与边界；
  - 基于 Kubernetes 的微服务架构、服务网关、注册中心、配置中心；
  - 熔断限流、弹性伸缩、灰度发布、全链路监控。

但生成出来的章节正文里：

```
Kubernetes: 0
DDD / 领域驱动: 0
熔断: 0
限流: 0
服务网关: 0
注册中心: 0
配置中心: 0
全链路: 0
灰度: 0
```

正文写的是“依据分为政策标准、招标技术条款、评分要求三类”“以招标文件为准”这类通用表述，**没有回应技术规范条款本身**。

### 1.2 写作 Prompt 的组成

`backend/services/chapter_sse.py::_stream_section` 实际给模型的内容：

```python
payload = build_section_payload({}, {
    "title": section.title,
    "points": section.points,
    "words": ...,
    "basis": section.basis,       # 只有 ref 名称
    "how": ...,
    "deliverables": ...
}, str(block.content)[:2000])     # 整章前 2000 字，不是本节
```

Prompt 里只有：

- 章节标题；
- 节标题；
- 3~5 个 points；
- basis 的 `ref` 名称（如“方案总体架构设计合理”）；
- 整章前 2000 字；
- 素材（仅“已绑定素材”，见下）。

**没有：**

- `spec_requirement_ids` 对应的规范条款全文；
- 本章 plan 的逐条编写要求；
- 当前节正文（只有整章前 2000 字）；
- 与本节相关的自动检索素材；
- 标包名称/编号/范围；
- 条款到节落的覆盖关系。

### 1.3 素材链路是空的

- `chapter_material_chunks`：0 行；
- `chapter_materials`：0 行；
- `material_chunks`：1446 段。

说明素材文件已经解析，但**没有绑定到章节/节**。写作时 `material_prompt_for_block` 找不到绑定，直接走 `NO_MATERIAL_HINT`：  
“不要编造具体项目名称、合同金额与精确数字；用概括但完整的表述把内容写完”。

这条提示本意是防止编造，但在“没有规范/素材”的情况下，等于要求模型写空话。

### 1.4 本章 plan 要求也是“抽象要求”

`writing_plans` 里 `s1.3.2` 的要求是：

```json
{"text": "写清楚「方案总体架构设计合理」", "type": "text", "source": "point"}
```

这不是技术规范条款，只是评分点要素的抽象描述。即使把它传给模型，也不足以生成 Kubernetes/DDD/熔断限流等具体内容。

### 1.5 已有能力没有接上

项目里已经有：

- `services/material_search.py`：按章节/要点关键词在 `material_chunks` 里检索；
- `spec_requirements`：612 条规范要求（当前 thread 153 条）；
- `blocks.spec_requirement_ids`：章节到规范条款的映射；
- `writing_plans`：章节编写要求；
- `requirement_coverage`：要求回应率检查。

但写作链路只用了 `section.points + basis.ref + 已绑定素材`，**上面这些上下文都没有进入 Prompt**。

---

## 2. 根因拆解

### 根因 1：上下文组装层缺失

当前 `_stream_section` 直接拼 Prompt，没有“本节上下文包”。

应该有一个 `SectionContext`：

```
标包：名称/编号/线程
本章：标题 + plan 要求（逐条）
规范：spec_requirement_ids → 条款全文
本节：标题 + points + basis 全文 + 当前节正文
素材：本节绑定素材 + 自动检索片段（文件/页码/原文）
邻节：上一节/下一节标题（避免重复）
```

现在这些信息散落在数据库和服务里，没有组装。

### 根因 2：规范条款只存了 ID，没有在写作时展开

`blocks.spec_requirement_ids` 是 JSON 列表，但 `_stream_section` 不读它，也不会 join `spec_requirements` 取 `text`。

所以模型只知道“方案总体架构设计合理”，不知道“要写 DDD、Kubernetes、服务网关、熔断限流、灰度发布、全链路监控”。

### 根因 3：素材检索没有接到写作链路

`material_search.search_block_materials` 已实现“章节标题/要点 → 素材片段”，但写作时没用；只用了人工绑定，而当前绑定为 0。

结果：
- 模型没有本项目事实；
- 只能用“以招标文件为准”的万能句式；
- 与当前标包的技术规范、产品名称、指标不匹配。

### 根因 4：本节正文没有进 Prompt

`block.content[:2000]` 是整章开头 2000 字，不等于当前节正文。章节越长，写作越早的节越容易“失忆”；同一章后面的节看不到自己的规划内容。

### 根因 5：Prompt 没有“覆盖契约”

当前 Prompt 要求：
- 开头结论；
- 3~6 段；
- 禁用空话；
- 不编数字。

但没有要求：
- 每条规范条款至少有一个落点；
- 每个条款要写出“要求 → 响应 → 证据”；
- 引用要能对上条款/素材；
- 不允许用“以招标文件为准”代替响应。

于是模型选择“安全但空泛”的写法。

### 根因 6：生成后没有对齐检查

当前有 `requirement_coverage`，但主要看关键词是否出现；没有在生成后做：
- 规范条款关键词/要素覆盖；
- 条款引用/素材引用检查；
- 与同章其他节的内容重复检查；
- “空话/套话”比例检查。

写作完成/进度统计也不会因为“没回应规范”而阻止。

### 根因 7：计划与写作的契约断了

计划阶段知道：
- 评分点；
- 章节要求；
- 规范 ID；
- 素材缺口。

写作阶段只拿到：
- 节标题、points、basis.ref。

计划阶段的“要求”没有变成写作阶段的“输入契约”。

---

## 3. 产品影响

| 影响 | 表现 |
|---|---|
| 评标得分 | 技术规范条款没有逐条响应，专家看不到“满足/优于”证据 |
| 可信度 | 大量“以招标文件为准”“按批复要求”，像模板文，不像针对本标包的方案 |
| 返工 | 用户要手工补技术细节，生成价值低 |
| 一致性 | 同章不同节风格/口径不统一，材料引用缺失 |
| 风险 | 编造数字被抑制了，但“该写的没写”成为更大的问题 |

---

## 4. 建议方案

### P0：先把上下文接上（1 周内）

1. **新增 `SectionContext` 组装层**
   - 读取 `block.spec_requirement_ids` → `spec_requirements` 全文；
   - 读取本章 plan requirements；
   - 读取当前节正文（`section_ranges` 定位）；
   - 调 `material_search` 按本节 points/basis 检索 3~6 段素材；
   - 读取标包/线程信息。

2. **重写 `_stream_section` Prompt**
   - 明确“当前标包/章节/节”；
   - 给出规范条款全文，逐条编号；
   - 给出本节响应矩阵：`条款 ID → 要写什么 → 证据来源`；
   - 要求每个条款至少一个落点；
   - 给出素材原文/页码；
   - 不再用整章前 2000 字代替本节正文。

3. **素材自动检索兜底**
   - 本节无人工绑定时，自动检索；
   - 检索结果按 score 排序、同文件最多 2 段；
   - Prompt 中要求引用 `【来源：文件（第 N 页）】`。

4. **生成后对齐检查**
   - 规范条款关键词/要素覆盖率；
   - 引用标记是否出现；
   - 空话比例（“以招标文件为准/按批复要求/相关标准”）；
   - 低覆盖时标记“待补”并给出缺哪几条。

### P1：把契约前移到计划

- 章节 plan 的 `requirements` 不再只写“写清楚某评分点”，而是带 `spec_requirement_id`、条款摘要、必要素材类型；
- 节级 plan 带 `requirement_ids` / `basis.text`；
- 计划面板显示“本章规范条款 N 条，已覆盖 M 条”。

### P2：评估闭环

- 用评标专家视角做“条款覆盖评分”；
- 对低覆盖章节自动重写/补写；
- 统计不同标包/章节的匹配度趋势。

---

## 5. 验收指标

- 本章规范条款覆盖率 ≥ 90%；
- 至少 1 条素材/条款引用落在正文；
- 空话句式占比 < 5%；
- 同章节间重复率明显下降；
- 评标专家盲测：能指出“这段回应了哪条技术规范”的比例 ≥ 80%。

---

## 6. 一句话

**当前不是“模型能力不足”，而是“写作时没有把标包规范书、本章要求和素材交给模型”。**

先把上下文组装和覆盖契约做出来，再谈模型和文风。

## 7. P0 已落地（本轮）

- 新增 `services/section_context.py`：
  - `blocks.spec_requirement_ids` → `spec_requirements` 条款全文；
  - 本章 `writing_plans` requirements；
  - 当前节 Markdown 正文（按 `##` 切分）；
  - `material_chunks` 按本节关键词自动检索（文件/页码/原文）；
  - 标包名称/编号。
- `chapter_sse._stream_section` 已改：
  - 不再传 `build_section_payload({}, ...)`；
  - 不再用整章前 2000 字代替本节；
  - Prompt 增加「当前标包 / 本章技术规范条款 / 本章编写要求 / 当前节正文 / 本节相关素材」；
  - 明确要求逐条回应规范条款，不能只用“以招标文件为准”。
- 生成后新增 `coverage_for_section`：
  - 计算规范条款覆盖数/缺失项；
  - 写入 section 事件，前端状态显示“规范覆盖 X/Y，缺…”。

### 实测（同一章节 s1.3.2，同一模型）

改造前生成正文：

```
Kubernetes: 0 / DDD: 0 / 领域驱动: 0 / 熔断: 0 / 限流: 0
服务网关: 0 / 注册中心: 0 / 配置中心: 0 / 全链路: 0 / 灰度: 0
```

改造后（P0 真实生成）：

```
Kubernetes: 3 / 领域驱动: 2 / 熔断: 2 / 限流: 2
服务网关: 2 / 注册中心: 2 / 配置中心: 2 / 全链路: 2 / 灰度: 3
```

正文已开始逐条回应 DDD、Kubernetes、服务网关、注册中心、配置中心、熔断限流、灰度发布、全链路监控等规范条款。

仍待 P1/P2：
- 本章 plan 的 requirements 仍是抽象评分点，需要计划侧也带 `spec_requirement_id`；
- 素材自动检索目前是关键词相关度，后续可做 rerank/embedding；
- 覆盖检查目前是关键词级，后续接评标专家审阅。
