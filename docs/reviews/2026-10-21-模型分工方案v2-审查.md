## 结论

**方向同意，但 v2 还不能直接排期。**

- 对"多 Agent 讨论/投票一律不做"的判断是对的，协同价值只在**分工、同源、校验、隔离**——这个结论保留。
- 但 v2 有三处**会直接导致返工**的问题：角色口径不闭合、并行与同源互斥、对当前编排现状判断失准。
- 另有 7 处必须补的设计（模型解析/回退、作用域与记忆、留痕与成本、校验判据、SSE 与进度面、失败隔离、验收可测性）。
- 建议先做 **M0（6 个决策 + 一张角色字典）**，再进入 M1。否则 M1 的接口参数和 M3/M7 的组件会返工两次。

**分档数量**：P0 × 3、P1 × 7、P2 × 10（同类合并）。

> **前提修正（2026-10-21 17:0x，用户澄清）**：图片**不是由章节正文派生**的，而是**辅助章节内容**的独立材料。因此本报告两处结论需要按此口径调整：
> - **P0-2** 的解法改为「同源于**节计划/依据/素材** + 图文并行」，不是「图由文生」；
> - **P1-4** 的「节点必须在正文找到」改为「交付物符合 + 依据可追溯 + 图文不矛盾」。
> 其余结论不变。

## 一、P0：阻断实施

### P0-1 角色口径四套并存，头像/设置/接口/代码对不上

v2 内部就出现了四套角色集合：

| 位置 | 角色集合 |
|---|---|
| §2.1 编写整章 mockup、验收 1 | **3 个**：主编 / 图片 / 表格 |
| §2.3 图标表 | **4 个**：主编 / **文字编写** / 图片 / 表格 |
| §3.1、§六、M7 | **5 个**：主编 / 文字编写 / **文字精修** / 图片 / 表格 |
| 代码 `ROLES`（`backend/agents/chapter_team.py:12`） | **6 个**：chief / text / table / diagram / wang_anshi / bao_zheng |

由此派生三个具体问题：

1. **正文由谁写，前后矛盾。** §2.1 写"主编：规划与统稿（**写正文**、控节奏）"；但代码里 `ChapterChiefAgent.plan()` 只产出任务包，正文由 `text` 角色写（`chapter_team.py:114-131` / `:134-150`）。§四的 ② 也是 `text(流式)`。把"主编写正文"画进 UI，等于把模型归属标错。
2. **`role` 参数无法区分"编写"和"精修"。** v2 §四只给了 `text/diagram/table` 三个 role 值，但设置里有"文字编写 / 文字精修"两个键。M1 按现在的写法实现，M5/M7 必然返工（重写时到底用哪个 role、哪个模型，接口层没有答案）。
3. **头像缺了干活最多的那个。** 3 头像里没有"文字"，但验收 3 要求"每个头像旁显示当前模型，可一键切换"——用户恰恰最需要切的就是文字模型（第 1 个诉求）。只画 3 个头像，这个诉求没有入口。

**建议**：先产出**唯一一张角色字典**，作为 M1/M3/M7 的共同输入。推荐值：

| 角色 key | 中文名（UI） | 接口 role | 职责 | 默认模型 | 是否头像 |
|---|---|---|---|---|---|
| `chief` | 主编 | `chief` | 只做大纲/编排，**不写正文** | pro | 是（仅大纲阶段工作） |
| `text` | 正文编写 | `text` | 每节正文（流式） | flash | 是 |
| `rewrite` | 文字精修 | `text` + `mode=rewrite` | 带原文的改写 | pro | 否（单 logo 时显示） |
| `diagram` | 图示 | `diagram` | 由本节正文派生图 | flash（不是 pro，见 P2） | 是 |
| `table` | 表格 | `table` | 由本节正文/交付物派生表 | flash | 是 |
| `wang_anshi` / `bao_zheng` | 技术/合规审校 | 同名 | 只出意见，不改正文 | 可选 | 否 |

头像建议 **4 个（主编 / 文字 / 图片 / 表格）**，或明确"主编 = 编排，不写正文"并把文字头像放在最前。若坚持 3 个头像，需在 mockup 与验收里写清"文字模型从哪里切"。

### P0-2 "图表并行"与"图由文生"互斥

- §1.2 表格：`异步 | 图/表可与正文**并行**，整章更快`
- §1.1 ②：`图/表 ← 正文 | 图/表由**本节正文**派生`
- §四：`diagram（**输入=本节正文**）`
- 代码现状：job 路径确实是并行——`asyncio.gather(produce('text'), produce('table'), produce('diagram'))`，三者都只拿到 `package + plan`（`backend/services/chapter_writing.py:120-124`），**没有本节正文**；关系图只是 `节点 -> 节点` 链（`chapter_team.py:166`）。

也就是说：**"并行"和"同源"只能二选一**。v2 同时承诺了两个，验收 6 的"节点必须能在正文找到依据"在并行下不可能成立。

**建议二选一（推荐前者）**：

- **A. 同源优先（推荐）**：每节 `text → (table + diagram 并行)`，图表输入本节正文；跨节用流水线补速度（第 N 节图表生成时，第 N+1 节正文已在写）。代价：单节完成时间变长，"3 个头像"会长时间停在"等待"。
- **B. 并行优先**：图/表继续按 plan 的 `purpose` 生成；放弃"图由文生"硬约束，只做"图与正文一致性"软提示。速度和成本好，但 v2 §5.2 的核心卖点没了。

选定后，§1.2、§5.2、§四、验收 6/8 要一起改，不能只改一处。

### P0-3 对现状判断失准：现在是"前端逐节 SSE 只写文字"，不是"后端逐节编排"

v2 §四把编排画成：

```
整章编写（SSE 一路到底）
  ① 主编读计划 → 产出节+三问
  ② 逐节循环：text → table → diagram
  ③ 汇总
```

当前实现是：

- "编写整章"= 前端 `for` 循环，每节发一个 **GET EventSource** 到 `/studio/section/stream`，只生成文字（`chapter-studio.mjs:1691-1737`、`:2346-2360`、`:2533-2549`）；后端 `stream_section()` 只推 `delta/done/error`，**没有 stage 事件、没有 table/diagram、没有 role/model 参数**（`backend/routes/chapter_studio.py:355-433`）。
- 能按角色分工的 job 编排（`/studio/writing-jobs`）还在，但 UI 已下线：`chapter-team.mjs` 没有被任何页面 mount，`chapter-studio.mjs:2645` 里只剩 `const team={refresh(){},show(){},dispose(){}}` 占位；该模块的测试还留着（`tests/frontend/chapter-team.test.mjs` 等）。
- `chapter-studio.mjs:1740` 的 `writeChapterApi()` 是死代码，真正"编写整章"用的是 `streamWriteSection()`。

**后果**：M1 不是"加 role/model 参数"这么小，而是要先把"整章编排"落到某一条引擎上。最少多出：图表生成接入主流程、整章级状态聚合、失败隔离、可恢复/可停止、进度回写。建议加 **M0：引擎决策**：

- 方案 1（推荐）：**扩展 SSE 引擎**——保留逐节流式，后端新增"节级编排"（text 完成后触发 chart），图表事件并进同一条 SSE；job 编排仅作为"后台任务"保留或直接删除。
- 方案 2：**复活 job 引擎**——把 `chapter-team.mjs` 重新挂进进度页，用它的 `role_states` + 轮询实现头像；代价是丢掉逐节流式高亮（或给 job 补 SSE）。

无论选哪个，`writeChapterApi`、`chapter-team.mjs`、`team` 占位和相应测试要一起清理，否则下次还会有人接错线。

## 二、P1：需要补的设计

### P1-1 模型解析、默认与回退没有定义（现状也不支持）

v2 只写"本次覆盖 > 章节默认 > 系统默认"，但：

- **顶部模型不参与编写。** 页面顶部模型选择器存在（`mode-outline.js:201`），`getModel` 也传进了 `mountChapterStudio`，但 `chapter-studio.mjs` **从未使用** `getModel`。用户以为切了，实际没切。
- **生成端点里只有 `/studio/draft` 支持显式选模型，其余全是轮询。** `stream_section` 直接取 `configs[index % len(configs)]`（`chapter_studio.py:397-402`）；`/studio/section`、`/studio/table`、`/studio/diagram` 都传 `settings={}`（`:480` / `:524` / `:240`），`/studio/outline` 也是 `{}`（`:340`）；`call_role` 在没指定时同样是 `configs[index % len]`（`chapter_team.py:91-93`）。所以同一章的不同节可能交替用 pro / flash，且用户无感知。`/studio/draft` 的"显式 model + 409 明确报错"是现成的好先例（`:630-633`），新实现应复用它而不是另起一套。
- **没有回退。** `call_role` 找不到指定模型时直接 `raise ValueError('…生成模型不可用')`（`chapter_team.py:93`）；v1 §七承诺的"自动回退 + 提示已回退"在 v2 里被删掉了。
- **验证池的坑。** `get_configs_and_next_index()` 在存在 verified 配置时**只返回 verified 的**（`config_store.py:190-197`）；用户选了一个 verify 失败的已配置模型，会得到"不可用"而不是回退。另外 `typesafe` 属于判断型 provider，不参与生成（`config_store.py:92`），设置面板必须显式排除，否则用户能选中一个必然失败的模型。
- **新增 role 会脏。** 若按 P0-1 增加 `rewrite`，`TeamRequest.models` 的 Literal（`backend/routes/chapter_writing.py:12-16`）和 `ROLES[role]`（错误文案处）都要同步，否则请求校验 422 或 KeyError。

**要补齐的规则（建议写进 v2）**：

```
解析顺序：本次覆盖 → 章节默认 → 项目默认 → 顶部模型（若仍保留）→ 系统默认（首个 verified 配置）
命中已配置但不可用 → 回退到系统默认，并在 SSE/响应里返回 requested / used / fallback 三个字段
显式选择模型 → 从 get_all() 里找，不要走 verified 轮询池
生成路径不再轮询；轮询只用于"完全没配置"的兜底场景
```

### P1-2 "本次覆盖 / 章节默认 / 记住上次"三者语义打架，且没有落库设计

- §3.3：`每个角色记住上次选项（localStorage + 项目设置）`、验收 4：`选择被记住`
- §六：`本次覆盖只在弹窗里，不写回默认`、验收 9：`覆盖不污染默认`

"记住上次"和"覆盖不污染默认"在语义上冲突：如果上次的覆盖被记住并下次生效，它就变成了新默认。必须定义"记住"是哪种：

- **推荐**：记住 = 在设置面板里显示"上次用：xxx"作为提示，不自动生效；默认只由"章节设置/项目设置"决定；"本次覆盖"只存在于当前任务，任务结束即失效。

另外两个未定义点：

- **作用域是项目还是章节？** v1 §6.1 写"项目级默认 + 本章覆盖"，v2 §3.1 写"章节默认"，§六又写"编写设置（章节默认）"。两边不一致。项目内各章通常用同一套分工，**推荐项目级默认 + 章节覆盖**，存储落在服务端（新表或 `projects` 配置字段），localStorage 只做缓存。
- **入口在哪？** v2 §3.1 说"编写整章弹窗"和"更多 → 编写设置"，但当前"编写整章"是**直接开跑**、没有弹窗（`chapter-studio.mjs:176`、`:2522`）。要么加弹窗（多一步），要么把模型选择放进头像条/设置面板（推荐，少一步）。§2.1"点头像换模型"和 §3.1"弹窗里换"也是两套交互，需要二选一。

### P1-3 v1 里的"留痕 / 回退 / 成本"被静默删掉，但"切模型"离不开它

v2 只保留了"当前模型"的展示（验收 3），没有回答：**这一节到底是哪个模型写的？刷新后还查得到吗？翻车了能回到上一版吗？**

代码现状：

- `block_revisions` 没有 model / role / prompt 字段（`backend/db.py:346-354`），`add_revision()` 只存内容、摘要、source（`backend/services/block_store.py:897-925`）。按 v1 §八的"每节记录 role/model/tokens/时长、可回滚"，需要扩表或新表。
- `llm_usage` 有 model / call_site / tokens，但**没有 block_id / section**（`db.py:406+`）；而 `/studio/section/stream`、`/studio/section`、`/studio/diagram`、`/studio/table`、`/studio/outline` 都没包 `run_context`（只有 `/studio/draft` 包了，`chapter_studio.py:636-639`），所以这些调用在用量表里 `project_id/thread_id` 是 NULL，连"这一章花了多少钱"都归集不到。
- v1 的"设置面板显示调用次数/¥X 估算"因此没有数据基础；v2 直接删掉了成本，问题被掩盖而不是解决。

**建议**：M1 同期做两件小事——给 `block_revisions` 加 `model/role/prompt`（或新增 `writing_calls` 表），并让 studio 五个端点都包 `run_context`。否则验收 3 只能显示"当前模型"，历史刷新后丢失，切换模型无法审计。

### P1-4 质量措施只写了"要什么"，没写"怎么判、判完去哪"

v2 §五的四条核心措施，当前都还没有实现，且若干处判据不成立：

| 措施 | 现状 | 需要补的判据 |
|---|---|---|
| 节点可溯源（硬校验） | `normalize_model_output` 只做形状/长度规整（`diagrams.py:70-105`），没有和正文比对；`strip_invalid_diagrams` 只删节点 <2 的块（`body_align.py:89-110`） | 匹配算法：原文包含 / 去标点后包含 / 2-gram 重合率阈值；不通过进 `proof` 组并带"正文未出现：X"，**不要静默删** |
| 字数不低于目标 80% | 目标字数由 outline `words` 给出（`section_outline.py:13`），但流式写完后没有任何检查 | 从 `payload.words` 取目标；**"压缩/精简"类提示词要豁免**，否则必然误报；缺口进 `auto`，不阻断保存 |
| 引用保留 | SECTION_SYSTEM 要求"【来源：文件名】"（`section_outline.py:176`），但流式路径**没有注入 citations**，也没有检查来源是否合法；`chapter_studio.py` 的 `stream_section` 只拿 block 旧正文当 evidence | 注入已接受来源列表；区分"保留原文引用"和"新造引用"；新造引用必须来自 citations 表，否则进 `proof` |
| 表格列名来自交付物 / 数字来自正文 | `/studio/table` 只接收 `title/requirement/text/columns(数量)`（`chapter_studio.py:253-258`、`:501-532`）；插入面板也不传交付物 `cols`（`chapter-studio.mjs` 插入表格逻辑） | 传 `deliverables[].cols`；数字比对做成 `proof`（表格数字未必在正文出现，不能硬拦） |
| 图型按交付物 | `pendingFigures` 点"生成"时把类型**硬编码为 layered**（`chapter-studio.mjs:2395`），忽略交付物里的 `type` | 从 `d.type` 取值；无值时再 auto |

另外两个具体缺陷：

- 图表校验失败后，`stream_section` 里的 `_dropped` / `_captions` 直接丢弃，没有进待办（`chapter_studio.py:417-420`），与 §5.4"缺口进待办"不符。
- 待办里"缺表格/缺图示"的 `autofix` 动作实际调的是**补写文字**（`todo2Act` 的 autofix 分支只认 `「标题」` 然后 `streamWriteSection`），不是生成图/表。M6 要顺手修掉，否则"一键修复"名不副实。

另外，"硬校验"这个词需要降级：图节点是**概括性短语**，正文里常常是展开表述，严格字面匹配会误杀大量好图。建议默认按"可核对"（proof）处理并展示证据，只有连续多节全部不匹配才升级为告警。是否"拦下"由你拍板（见决策 6）。

### P1-5 SSE 事件撑不起已画的 UI，且会多出第三套进度面

- §2.1 要显示"正在写：③ 行业发展背景分析（3/8 节）、62%、规划中/统稿中"，§四给的事件只有 `{role, state, section, model}`，**缺**：节序号/总数、阶段名、"跳过"的触发方、失败原因、重试次数、请求 id。
- 当前 SSE 是**每节一条**（前端循环打开 EventSource，`chapter-studio.mjs:1712`），不是"一路到底"。头像状态需要跨多条 SSE 由前端聚合，事件设计要按"章级会话 + 节级事件"来写，不能按单连接设计。
- `/studio/section/stream` 是 **GET**，`EventSource` 不能带 body：`role/model` 只能走 query 或服务端默认。v2 的"本次覆盖"若走请求体，这个接口不成立。
- 进度面已经有：右栏"进度"页签（逐节状态 + 编写/重写 + 图表）、正文预览区高亮、章头按钮文案"编写中 1/8"。再叠加"3 个头像 + 62% 进度条"，就是**第三套进度表达**，与之前"不要两套进度"的产品收敛方向冲突。
- 另外"编写整章"目前有两份重复实现（进度页签 `:2346` 与章头按钮 `:2522`），加头像前应先收敛成一个函数。

**建议**：头像条不独立成"第三个进度面板"，而是复用进度页签的数据模型，只在**正文上方做一条轻量状态条**（4 个头像 + 一行当前节）；状态事件定义成章级 `{job_id, section_index, section_total, role, state, model, error?}`。这样既满足"看到 3 个 Agent 在干活"，又不增加一套进度逻辑。

### P1-6 失败隔离与"三套状态词"没对齐

- v2 §四承诺"图/表失败 → 待补，正文照常完成"；当前 job 路径是**任一 specialist 失败整单失败**：`outputs = gather(..., return_exceptions=True)`，只要有异常就 `raise ValueError`（`chapter_writing.py:120-124`）。要落实隔离，需要改成"文字成功即落正文，图表失败记缺口"。
- 审校呢？当前 job 路径**每次都跑**王/包双审校（`chapter_writing.py:127-133`），且审校失败会导致整单失败、不保存（测试 `test_review_error_does_not_save_incomplete_output`）。v1 说"审校默认关、可开"，v2 把审校从设置/头像/验收里全删了，但 §1.1 又把"审校→待办"列为三大协同之一。**去留必须先定**（见决策 5）。
- 状态词现在有三套：`图待补/表待修`（位置待办）、`auto/proof`（待办分组）、`跳过/失败/完成`（头像）。需要统一成一套状态枚举，否则同一件事在三个地方叫三个名字。

## 三、P2：文字与细节

1. **"已有两条配置"与现状不符**：当前 `.api_config.json` 有 4 条——`deepseek-v4-pro`、`deepseek-flash`、`deepseek-v4-flash`（3 条生成）+ `jev-latest`（typesafe，判断型，不参与生成）。"强/快"标签在配置结构里没有对应字段，需要硬编码映射或新增元数据；自定义模型会显示成什么要定义。
2. **默认模型给 pro 缺成本依据**：§3.1 图片 pro、§六图片 pro；但 §2.1 mockup 图片位又写 `deepseek-flash`。同一文档三处不一致。建议先按"全部 flash，pro 作为可选"跑一版量测，再定默认；不要在方案里先写死"推荐 pro"。
3. **"编写整章弹窗"不存在**：当前按钮直接开跑，§3.1 的"编写整章弹窗"是凭空假设；要么新增弹窗，要么改成头像条/设置面板（推荐后者）。
4. **节点数 2–12 与 job 路径 2–10 / 关系链格式不一致**：`/studio/diagram` 是 2–12、结构化 `:::diagram type=…`；job 路径 `DiagramPiece` 是 2–10、只产 `A -> B -> C` 关系链（`chapter_team.py:70-73`、`:166`）。若复活 job 引擎，"图型按交付物"在那边根本不成立；若扩展 SSE 引擎，job 侧的 diagram 可以先删。
5. **角色命名不统一**：正文 Agent / 文字编写 / 正文编写 / 文字精修 / text / rewrite。建议只保留一套（P0-1 字典），UI 文案、SSE、日志、设置键、测试全部引用同一常量。
6. **v1 与 v2 没有"谁生效"的声明**：两份都在 `docs/design/`，v2 没有写"取代 v1"。建议 v2 开头加"本篇取代 v1 的第 X/Y 节，保留 v1 的 A/B/C"，并把留痕、成本、回退、审校这些 v1 已有内容合并回来（不是删掉）。
7. **§九"待你确认"里有两项其实已经定了**：#2"换模型入口"——§2.1 已写"点头像换"；#3"图片硬校验是否可接受"——§5.2 和验收 6 已按"硬校验"写。待确认项应只保留真正没定的（建议换成第 6 节那 6 项）。
8. **冗余可合并**：§1.1② 与 §5.2"图由文生"重复；§3.1 默认值列表与 §六设置树同表两画法；§2.3 图标表出现 UI 里不存在的"文字编写"；§5.1"【来源】不得丢"在"整段删除/压缩"场景下必然不成立，需要限定为"未被删除段落内的引用不得丢"。
9. **"重写 / 精修 / 局部改写"是同一个动作还是三个，没有定义**：§2.2 标题写"重写"，§5.1 说"让模型改而不是重写一篇"，§六 又叫"文字精修"；v1 §5.2 还列了整节重写 / 只改某一段 / 换语气 / 压缩 / 图不对五种场景，v2 全丢了。建议明确：整节重写（保留图表）与局部精修（只改选中段/压缩/换语气）共用 `rewrite` role、不同 prompt；"图不对"单独走 diagram。
10. **表格的"双源"要写清时序**：§5.3 说列名来自交付物、数字来自正文/素材；但正文没写全列名时（当前常见），是"先按交付物列名生成空表"还是"等正文写完再生成"，会直接改变 P0-2 的执行顺序，也需要在 M6 里定。
