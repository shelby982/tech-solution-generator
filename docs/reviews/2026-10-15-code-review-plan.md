# ge-solution 全面代码审查方案

## 1. 审查目标

本次审查回答四类问题：

1. 产品主流程是否能从真实输入走到正确输出。
2. 模块边界、状态机和数据模型是否保持一致。
3. 是否存在重复实现、死代码、无效数据和不可持续的维护结构。
4. 测试是否覆盖真实契约，并且不会污染开发或生产数据。

审查以“可证明的问题”为核心。每个缺陷必须包含代码位置、触发条件、影响和整改方向；单纯风格偏好不列为缺陷。

## 2. 审查范围

| 维度 | 主要检查内容 | 产出 |
|---|---|---|
| 产品主流程 | 上传、解析、标包识别、评分点拆分、大纲、匹配、生成、评审、导出 | 端到端断点和错误状态 |
| 架构 | routes/services/domain/infra/orchestrator 依赖方向、模块职责、全局状态 | 边界问题和拆分建议 |
| 业务逻辑 | 状态转换、幂等、重试、并发、取消、恢复、空结果 | 可复现逻辑缺陷 |
| API 契约 | HTTP 状态码、路径参数与实体归属、错误传播、前后端枚举 | 契约漂移和数据串线风险 |
| 数据 | 外键、唯一性、孤儿数据、历史数据、索引、迁移和清理 | 只读数据质量报告 |
| 冗余和死代码 | 无调用路由、旧页面、重复管线、无引用函数和错误测试契约 | 删除或收敛清单 |
| 前端 | 模块启动、隐藏视图副作用、事件监听、缓存、URL 状态 | 初始化和状态管理问题 |
| 测试 | 隔离、真实链路、错误路径、浏览器启动、测试是否固化旧行为 | 覆盖缺口和守卫建议 |
| 运行质量 | 日志、健康检查、资源回收、数据库增长 | 可观测性和长期运行风险 |

## 3. 审查方法

### 3.1 建立系统地图

- 确认真实产品入口、前后端路由、后台任务和持久化边界。
- 统计核心文件规模，识别职责过度集中的模块。
- 从入口反向追踪主流程所依赖的数据表和状态字段。

### 3.2 静态逻辑审查

- 阅读路由、服务、领域对象、基础设施和编排层的调用链。
- 搜索宽泛异常处理、无效分支、旧兼容逻辑、重复 CRUD 和未引用入口。
- 检查 URL 参数、项目 ID、运行 ID、block ID 等实体归属是否被验证。

### 3.3 数据审查

- 以 SQLite 只读模式执行 `integrity_check`、外键检查、孤儿检查和分布统计。
- 检查运行状态、失败记录、历史 checkpoint、无正文材料和重复逻辑键。
- 使用 `EXPLAIN` 检查核心查询是否命中索引。

### 3.4 测试与运行验证

- 执行 Python 编译检查、后端测试、前端 Node 测试和 `git diff --check`。
- 对照测试夹具与真实运行路径，检查测试是否绕开上传、持久化或浏览器启动。
- 测试必须使用临时数据库；审查真实数据库时只允许只读连接。

## 4. 严重级别

| 级别 | 定义 | 处理门槛 |
|---|---|---|
| P0 | 数据不可恢复、安全事故或核心服务不可用 | 立即停止发布 |
| P1 | 主流程错误、跨项目污染、静默数据损坏、错误被当成功 | 发布前修复 |
| P2 | 长期资源增长、结构性冗余、迁移和测试缺口 | 纳入近期迭代 |
| P3 | 边界输入、可维护性和体验瑕疵 | 排期处理 |

## 5. 证据和通过标准

### 缺陷证据

- 必须给出精确文件和行号。
- 必须描述输入、执行路径和错误结果。
- 数据问题必须由只读查询验证；推测与实测分开标注。
- 测试通过不能自动证明业务正确，需要验证测试是否覆盖真实契约。

### 审查通过标准

- 没有未解决的 P0/P1。
- 上传到标包识别的真实链路有集成测试。
- 项目与运行实体归属在服务端强制校验。
- 所有前端 API 对非 2xx 统一抛错。
- 外键策略、级联策略和清理脚本保持一致。
- 测试运行不能触碰真实数据库。
- 旧入口和重复实现有明确的删除或兼容期限。
