# 章节工作台：素材库 × 方案编辑 的模块化与共用设计

> 2026-09-21 · 产品/交互设计稿（**待用户拍板，未改代码**）
> 背景需求：素材库视图点「素材匹配」看不到任何匹配界面；素材库与方案编辑本质上都在
> 「章节结构」上做事（找素材 / 写内容），匹配是撰写的前置，希望模块化 + 模块共用。

---

## 0. 结论先说

1. **中心对象是章节**，不是"素材"也不是"正文"。三个模块（要求与大纲 / 素材库 / 方案编辑）
   本来就该共用同一个主视觉骨架：**左＝章节树，中＝当前章节的工作区，右＝当前章节的上下文**。
   换模块 = 换中/右两栏的内容，**章节选择与滚动位置不丢**。
2. **把「匹配」做成一个真正的模式**（现在是缺失的）：中间区 = `应答要求条目 × 依据` 的对齐视图，
   右侧 = 素材池（本条目可用 / 供了哪些章），顶部 = 匹配总览与增量按钮。
3. **模块共用要落到"一份实现"**：章节树、章节状态投影、依据渲染各只做一份，
   两个页面 import 同一个模块（而不是各写一套）。本轮已实测出"两套渲染必然漂移"的代价（见 §2.4）。
4. **分三步走**：P0 补齐匹配模式 + 统一依据渲染；P1 统一章节树/状态 + 跨模块带上下文跳转；
   P2 再决定要不要把两个页面合成一个（§8）。

## 1. 现状核实：为什么"点了素材匹配没看到界面"

结论：**匹配确实跑了，但界面没有任何"匹配"的落点**。三条证据：

| 事实 | 数据 |
|---|---|
| 匹配真的执行过 | 项目 18 / thread `f0e6f7ae`：`workflow_runs.stage='materials_review'`（07:31 写入） |
| 依据真的产出了 | 33 章里 **29 章有依据**，共 **112 条**；其中 19 章挂到了具体应答条目（`item_ids`） |
| 界面几乎没变化 | 素材库视图的"匹配结果"只有：章节行上一个绿色小徽标「依据 N」+ 展开卡片后的一段依据列表 |

也就是说：一次匹配（1 份素材、零模型调用）大约 1 秒跑完，状态栏的「沈括匹配素材中…」一闪而过，
之后**主视觉区与匹配前完全一样**。用户找不到"匹配完的结果在哪"是必然的。

另外还有两个空白：

- **没有匹配总览**：33 章里哪些缺依据、缺几条、要补什么素材 —— 没有一个地方能一眼看到。
- **没有空状态**：项目里没有 `source` 素材时点匹配，界面同样毫无反应（正确做法是直接告诉用户"还没有可匹配的素材"并给上传入口）。

### 1.1（已顺手修掉）两套渲染漂移的实证

同一份 `blocks.source`，两个页面各写了一套渲染：

| | project-init（素材库） | workbench（方案编辑） |
|---|---|---|
| 出处 | `locator` → `P12 · 第 8 段 · 切片标题` | `#${chunk_index}` → 契约升级后该字段已不存在，**每行都显示 `#undefined`** |
| 性质 | `kind` 徽标（事实/方案/背景） | 无 |
| 相关度 | 无 | `×11.468872800564196`（BM25 原始分，15 位小数） |

已在 `workbench.html` 临时修正（改用 `locator` + `kind` + `confidence` 百分比），但这只是止血 ——
**根治办法是下面 §5 的"一份依据组件"**。

## 2. 三个模块现状对照

| 模块 | 主视觉区 | 左栏 | 右栏 | 能做的动作 | 看不到的 |
|---|---|---|---|---|---|
| 要求与大纲（project-init outline） | 章节树（8 字段卡片） | 要求/素材上传 + 提炼要求 | 进度环 + 目录 | 拆目录、逐节提炼、改标题/顺序、确认 | 匹配结果 |
| 素材库（project-init matching） | **同一棵章节树**（8 字段 + 依据段落） | 同上（素材列表带「供 N 章」） | 同上 | 素材匹配、确认素材 | 匹配总览、逐条目对齐、人工挂接 |
| 方案编辑（workbench） | 单章正文编辑器 | 章节树 + 生成进度 | 8 张参考卡片 + 匹配素材面板 + 引用栏 | 逐章生成/编辑/保存、引用素材 | 缺依据的章是哪些；依据与条目的对应关系 |

**问题一句话**：三个模块都在渲染"章节"，但各自实现了一套渲染与状态判定；
跨模块跳转是**整页跳转且不带当前章节**（`workspaceUrl()` 其实支持 `blockId`，导航却没用它）。

---

## 3. 设计原则

1. **章节是唯一的导航单元**：任何模块的点击、选中、滚动都以章节为锚，跨模块传递 `blockId`。
2. **匹配是撰写的前置，不是另一个页面**：同一章节能从左到右走完「要求条目 → 依据 → 正文」。
3. **一份数据、一处渲染**：状态投影与依据渲染做成纯模块，谁需要谁 import；页面只管布局。

## 4. 目标信息架构

```
顶部：项目导航（要求与大纲 · 素材库 · 方案编辑 · 质量检查）+ 阶段推进条 + 当前章节目录
┌ 左：章节树（33）─────────┬ 中：当前章节工作区 ─────────────────┬ 右：当前章节上下文 ────────┐
│ 筛选：全部/无依据/未撰写  │  ┌ 大纲模式：8 字段编辑            │  ┌ 素材池 / 归属           │
│ 徽标：依据 N · 正文 x/y   │  ├ 匹配模式：要求条目 × 依据        │  ├ 参考卡片（8 字段）      │
│ 状态点：○待提炼 ●已提炼   │  └ 撰写模式：正文编辑器            │  └ 评审意见 / 版本         │
│        ◐已匹配 ✓已撰写    │                                    │                            │
└──────────────────────────┴────────────────────────────────────┴────────────────────────────┘
底部：当前模式的主按钮（拆目录 / 分析素材归属 / 生成正文）
```

关键：**左栏与顶部在所有模式间共享**，只有中/右栏随模式切换。切模式 = 原地换面板，
不换页面、不丢选中章节。

### 4.1 匹配模式（本次要新建的主视觉）

```
┌ 章节（33）──────────────┬ 2.1 数据层设计 ── 应答要求 6 条 ────────────────┬ 本条目可用素材 ──────┐
│ 筛选: 全部|无依据 4|    │ 覆盖 4/6 · 依据 9 条 · [只看无依据]            │ 素材池（1 份）       │
│       未撰写 33         │ ─────────────────────────────────────────────  │ 规格书.pdf  供12章41条│
│ ▸ 1 项目理解       ●3   │ R1 支持国产数据库       ●2  规格书 P12 ↗      │   ├ 达梦 DM8 …  ↗    │
│ ▾ 2 技术方案       ●10  │ I1 并发 ≥2000 用户      ○0  [找素材 ▾]        │   └ 分层架构 …  ↗    │
│   ▸ 2.1 数据层设计 ●9   │ V1 未提供检测报告即无效  ●1  架构方案 P8 ↗     │ 架构方案.pptx 供6章  │
│   ▸ 2.2 应用层设计 ●6   │ S1 技术方案完整性20分   ○0  [找素材 ▾]        │ [+ 上传素材]         │
│   ▸ 2.3 接口设计   ○0   │ ── 章节级依据（不挂具体条目）2 条 ──           │ 拖拽 = 人工挂接      │
└─────────────────────────┴────────────────────────────────────────────────┴──────────────────────┘
顶部总览：33 章 / 165 条要求 · 有依据 128 条 · 无依据 37 条（信息性，不阻断撰写）
         [分析素材归属（新增 0 份）]  上次匹配：1.2s · 0 次模型调用
```

- `●n / ○0` = 该条目已有 n 条依据 / 无依据；无依据条目**不置灰为错误**，而是给「找素材 ▾」入口
  （方案 §4 已定：无匹配素材不阻断，撰写阶段直接撰写）。
- 右侧素材池 = 素材 → 章节的**反向视图**：每份素材显示「供 N 章 · M 条」，展开看命中章节。
- 人工挂接/解绑：把素材行拖到左侧条目（写 `blocks.source[].item_ids`，`by='human'`、`locked=true`）。

### 4.2 撰写模式（复用现有 workbench，补三处）

1. 章节树换成**共享组件**（带「依据 N」徽标，与素材库完全一致）。
2. 参考卡片区顶部加一行「本条要求：依据 2 条 ↗」——点开跳到该条目的依据（关联 §4.1）。
3. 正文里的 `[依据#3]` 角标与右侧引用栏使用同一份 `MaterialEvidence` 渲染。

### 4.3 全局视图（跨章节，P1）

两屏解决"一屏看全"的问题，比逐章点开快一个数量级（33 章 → 1 屏）：

- **章节覆盖矩阵**：行=章节，列=`大纲 / 提炼 / 依据数 / 条目覆盖 / 正文 / 评审`，可排序筛选；
  这是撰写阶段"覆盖度自检"（方案第 1 点）的天然载体。
- **素材使用矩阵**：行=素材，列=章节（哪些章用了它），用于发现"传了但没用上的素材"。

## 6. 章节级状态机与"下一步"引导

每个章节只有一个状态，界面永远显示"下一步做什么"：

```
待提炼 ──提炼──▶ 已提炼 ──匹配──▶ 已匹配(n 条依据) ──撰写──▶ 已撰写 ──评审──▶ 已通过
  │                     │                    │                    │
  └ 无原文(no_source)   └ 无依据(不阻断)      └ 正文待补           └ 评审问题 n 条
```

- 章节行徽标 = 当前状态（而非"完成/未完成"二元），筛选器按状态过滤 → 直接就是任务清单。
- 顶部主按钮随当前章节状态变化：「提炼本节 / 分析本节素材 / 生成本节正文」。
- 全部章节状态聚合 = 顶部总览（`已提炼 33/33 · 有依据 29 · 已撰写 x/33 · 待处理 n`）。

## 8. 落地顺序

**P0（约 1 天，收益最大，不动路由）**
1. 素材库主视觉改成 §4.1 的三栏匹配工作区（章节树 + 条目×依据 + 素材池）。
2. 顶部匹配总览 + 空状态（无素材时给上传入口）+ 增量按钮文案（"只分析新上传的素材"）。
3. workbench 的匹配素材面板换成共享依据组件（删掉内联实现）。
4. `match-overview` 接口 + 契约测试。

**P1（2–3 天）**
5. 抽出共享 `chapter-tree.js`，两页共用（徽标/筛选/折叠记忆一致）。
6. 导航带 `blockId` + `mode`，跨模块跳转保持章节与滚动位置。
7. 人工挂接/解绑（拖拽 + `PUT /blocks/{id}/evidence`，写 `by='human'`、`locked=true`）。
8. 章节覆盖矩阵（撰写阶段的覆盖度自检载体）。

**P2（观察后定）**
9. 是否把「素材库」并入「方案编辑」成为一个 mode（同一页面三模式）。
   判断标准：P1 之后两个页面的壳是否已 90% 相同 —— 是则合并是机械活；否则维持两页 + 共享组件。
10. 素材使用矩阵、向量召回补语义层。

**风险**：① 三栏布局在 1280 宽下略挤（右栏可折叠，已有 `.ot-edit-panel` 的先例）；
② 抽共享章节树要小心现在两页的折叠/展开状态存在 sessionStorage 的不同 key 上（需统一）；
③ 匹配总览是"信息性"的，**不能**做成红色告警（方案已定：无依据不阻断）。

### 与设计稿的偏差（有意为之）

1. **没有抽 `chapter-tree.js` 这个 DOM 组件**：两个页面的树 DOM 差异太大（素材库带结构编辑面板与折叠记忆，
   方案编辑带生成进度与批量生成），硬合并会把两边的交互都做折。改为共用**真正会漂移的那一层**：
   状态投影、徽标文案、筛选逻辑、依据渲染片段、样式。树 DOM 各页自持。
2. **撰写模式的参考卡片里没有加"本条要求：依据 n 条 ↗"**（P1 第 3 小项，未做）。
3. **覆盖矩阵放在素材库视图**（它回答的是"哪些章节还没找到素材"），撰写覆盖度将来复用同一接口。

### 验证

- 后端 **612 绿**（+11：overview 6、evidence 路由 3、material-chunks 1、人工挂接保留 1）
- 前端 **69 绿**（+6：章节状态/筛选/祖先链/无依据条目列表）
- 隔离后端 + 真实浏览器逐项核对：总览数字、筛选（无依据 6 → 保留祖先链后中间栏不再空白）、
  选中章节出详情、`找素材` 选择器 48 段素材可选、挂接后 DB 落 `by=human/locked=true/item_ids`、
  解绑回滚、覆盖矩阵 11 行、跨模块跳转（`blockId=s2.2` → 方案编辑打开"系统架构设计"）、
  方案编辑的匹配素材面板用共享片段渲染（`be-kind fact` + 出处 + 100%），控制台 0 错误。

## 15. 提炼字段口径修正（2026-09-21，用户拍板「改提炼口径」）

§14 只在**展示层**区分了"要回应的事项"和"评分口径"。这一步改**产出**。

### 改了什么

**① prompt 字段口径**（`agents/prompts.py` 的 `OUTLINE_EXTRACT_INSTRUCTIONS`）

| 字段 | 旧口径 | 新口径 |
|---|---|---|
| `requirement` | "全面提炼、覆盖原文所有要点、不遗漏关键信息" | **只写"我方要做什么"**（投标方应/须/需…）；明确**不要把评分档位、分档描述、得分规则抄进来** |
| `score_items` | "关联的评分项及分值，格式'评分项名称 X分'" | **评分项 + 分值 + 分档口径**（含「优良（7-10分）：…」这类档位） |
| `indicators` | 量化指标与时限 | 同左，但补一句"分档描述不要放这里（属于 score_items）" |

旧口径那句"覆盖原文所有要点、不遗漏"是根因：它逼着模型把评分细则也抄进 requirement。

**② 确定性兜底**（`domain/spec/field_normalize.py` + `zhang_heng.extract`）

prompt 不保证听话，**历史数据更不会因改 prompt 而变好**，所以在提炼落库前加一次按行归位：
把 requirement 里判定为评分口径的行搬到 score_items（去重、保序）。三条保守规则：

1. 只按**行**判定，不拆句子；
2. **带义务动词的句子不搬** —— 「投标响应**须**完全满足招标技术要求，这是获得中等（6分）及以上评分的前提。」
   是"我方要做的事"，搬走会让 requirement 丢抓手（实测误伤，加了 `_OBLIGATION_RE`）；
   `应` 还要排除词内出现（响应/对应/适应/供应/相应/反应/应答），否则「按**响应**度分档评审」
   这种纯评分口径会被当成义务句、漏搬一半（实测漏搬）；
3. requirement 整段都是评分口径时**不动**（主字段不能清空）。

判定规则只有一份：`response_items.is_informative()` —— 展示层与归位层共用，避免"界面说是评分口径、
归位层不认"的发散。

**③ 历史数据回填脚本**（`backend/scripts/normalize_extract_fields.py`）

改 prompt 只影响新提炼。历史数据用这个脚本按同一套规则归位，**默认预演**、`--apply` 才写：

```
cd backend
python -m scripts.normalize_extract_fields --project 18            # 预演
python -m scripts.normalize_extract_fields --project 18 --apply    # 写回
```

两处都写（读者不同）：`blocks` 表（工作台 8 字段展示）+ checkpoint 的 `spec.outline_matrix`
（**撰写阶段读的是它**）。默认只处理**最新一次运行**的行（不传 thread 时以前会把该项目所有
历史 run 的 128 行一起改）。

### 验证

- 后端 **620 绿**（+7：字段归位 6 条含"误伤保护""永不清空"，评分口径 1 条）、前端 74 绿
- 在用户真实项目上**预演**（只读）：33 章里 28 章需归位、共搬走 65 条；抽查
  s1 搬 6 条/保留 1 条、s1.1 搬 6 条/保留 4 条（含"投标方需对招标技术条款作出响应"）、
  s1.2 搬 3 条/保留 4 条（含"投标人须按响应表逐条实质性响应，不得出现未作响应"）
- prompt 结构契约测试仍绿（稳定前缀仍在最前，`build_outline_extract_user` 的缓存结构没变）

## 19. 两侧目录栏真正统一（2026-09-21，用户第二次反馈「还是不一致」）

上一轮只是"看起来像"，这一轮把**根因**挖出来了。

### 根因：workbench 用的 CSS 变量从来没被定义过

```
--ink / --ink-2 / --ink-3 / --ink-4     → 空
--surface / --surface-2                 → 空
--line-2                                → 空
（--text / --muted / --line / --bg-2 有定义）
```

`var()` 解析失败时，属性在 **computed-value 阶段变成无效**：
- `color: var(--ink-3)` → 继承父级 → 该灰的字全是深色
- `background: var(--surface)` → 透明 → 该有底色的块没有底色
- `border: 1px solid var(--line-2)` → 整条声明无效 → 边框退化成 currentColor（深色）

所以方案编辑页整体"发黑、发重"、和素材库不是一套东西。修法：在 `assets/styles.css`
的 `:root` 里把别名变量映射到已有调色板（两页共用一份），一行不改任何选择器。

## 20. 「上下重复」核实与修复（2026-09-21，用户截图反馈）

用户说"该部分上下存在重复"，核到**两处真重复**（不是错觉）：

### ① 界面层：要求原文显示了两次（我上一轮引入的）

「本章要求」条里 `#req-bar-main` 显示要求原文，而展开的 8 张卡里**第一张就是「应标要求」**，
同一段文本上下各一遍。修法：展开字段时给 bar 加 `.fields-open`，`#req-bar-main` 隐藏。

### ② 数据层：requirement 末尾的【评分对应】与 score_items 逐条重复

用项目 18 的 `s2.1 方案可行性` 实测：

```
requirement 共 12 行，其中 7 行是【评分对应】：
  【评分对应】方案可行性 评分项 8-12分   ← 与 score_items 的「方案可行性 8-12分」完全同值
  …（7 行全部重复）
score_items 7 行
```

来源是提炼 prompt 里那句"若有【评分上下文】…请在末尾用「【评分对应】XXX X分」追加" ——
它让模型把已经结构化写进 `score_items` 的分值又追加到 `requirement` 末尾。

**修法（三层）**：
- **prompt**：追加前先判断 `score_items` 里有没有 → 已有就**不要追加**；`indicators` 明确
  "不要复述评分档位或分值"（原来只写了"分档描述不要放这里"，模型照样复述）。
- **落地归一化**（`domain/spec/field_normalize.py`）：`normalize_row_fields` 新增
  `dropped` —— requirement 里以【评分对应】/【评审对应】开头、且分值已存在于 score_items 的行**直接删**；
  score_items 里没有的仍照老行为补进去（不丢信息）。
- **指标复述清理**：`indicators` 里带"档位/总分/满分/得分/评分/分值"且**数字全都能在
  score_items 找到**的行也算复述 → 删。数字比较时**排除 0**（"0分（没有内容不得分）"是档位下界，
  不排除的话「…得分档位：8-12分、5-7分、1-4分、0分」会因为多一个 0 而漏判）。
  真正的量化指标（"不少于35人""交付周期90天"）没有这些字样，不会被碰。
- **回填脚本**同步报三个数：`moved` / `dropped_duplicate` / `pruned_indicators`。
