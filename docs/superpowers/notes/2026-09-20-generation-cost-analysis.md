# 生成链路费用分析与降本方案

- 日期：2026-09-20
- 作者：江河（与 DSH 协作）
- 数据来源：`backend/data/ge_solution.db` 的 `llm_usage` 表（183 条真实调用记录，2026-09-17 ~ 09-20）
- 结论摘要：**输出 token 占总费用约 84%**；当前约 **13% 的 token 是纯浪费**；按本方案实施可**降低约 55–65% 的生成费用**

---

## 1. 实测基线与账单结构

### 1.1 总量

| 指标 | 实测值 |
|---|---|
| 真实调用记录 | 183 条（`LLM_MODE=mock` 不落库，故全部是真实 API 调用） |
| 输入 token 合计 | 约 118,000 |
| 输出 token 合计 | 约 488,000 |
| **输出 : 输入** | **4.1 : 1** |
| 失败调用 | 80 条（44%） |
| 失败消耗 token | 80,668（占总量 13%） |

**输出 token 是输入的 4 倍**——而主流模型输出单价约为输入的 3–4 倍，因此：

> **成本 ≈ 输入 × 1 + 输出 × 4 ⇒ 输出占 84%，输入占 16%。**
> 降本必须主攻**输出 token**，优化输入（截断、缓存）是次要战场。

### 1.2 分环节实测（仅统计成功调用）

| call_site | 模型 | 次数 | 输入均值 | 输出均值 | 输出上限 | 备注 |
|---|---|---|---|---|---|---|
| `outline_draft` | v4-pro | 11 | 1,742 | **7,963** | 11,838 | 目录派生，整版输出 JSON |
| `outline_draft` | flash | 10 | 1,673 | 6,715 | 11,110 | 同上 |
| `outline_extract` | v4-pro | 24 | 876 | **4,296** | 6,721 | **8 字段提炼，每节一次** |

| `section_outline` | flash | 4 | 1,068 | 2,499 | **2,500（触顶）** | 写作大纲，**实际近乎全废** |

### 1.3 失败构成（浪费的钱在哪）

| 失败原因 | 次数 | 是否计费 | 说明 |
|---|---|---|---|
| **402 Insufficient Balance** | **53** | 否（未推理） | 3 条配置（deepseek-flash / v4-flash / v4-pro）全部余额不足 |
| `section_outline` 输出截断（`finish_reason='length'`, `content_len=0`） | **23** | **是，照扣 token** | 推理模型的 max_tokens=2500 **全被 reasoning 吃掉，正文 0 字** → JSON/文本为空 → 重试再烧一遍 |
| 请求超时 | 1 | 未知 | 60s oneshot 超时（既有已知问题） |
| 其他（0 token） | 3 | 否 | — |

**两个独立的问题**：
1. **运维**：三个 key 的账户余额都烧完了（这才是「项目阻塞」的真相——不是缺 key）。
2. **代码**：`section_outline` 的 `max_tokens=2500` 对推理模型偏低，**100% 空手而归还照扣费**（v4-pro 实测 14/14 失败）。同一病因在 `zhang_heng.py:246` 已有记录（`doc_summary` 的 max_tokens=2000「连思考都写不完」，该步已停用），但 `section_outline` 没修。

## 2. 单轮费用模型（以项目 17 的 208 个 block 为样本）

每 block 的调用链：`rerank`(1) + `section_outline`(1) + `stream_generate`(1) + `outline_extract`(1)，整轮再叠加评审 `王安石 + 包拯`(2/block)。

| 环节 | 调用次数 | 输入/次 | 输出/次 | 输入合计 | 输出合计 | 加权成本* |
|---|---|---|---|---|---|---|
| `outline_extract` | 208 | 850 | **4,200** | 177K | **874K** | **3.67M（29%）** |
| `stream_generate` | 208 | 840 | 3,300 | 175K | 686K | 2.92M（23%） |
| `section_outline` | 208 | 1,070 | 2,500 | 223K | 520K | **2.30M（18%）——当前近乎全废** |
| `rerank`（估） | 208 | ~4,300 | ~600 | 894K | 125K | 1.39M（11%） |
| 双评审（估） | 416 | ~1,200 | ~1,000 | 499K | 416K | 2.16M（17%） |
| `outline_draft` | 1 | 1,700 | 7,400 | 1.7K | 7.4K | 0.03M |
| **合计** | **~1,249 次** | | | **≈1.97M** | **≈2.63M** | **≈12.5M** |

\* 加权成本 = 输入 × 1 + 输出 × 4（按输出单价 = 输入 4 倍折算）。**单价请按你的实际账单换算，本节的比例结论与单价无关。**

> **未实测项**：`rerank` 与双评审在真实运行中**从未跑过**（`llm_usage` 里没有这两类 call_site，重排/评审此前只在 mock 下走过），上表按 prompt 构造代码估算，标注为「估」。

## 3. 降本方案（按 ROI 排序）

### P0-1 去掉 / 合并 `section_outline`（省 ~18%）

- **问题**：每 block 一次调用，`max_tokens=2500` 被 reasoning 吃光，返回空串；实测 23/27 失败、成功的 4 次输出恰好卡在 2,499–2,500（同样是截断）。**这一环目前只花钱不产出。**
- **方案 A（推荐）**：把「写作大纲」合并进 `stream_generate` 的 `extra_prompt`，一步出大纲+正文 → **省掉全部 N 次调用**（208 次 / 单轮 2.3M 加权成本）
- **方案 B（保守）**：保留该步但把 `max_tokens` 提到 6,000+ 并改用非推理模型。不省钱，只止血（让它真能产出）
- 涉及：`dispatcher.generate_section_outline`、`zhuge_liang._generate_tech`、`SECTION_OUTLINE_SYSTEM`

### P0-2 给输出加**上限**，不只是下限（省 ~9%）

- **问题**：`_stream_generate` 的提示词写的是「扩写后内容**不少于** {target_words} 字」，只有下限没有上限。`target_words=600`，实测输出 3,300 tokens ≈ 2,200 汉字（**3.7 倍**），且 `max=4,096` 正好顶到 `max_tokens` 上限 —— **正文被硬截断**（质量风险：章节可能断在半句话）。
- **方案**：提示词改为区间约束（如「控制在 600–900 字，超过 1,200 字必须收束」），并按章节类型设档（概述/承诺类短、方案类长）。字数变**受控**而非「越长越好」。
- 预期：输出降 ~40%（686K → ~410K）

### P1-3 判断类任务改用**非推理模型**（省 ~26%，最大单点）

- **问题**：`outline_extract` 的活是「按 8 个字段抽取」，合理输出约 300–500 token，**实测 4,200 token**——差额全是 reasoning。抽样失败记录显示 `reasoning_len≈4,000 字符`。抽取、重排、评审都是**判断类**任务，不需要长思考却按输出计费，还额外拖慢 35s/次。
- **方案**：按 `call_site` 分级路由——
  - 判断类（`outline_extract` / `rerank` / 双评审 / `scope_select`）→ 非推理或 flash 档
  - 生成类（`stream_generate` / `outline_draft`）→ 保留强模型
  - 当前 3 条配置里 2 条是 pro 级且**按轮询随机分配**，便宜的活会随机落到贵模型上
- 预期：extract 输出 874K → ~110K（-88%），评审同步下降

### P1-4 批量合并逐节调用（省输入重复 + 调用数）

- **问题**：`outline_extract` 每节一次调用（208 次），每次都重复送 system prompt + 评分上下文等固定前缀；`rerank` 同理每 block 一次。
- **方案**：extract 每批 5–8 节一次调用（输出仍分节标注，代码侧拆分）；**调用数 208 → ~30**，固定前缀重复开销同比例下降。
- 风险：单次输出变长（8×400=3,200 token），需配合 P1-3 的非推理模型一起做。

### P1-5 失败重试要**分类**（省时间与配额，止血）

- **问题**：`dispatcher` 里所有调用都是 `except Exception` → 无差别换下一条配置重试。**402/401/400 这类不可重试错误也会把 3 条配置全试一遍**（实测 53 次 402 就是被这样放大的），既拖慢又掩盖真实原因。
- **方案**：错误分类——可重试（超时/429/5xx）才换 config；不可重试（401/402/403/400）立即抛出并给出明确提示（如「账户余额不足，请充值或更换配置」）。启动期余额预检一次。

### P2-6 提高缓存命中率（输入侧）

- 实测命中率：`outline_draft` 39%、`stream_generate` 29%、`section_outline` 28%、`outline_extract` 21.5%（deepseek 上下文缓存已部分生效）。
- **方案**：把**稳定前缀**（system prompt + 6 条核心规则 + 固定模板）严格置于消息最前且内容不变，动态内容（原文/素材/要求）一律后置；避免在固定段中间插变量破坏前缀。命中率提到 60–70% 可再降输入成本 ~30%。

### P2-7 修 `_generate_doc_summary` 的预算记账 bug（恢复该步前必做）

- 已知缺陷：标题行不扣预算，实测 379 章时实际输入 15,615 字符而非预算的 8,000（白吃 7,615）。该步现已停用，**若要恢复必须先修**，最小修法是直接复用 `build_spec_digest(sections, budget=8000)`。

### P2-8 补齐费用归集能力（管理手段）

- **缺口**：`llm_usage` 表**没有 `project_id` / `thread_id` 列**，无法回答「这次运行花了多少」「哪个项目最烧钱」。表里已有 `call_site/model/tokens/latency`，加两列即可按运行归集，前端可展示每轮费用。
- 同时建议落库 **推理 token 数**（现在只在失败时的 error 文本里以字符串形式存在），否则「reasoning 吃掉多少」只能靠猜。

## 4. 预期效果汇总

| 措施 | 输出 token 变化 | 加权成本节省 |
|---|---|---|
| P0-1 去掉 section_outline | −520K | ~18% |
| P0-2 输出加上限 | −275K | ~9% |
| P1-3 判断类改非推理 | −800K+ | ~26% |
| P1-4 批量合并 | 输入 −150K | ~2% |
| P2-6 缓存优化 | 输入 −300K | ~3% |
| **合计（去重后）** | 2.63M → **~1.05M** | **≈55–65%** |

---

## 5. 建议执行顺序

1. **立即止血**：P1-5（重试分类）+ 充值/更换余额充足的 key —— 否则现在每次运行都有一半时间在空跑
2. **本轮实施**：P0-1 + P0-2（一个流程合并 + 一处提示词约束，改动小、收益 27%）
3. **紧随其后**：P1-3 + P1-4（需要按 call_site 配模型档位，是收益最大的一项）
4. **持续优化**：P2-6 / P2-7 / P2-8

> ⚠️ 所有改动都应按项目既有规范配 mock 测试，并在真实项目上对比「单位费用产出的可用正文字数」后再全量启用。
