## 二、致命问题（必须改，不改会直接扣分/废标风险）

### 🔴 1. 图没出来，还漏了内部语法

```
图  type=layered 现状与目标对比图图示      ← 这是图题，不是图
```

- 「现状与目标对比图」这一节有 **1,096 字在讲"图怎么画"**（横轴是四个维度、纵轴四层、色带表示现状与目标…），**但文档里没有图** ✗
- 更严重：`type=layered` 是生成系统的内部语法，出现在交付文件里 → 评委一眼看出是机器生成未整理
- **改法**：① 真正插入一张图（分层带状对比图）② 图题改为「图 1-1 现状与目标差距对比」③ 图下只留 3~5 行解读，删掉"怎么画"的描述

### 🔴 2. 14 处【待补充】占位

实测 `【待补充】` 出现 **14 次**，例如：

| 位置 | 占位内容 | 影响 |
|---|---|---|
| 政策依据 | 招标文件条款编号、发文机关、文号 | 政策引用不完整，依据不硬 |
| 项目现状 | 现有系统等级保护落实情况 | **现状描述整段失去事实支撑** |
| 项目现状 | 项目单位名称、业务量、用户数 | 评委无法判断"是否真的了解项目" |
| 目标体系 | 考核指标值 | 目标不可验收 |

> 技术应答出现【待补充】= 未完成稿。**要么补齐，要么删掉该断言**（不要留着占位交上去）。

### 🔴 3. 内部术语外泄

- 「**任务包**」出现 **8 次**（"任务包已确认的政策结论""任务包已载明事实"）→ 这是内部工作包叫法，评委看不懂、也不知道是什么文件 → 统一改成「招标文件」「需求文件」「技术规范书」。
- 「可核验/可追溯/可度量」这类词出现多次但**没有一处给出具体口径**，属于自我评价而非应答内容。

## 三、严重问题（影响"深入、全面"得分）

### 🟠 4. 现状描述没有事实

抽查「项目现状描述」（1,196 字）：

| 应有 | 实际 |
|---|---|
| 项目单位是谁、现有系统叫什么/什么版本/什么时候上线 | 无 |
| 系统规模（用户数、并发、数据量、接口数） | 无 |
| 现有安全建设情况（等保级别、已有哪些措施、测评结论） | 无（写了"【待补充】"）|
| 现有数据管理现状（有没有分类分级、权限台账） | 只有定性："数据分散留存，尚未形成统一…" |

**评委视角**：整段可以用在任何项目上 → 说明"没做功课"。
**改法**：每一条现状判断后面跟**一个事实来源**（合同/测评报告/访谈记录/系统截图），或直接引用招标文件里的现状描述原文。

### 🟠 5. 全文 0 个量化指标

- 带单位数字（%、个、项、人、万、亿、台、套、小时、天）出现 **0 次**
- 「项目目标体系」写了五段"目标"，但**没有一个可验收的数值或阈值**：
  - 现在写：「验收阶段证明已落实网络安全保护义务」✗
  - 应该写：「等级保护测评得分 ≥ 90」（若招标有要求）+「渗透测试高危漏洞 0 个」+「数据分类分级覆盖 100% 业务表」

### 🟠 6. 政策依据不够硬

| 问题 | 现状 | 应补 |
|---|---|---|
| 缺标准号 | 「网络安全等级保护相关技术与管理措施」出现 **4 次**，全文**没有 GB/T 22239** | 基础类：GB/T 22239-2019；测评：GB/T 28448-2019 |
| 缺文号 | 只有法名，没有"主席令第 XX 号"或发文机关 | 三法各补文号 + 施行日期（日期已有 ✓）|
| 无条款级引用 | 【来源】35 处，全是「【来源：招标文件-项目背景与建设依据】」这类**自指** | 关键要求要引到"第 X 条"或"技术规范书 X.X" |
| 无配套条例 | 只引三法 | 数据安全领域还应看《网络数据安全管理条例》（2025-01-01 施行）等落地文件 |

### 🟠 7. 大量"拟实施/将/有待"式弱表述

实测：「拟」5 次、「待」19 次、「将」15 次、「尚需」3 次。

- 典型：「数据分类分级与权限控制规则将按实施方案明确」→ **技术标里这是"我们还没想好"** ✗
- 应改为「数据分类分级按“业务域—数据类—敏感级”三级模型设计，设计阶段产出分类分级清单，实施阶段完成 100% 业务表打标」✓
- 原则：**能确定的写死；确实依赖调研的，写清"何时、由谁、交付什么"**（例如"合同签订后 10 个工作日内由我方完成数据摸底并提交清单"）。

### 🟠 8. 三张表没有表号，且与正文重复

| 表 | 行×列 | 问题 |
|---|---|---|
| 表「政策文件/核心要求/对应工作/落实阶段」| 4×4 | 与正文「重点政策响应安排」重复；无表号 |
| 表「对比维度/现状/目标」| 5×3 | 与「现状与目标差距可归纳为三点」重复 |
| 表「维度/现状/目标/主要差距/影响程度」| 6×5 | 与「现状差距分析」三段正文重复 |

**改法**：正文说结论（3 行），表格承载细节（全量覆盖），表题统一为「表 1-1 政策要求与项目对应关系」并前置一行引言「如表 1-1 所示」。**表2 与表3 建议合并**（内容高度重叠，都是"维度—现状—目标—差距"）。

## 七、可直接复用的改法示例（三条）

**① 现状（差 → 好）**
- 差：「数据分散留存，尚未形成统一的管理机制」
- 好：「现有 3 套业务系统分别由不同厂商建设，用户与权限各自维护（来源：XX 系统运维记录，2025-06），未建立统一身份与权限台账，2025 年审计提出 2 项权限越权问题」

**② 目标（差 → 好）**
- 差：「验收阶段证明已落实网络安全保护义务」
- 好：「通过等级保护测评（目标 ≥ 90 分，等保三级）；高危漏洞 0 个、中危 ≤ 3 个；数据分类分级覆盖 100% 业务表；权限台账覆盖 100% 账号，季度复核」

**③ 难点（差 → 好）**
- 差：「能力瓶颈：安全技术措施与管理制度的对应设计能力需加强」
- 好：「难点：等级保护 2.0 的三级要求与现有系统架构存在 7 项不满足项（其中 3 项需改架构）。影响：若在设计阶段不闭环，实施阶段返工约增加 15% 工期。措施：设计阶段先做差距矩阵 + 架构评审，逐项给出“改造/补偿/风险接受”。验证：设计评审记录 + 测评机构预评估意见」

## 八、结论

- **可以交的部分**：政策依据梳理（法条准确）、章节结构、表格维度设计
- **必须先修的部分**：图（P0）、【待补充】14 处（P0）、内部术语（P0）
- **决定得分上限的部分**：现状事实、量化目标、量化验收判据 —— 这三项不补，这一模块只能拿"框架分"，拿不到"深入理解"的分数
